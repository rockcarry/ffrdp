# 第一部分：v1.0.0 —— 帧格式与基本协议（§1.1 ~ §1.7）

## 1.1 帧格式

### 1.1.1 帧头（4 字节，所有帧统一）

```
byte 0      : 帧类型 type
byte 1 ~ 3  : 帧序号 seq（24 bit，小端）
```

- 访问宏：`GET_FRAME_SEQ(f) = *(uint32_t*)(f)->data >> 8`，
  `SET_FRAME_SEQ(f, seq)` 保留 byte 0 的 type，只写高 24 位 ⇒ **类型与序号共用一个 4 字节头**。
- `seq` 为 24 bit ⇒ 回绕周期 2^24 帧，序号比较一律用"距离"（`seq_distance`）而不是大小。

### 1.1.2 数据帧

```
data_full  frame: 0x00 seq0 seq1 seq2 data ...              ← 装满 MSS 的数据帧
data_short frame: 0x01 seq0 seq1 seq2 data ...              ← 未装满就发出的数据帧
```

- **两种数据帧都不带 FEC 尾部的 2 字节**，载荷长度 = 帧长 − 4。
- `data_short` 的产生：应用送来的数据没填满一个 MSS 时，帧会先攒着；
  等 `FFRDP_FLUSH_TIMEOUT`（500ms）超时、或应用显式 `ffrdp_flush()` 时，
  以 `SHORT` 类型发出（避免小包被无限期攒住）。
- 接收端用 `FULL` 帧的长度学习对端 MSS（`rmss = 帧长 − 4`），
  用 `SHORT` 帧仅计数 —— 两者都**不进入接收数据流**（它们是用来测量与维持链路的）。

**接收端必须拒绝的输入**（不是风格问题，是内存安全问题 —— 见 `notes.md` 12）：

- **长度下限**：`FULL` 帧必须 `> 4` 字节、FEC 类型帧必须 `> 6` 字节（即**至少要有一个载荷字节**）。
  更短的帧描述不了任何东西，而 `rmss` 正是**用帧长学来的**（`rmss = 帧长 − 4 / − 6`）⇒ 4 字节的
  `FULL` 帧会让它变成 **0**（它随后被当作除数 ⇒ 除零）；4 字节的 FEC 帧会让它**下溢**、载荷长度
  变成**负数**（随后被当作拷贝长度 ⇒ 40 亿字节的 `memcpy`）。违反者丢弃并计入 `counter_rx_bad`。
- **乱序队列有界**：帧比 `una` 更远于**我们广告的窗口**（它在 ACK 里占 1 字节 ⇒ ≤ 255 帧）时一律
  丢弃并计入 `counter_recv_drop` —— 守规矩的对端受这个信用额度约束，更远的只能是谎话或重复；
  不丢就等于允许"一个数据报换一个约 1.5KB 的帧"。

### 1.1.3 FEC 帧

```
data_fecN frame: 0xN seq0 seq1 seq2 data ... fec_seq0 fec_seq1     (N = 2 ~ 32)
```

- 帧类型值**就是**冗余度 N（每 N 个数据帧附 1 个 FEC 帧）；
  `N = 2` 时同时是 `FEC2`（类型 2），最大 `32`（`FEC32`，类型 0x20）。
- 载荷长度 = 帧长 − 4 − 2（末 2 字节是 16 bit 的 `fec_seq`）。
- 详见1.5 节。

### 1.1.4 ACK 帧

```
ack frame: 0x21 una0 una1 una2 mack0 mack1 mack2 rwnd [dups]
```

| 字节 | 内容 |
|---|---|
| `[0]` | 类型 `0x21` |
| `[1..3]` | `una`（24 bit）：**第一个还缺的帧号**（该号之前全部已收到）|
| `[4..6]` | `mack`（24 bit）：乱序到达位图，见1.2 节 |
| `[7]` | `rwnd`（8 bit）：本端接收缓冲还能装多少帧（0~255）|
| `[8]` | **v1.1.0 新增，可选**：自上一个 ACK 以来收到的重复帧数（`dups`），见 见 §2.1.3 |

- 基本长度 **8 字节**；只有"有内容可报"时才发第 9 字节。
- `rwnd = (接收缓冲剩余字节) / rmss`，上限 255。

### 1.1.5 QUERY 帧

```
query frame: 0x22                      ← 只有 1 个字节
```

- 发送端在**没有数据要发**、且距上次询问超过 `FFRDP_QUERY_CYCLE`（500ms）时发出；
- 对端收到 QUERY 会**立刻回一个 ACK**（即"非延迟 ACK"的另一面：确认不靠定时器攒）。
- 用途：让发送端在空闲时也能持续获得对端窗口与 `una` 信息。

### 1.1.6 帧类型取值

| 取值 | 帧 |
|---|---|
| `0x00` | `data_full` |
| `0x01` | `data_short` |
| `0x02 ~ 0x20` | `data_fecN`（N = 2~32，类型值 = N）|
| `0x21` | `ack` |
| `0x22` | `query` |

⇒ **数据帧占 `0x00~0x20`，控制帧从 `0x21` 起**。

## 1.2 mack 语义（怎么表达"缺哪一帧"）

`mack` 是 24 bit 位图，`bit i`（i = 0..23）对应帧号 **`una + 1 + i`**：

```
una  = 16, mack = 0x000003
  ⇒ bit0 = 1 ⇒ 帧 17 已收到
  ⇒ bit1 = 1 ⇒ 帧 18 已收到
  ⇒ 更远的位为 0 ⇒ 19 及以后尚未收到
  ⇒ 帧 16 尚未收到（una 就是"第一个还缺的帧"，不在位图里）
```

- 发送端据此**只重传确实缺失的帧**（选择重传），而不是"从 una 开始整段重发"。
- 位图只有 24 位 ⇒ 只能报出 `una` 之后 24 帧以内的乱序；
  **更远的乱序报不回去**（这是 v1.1.0 明确记录的一条局限：已按真机数据评估过，结论是**暂不加宽**，见 见 §2.3.4）。
- `una + mack` 同时支撑**快速重传**：位图里出现"洞"（某位为 0 而更高位为 1）即知该帧可能丢失。

## 1.3 通信流程

### 1.3.1 发送

- 应用数据被切进帧、入发送链表，首发的帧消耗**对端信用**（`swnd`，见 见 §1.3.4）；
- 首发时打 `FLAG_FIRST_SEND` 标记；此后该帧的"是否已首发"决定它算不算"在途"。

### 1.3.2 接收与确认

- 收到数据帧 ⇒ 插入**按序号排序的接收链表**（重复帧丢弃并计数）；
- 连续可交付的部分搬进应用接收缓冲，`recv_seq` 前移；
- 只要收到数据或 QUERY（`got_data || got_query`）就**立刻回 ACK** ⇒ 非延迟 ACK。

### 1.3.3 重传（两种）

| 方式 | 触发 | 行为 |
|---|---|---|
| 超时重传 | `now > tick_timeout` | 重发该帧，并触发拥塞控制事件 `CEVENT_ACK_TIMEOUT` |
| 快速重传 | ACK 的 mack 报出"洞" | 打 `FLAG_FAST_RESEND`，在下一次 `ffrdp_update()` 里立即重发 |

- v1.0.0 的快速重传是**立刻**执行的（v1.1.0 加了等待纪律，见 见 §2.2 / 2.3.3.3）。

### 1.3.4 流控与窗口（三个不要混用的量）

| 量 | 含义 | 谁决定 |
|---|---|---|
| `rwnd` | 对端**接收缓冲**还剩多少帧（经 ACK 传回）| 接收端 |
| `swnd` | 对端授予的**信用**，每个 ACK **重新授予**一次 | 接收端（随 ACK 更新）|
| `wait_snd` | 应用侧排队帧数（`FFRDP_MAX_WAITSND = 256`）| 本端 |

- `ffrdp_send()` 在发送队列满时返回失败（应用被背压）；
- **`swnd` 是缓冲区大小，不是链路能跑多少** —— 这条认识是 v1.1.0 的起点（见 见 §2.3.2）。

## 1.4 RTT / RTO 计算（v1.0.0）

**测量**：

```
rttm = 当前时间 - 报文发送时间
```

关键限制：**不能对重传报文测量** `rttm` —— 收到 ACK 时无法判断它确认的是原始报文还是重传报文
（Karn 规则）。

**初始化 / 迭代**（EWMA）：

```
rtts = rttm;                                  rttd = rttm / 2;
rtts = (1 - 1/8) * rtts + (1/8) * rttm;       rttd = (1 - 1/4) * rttd + (1/4) * |rttm - rtts|;
```

**RTO**：

```
正常：  rto = rtts + 4 * rttd;
超时：  rto = 1.5 * rto;                 ← v1.0.0：每个超时帧各退让一次
      rto = max(rto, FFRDP_MIN_RTO);     ← v1.0.0 为 **16 ms** ✓
      rto = min(rto, FFRDP_MAX_RTO);     ← 2000 ms
```

两个重要推论（后面反复用到）：

1. **`rtts` 恒 ≤ `rto`** —— 因为 Karn 规则只统计"从未超时"的帧
   ⇒ 想用 RTT 统计量把 RTO 抬上去是**无效**的（v1.1.0 里那次尝试空转就是这个原因）；
2. v1.0.0 的超时退让是"**每帧一次**"：同一轮里多个帧同时超时，
   `rto` 会被连续乘 1.5 直到上限（v1.1.0 改为**每往返一次**，见 见 §2.3.3）。

## 1.5 FEC（前向纠错）

- **异或方式**：发送端把连续 N 个数据帧逐字节异或，得到 1 个 FEC 帧；
- 只对 **`data_full`（满 MTU 长度）** 的帧做（长度相同才能异或）；
- `data frame` 的**最后 2 字节**用作 FEC 的 `fec_seq`（16 bit）；
- 冗余度 N 由**帧类型**携带（`data_fecN`，N = 2..32）；默认 0（不启用）。
  发送端每 N 帧发一个 FEC 帧，接收端用同一分组内的帧做异或恢复丢失的那一帧。

**实测结论：默认关闭。** 目标链路真丢包仅 ~0.2%，而 FEC **只救"丢"、不救"迟到"**；
5 倍空口换来的是更多超时（实测重传率反而升到 7.9%）⇒ 关掉是净收益。

## 1.7 v1.0.0 的已知问题（v1.1.0 的出发点）

1. **重传几乎全是白费的**：对端确认"重复帧"的数量 ≈ 本端重传次数 ⇒
   帧其实早就到了，只是**迟到** ⇒ "丢包"这个信号分不清"丢"与"迟到"；
2. **RTO 落在延迟分布中位数附近** ⇒ 长尾（迟到帧）引发大量伪超时；
3. **唯一的刹车是对端缓冲区大小**（`rwnd/swnd` 有 148~256 帧），而链路只需要几帧 ⇒
   发送端会**自愿把路径上的队列灌满**，形成约 200ms 的常驻排队延迟
   （`ping` 可见：跑传输时 217~228ms，传输一停立刻回到 4~7ms）；
4. 超时退让"每帧一次" ⇒ 突发超时会把 RTO 连乘到上限。

⇒ 第二部分逐个说明 v1.1.0 怎么处理它们。

# 第二部分：v1.1.0 —— 协议逻辑优化（§2.1 ~ §2.5）

## 2.1 先说结论：帧格式不变

### 2.1.1 逐项对比（v1.0.0 → v1.1.0）

| 项 | v1.0.0 | v1.1.0 | 是否变化 |
|---|---|---|---|
| 帧头 | 4 字节：type + 24 bit seq | 完全一致 | **未变** ✓ |
| 帧类型取值 | `0x00/0x01/0x02~0x20/0x21/0x22` | 完全一致（**无新帧类型**）| **未变** ✓ |
| 数据帧（full/short）| 4 + 载荷 | 完全一致 | **未变** ✓ |
| FEC 帧 | 类型 = N(2~32)，末 2 字节 `fec_seq` | 完全一致 | **未变** ✓ |
| ACK 帧 | 8 字节：`0x21 + una(24) + mack(24) + rwnd(8)` | **前 8 字节逐字节相同**；尾部**可选**第 9 字节 `dups` | **兼容扩展** ✓ |
| QUERY 帧 | 1 字节 `0x22` | 完全一致 | **未变** ✓ |
| `seq` / `una` / `mack` 位宽 | 24 / 24 / 24 bit | 完全一致 | **未变** ✓ |
| `rwnd` 位宽 | 8 bit | 完全一致 | **未变** ✓ |
| 对外 API（`ffrdp.h`）| 8 个函数 | **逐字相同** | **未变** ✓ |

代码级证据（`git show v1.0.x:ffrdp.c` vs 当前 `ffrdp.c`）：
`SET_FRAME_SEQ` / `GET_FRAME_SEQ` 宏、帧类型枚举、帧分配与长度计算
（`4 + size + (type <= SHORT ? 0 : 2)`）、FEC 异或与 `fec_seq` 处理、ACK 前 8 字节的构造
（`*(uint32_t*)(data+0) = (ACK << 0) | (una << 8)`、`*(uint32_t*)(data+4) = mack | (rwnd << 24)`）
**全部逐字相同** ✓。

### 2.1.2 为什么是"兼容扩展"而不是"新版本帧"

`dups` 放在 ACK 尾部，两个方向都安全：

| 方向 | 行为 |
|---|---|
| **新发送端 ← 老接收端** | 老对端只发 8 字节 ⇒ 解析时 `ret >= 9` 不成立 ⇒ `dups` 读到 0 ⇒ **RTO 下限永不移动，行为退回 v1.0.0** ✓ |
| **老发送端 ← 新接收端** | 老对端解析 ACK 只读前 8 字节（不校验长度）⇒ **多出来的第 9 字节被忽略** ✓ |
| **新 ↔ 新** | 只有"确实有重复帧"时才多花这 1 字节；链路干净时 ACK 长度与 v1.0.0 **完全相同** ✓ |

⇒ 因此 v1.1.0 的改动**可以在两端不同时升级的情况下上线**（收益只在两端都升后出现）。

### 2.1.3 唯一新增的线上字段：`dups`

| 项 | 说明 |
|---|---|
| 位置 | ACK 帧第 9 字节（下标 8）|
| 含义 | 自上一个 ACK 以来，接收端收到**它早就有的**重复帧个数（夹到 255）|
| 发送条件 | `dup_seen != 0` 才发（否则 ACK 保持 8 字节）|
| 用途 | 发送端据此算 `waste = 对端重复上报 / 本端重传`，驱动 RTO 下限与快重传纪律 |
| 为什么必须来自对端 | 本端的重传计数器只知道"我重传了几次"，不知道"对端是不是早就有" ⇒ 这是链路上**唯一**不被本端计数污染的证据 |

## 2.2 v1.1.0 规格摘要

v1.1.0 在**协议逻辑**上有四处改动，全部作用于发送端的内部决策，**不改变帧的格式**：

| # | 机制 | 触发 | 动作 | 参数（默认）| 详见 |
|---|---|---|---|---|---|
| 1 | **RTO 下限** `rto_floor` | 证据窗口（128 次重传 / 约 1 秒）结束时 | 白费多 ⇒ 抬下限；白费少 ⇒ 归还；再施加相对上限 `max(3×rtts, 100ms)` | `WASTE_HI/LO = 80/40%`、上限 1000ms | §2.3.3.2 |
| 2 | **快重传纪律** `hole_wait` | ACK 报出"洞" | 白费多 ⇒ 等 `3×rtt`（≤300ms）再重传；白费少 ⇒ **立刻**（= v1.0.0 行为）| 同上 | §2.3.3.3 |
| 3 | **在途量闸门** | 每次首发 | 限制"已首发未确认"的帧数；**重传不受限** | `FFRDP_INFLIGHT_MAX = 64`（保守默认）| §2.3.3.4 |
| 4 | **延迟探测** | `rtts > 3 × rtt_min`（或有白费）且砍半后的上限**严格低于当前上限**、不越过 4 帧地板 | 把在途上限砍一半，保持 `2×rtt + 500ms`；**典型** RTT 比探测前低 **≥2ms** 且确认速率没掉 ⇒ 保留，否则立刻还原 | `QUEUE_RATIO = 3`、`RTT_DROP_MS = 2`、`RATE_KEEP = 85%`、`INFLIGHT_MIN = 4` | §2.3.3.5 |

另外两处**非协议**改动（v1.1.0 一并做了）：

- **超时退让改为"每往返一次"**（v1.0.0 是每帧一次 ⇒ 突发超时会连乘到上限）；
- **诊断输出**（`ffrdp_dump`）补上 `build`/`rtt_min`/`inflight`/`cap`/`probe` 等行，便于维护与自证版本。

以下2.3 节给出这些改动的**依据、证据与被否掉的路线**。

## 2.3 依据与证据

### 2.3.1 目标与优先级

项目要求：**低延迟** + **弱网下带宽稳定**。据此确定取舍顺序（项目方拍板）：

**① 优先降低重传率 → ② 然后保证低延迟 → ③ 然后保吞吐量**

可量化判据：

| 优先级 | 判据 | 对设计的要求 |
|---|---|---|
| ① 重传率 | 客户端 `counter_resend_ratio`：38.7% → **< 5%** | 允许为此适度延长 RTO / 牺牲修复延迟 |
| ② 低延迟 | 平均延迟不恶化；RTO 取"能压住重传率的最小值" | 不接受"用秒级 RTO 换重传率"；需要快修复路径 |
| ③ 吞吐量 | 有效载荷吞吐不下降 | 不作否决项，但不能明显掉 |

### 2.3.2 诊断：问题真正的成因

#### 2.3.2.1 观测手段

`ffrdp_dump()` 输出的关键字段（本轮新增的用 ★ 标注）：

| 字段 | 含义 |
|---|---|
| `rttm` | **最近一次**往返采样（名字有误导，**不是最小值**） |
| ★ `rtt_min` | 本区间内的**最低**往返 —— 判断"这条路最快能多快" |
| `rtts` | 平滑往返（EWMA 1/8）—— **典型延迟** |
| `rttd` | 平均偏差 —— **抖动** |
| `rto` | `rtts + 4·rttd`，并受下限约束 —— **是计时器，不是延迟** |
| ★ `inflight` | **真正在途的帧数**（只数已首发、未确认的帧） |
| ★ `in-flight limit` | 当前生效的在途上限 |
| `swnd` | 对端广告的接收窗口（**信用**，不是速率） |
| `wait_snd` | 应用侧排队帧数（钉满 = 应用被背压） |
| `counter_resend_perMB` | **每交付 1MB 的重传次数**（按交付归一，比 `ratio` 更可信） |
| `rto_floor` | RTO 下限（本端计时器）|
| `counter_resend_waste` | **对端**确认"我的重传里有多少是白费的"比例 ✓（链路上唯一不被本端计数污染的判据）|

#### 2.3.2.2 结论（按发现顺序，含被推翻的假设）

1. **目标链路的重传 99% 是白费的**：`counter_ack_dup`（对端确认"重复帧"）≈ 重传次数 ⇒
   帧其实早就到了，只是**迟到**。所以"丢包"信号在这条链路上分不清"丢"与"迟到"。
2. **`rttm/rtts/rttd` 恒 ≤ RTO**（Karn 规则只统计"从未超时"的帧）⇒
   任何"用 RTT 统计量去抬高 RTO 下限"的做法**永远越不过 RTO**（"用 RTT 统计量抬 RTO"永远无效的代码级原因）。
3. **`swnd` 不是闸门**：它每个 ACK 都被重新授予（= 对端缓冲区大小），夹它**从未生效**。
   实测证据：`inflight 63` 而 `cap 22` —— 上限形同虚设。
4. **那 200ms 是"我们自己撑住的队列"**（最后才被证实）：

```
空载 ping                 4~7 ms
跑 ffrdp 时 ping          217~228 ms     ← 与 rtts 219ms 完全一致
传输一停 ping             4~7 ms         ← 立刻回落
iperf3 TCP 跑时 ping      374~704 ms     ← TCP 用 550~700KB 在途，自残更狠
关系式：RTT = 在途量 ÷ 链路速率
  我们：64 帧 × 1280B = 80.7KB ÷ 365KB/s = 221ms ✓ 与实测 219ms 吻合
  TCP ：550~700KB ÷ ~1000KB/s = 550~700ms ✓ 与 ping 实测吻合
```

⇒ **在途量就是延迟的来源**；`rtt_min = 4ms` 是这条路的地板。（通俗解释见 见 §2.3.2.3）

#### 2.3.2.3 "这 200ms" 到底是什么

全文反复出现的"这 200ms"，指的是**一次往返里多出来的排队时间**。先说数字：

```
空载 ping（没有任何传输）   4 ~ 7 ms     ← 这是这条路"最快能有多快"
跑传输时 ping              217 ~ 228 ms  ← 多出来的 ~215ms 就是"这 200ms"
传输一停 ping 立刻回到       4 ~ 7 ms     ← 队列消失（两次独立测量都如此 ✓）
```

##### 它花在哪里：不是花在路上，是花在排队上

无线电/光纤的**传播时间只有几毫秒**（空载 ping 就是这么来的 ✓）。多出来的 200ms
**全部花在"排队"上**：包已经发出去了，但卡在路径上某个设备（这里是 AP/路由器）的
**发送缓冲区**里，等着被真正送出去。

##### 队列是怎么被排出来的（用实测数算一遍）

```
链路出口的速率（它每秒只能送走这么多）        ≈ 365 KB/s   ← 由链路决定，改不了
我们同时放在路上、还没被确认的数据            = 在途量 = 64 帧 × 1280B ≈ 80 KB
把这 80KB 全部送出去需要的时间                = 80KB ÷ 365KB/s ≈ 221 ms
                                            ↑ 与实测往返 219ms 吻合 ✓
```

一条式子就够：**排队时间 = 积压量 ÷ 出口速率**。
我们**放出去的比出口能消化掉的多**，多出来的部分只能堆在缓冲区里；堆得越多，
每帧的往返就越长。空载时没有积压 ⇒ 4~7ms；开始传输后积压 80KB ⇒ 221ms ✓。

##### 类比（高速收费站）

| 名词 | 对应 |
|---|---|
| 收费站的通行速度 | 链路速率（≈365KB/s）|
| 我们同时在路上的车数 | 在途量（64 帧）|
| 收费站前排队的车 | AP/路由器缓冲区里积压的包 |
| 每辆车通过收费站要花的时间 | 我们观测到的往返（219ms）|

**要缩短它，唯一要做的是"少放一些车同时上路"** ✓ —— 不是修路（路没坏：空载只要 4ms ✓）。

##### 为什么说"是我们自己撑住的"

- 排队时间**正好等于**"我们的在途量 ÷ 链路速率" ✓（不是巧合，是定义 ✓）；
- **传输一停，队列立刻排空**，ping 当秒从 220ms 掉回 4~7ms ✓；
- 换成 iperf3（在途量 550~700KB ✗）测，ping 就涨到 **374~704ms** ✓
  ⇒ **谁把在途量放得多，谁的队列就更长** ✓。

##### 为什么它会拖累别人、也拖累自己

`ping` 是 ICMP，和我们的数据包毫无关系，却被同样延迟了 219ms ✓
⇒ 队列是**共享**的，摆在路径上的同一个位置 ⇒ 我们自己把同一时刻的其他流量
（包括同一连接上的交互流量）一起拖慢了 ✓。

##### 为什么它很难被发现（关键）

```
队列不是在"跑了一会儿之后"才出现的，而是从第一秒就被填满 ✗
⇒ 我们记录到的"最小往返"（rtt_min = 16ms；对照组"好链路"只有 4ms，见 见 §2.3.5 开头）本身就已含这个队列 ✗
⇒ 所有"拿当前往返和历史最小值比较"的算法（延迟梯度那一类）都会得出
  "没有拥塞"的错误结论 —— 它们被这个常驻队列结构性地蒙住了 ✗
⇒ 只有在传输停止的那一刻队列才排空，这时才能看到地板（4~7ms）✓
```

这就是为什么判断"这 200ms 是不是我们的"**不能靠观测，只能靠实验**（见 见 §2.3.3.5 ✓）。

##### 这个现象的标准名字：bufferbloat（缓冲膨胀）

链路设备给的缓冲远大于"链路速率 × 往返时间"：

```
这条路：设备缓冲 ≈ 对端广告的 148 帧 ≈ 185KB
        链路真正需要的 ≈ 5 帧 ≈ 6KB
        ⇒ 相差 30 倍，多出来的缓冲必然被发送方填满 ⇒ 常驻队列 ✗
```

典型表现就是**带宽没变、延迟暴涨** ✓。所以"这 200ms 是不是我的"=
"这 ~215ms 排队，是不是我自己放太多帧造成的" ✓ —— 只有两种答案，且必须用实验区分 ✓。

### 2.3.3 改动清单

一个改动一个提交，各自附仿真/真机证据。

#### 2.3.3.1 ACK 扩展：回传"我的重传有多少是白费的"（可变长 ACK）

- **问题**：发送端无法从自身计数判断"重传是否必要"（它只知道自己重传了几次，不知道对端是否早就有）。
- **做法**：接收端统计"收到的重复数据帧"数，追加 1 字节在 ACK 尾部（`data[8]`，`ret >= 9` 时才发）；
  老对端不发这一字节 ⇒ 发送端读到 0 ⇒ 行为退回原样（**向后兼容** ✓）。
- **理由**：这是链路上**唯一**无法被本端计数污染的证据 —— 来自接收端的事实。
- **协议层细节见 见 §2.1.3**。

#### 2.3.3.2 RTO 下限由"对端重复上报"驱动（`rto_floor`）

- **问题**：往返分布有长尾（迟到帧），固定倍数的 RTO 落在中位数附近 ⇒ 大量伪超时。
- **做法**：以证据窗口为单位统计"重传次数"与"被对端确认白费的次数"；
  白费占比高（≥ `FFRDP_WASTE_HI`）⇒ 抬 `rto_floor`（×5/4，上限 1000ms）；
  白费低 ⇒ 归还下限；并施加相对上限 `max(3×rtts, 100ms)`，让链路变快时下限自动回落。
- **关键教训**：**安静窗口不能触发衰减** —— 在限速链路上"安静"往往正是下限在起作用，
  对它衰减会让环路自我拆台（曾用 v5 犯过这个错）。
- **证据**：目标链路重传 28% → 2.3%（`perMB` 230 → 19），且好链路逐字不变。

#### 2.3.3.3 快重传纪律（`hole_wait`）

- **问题**：对端报的"洞"多数是**乱序**，不是丢包 ⇒ 立刻快重传 = 白费（占重传 65%）。
- **做法**：等待时长 `hole_wait` **由对端重复上报决定**：
  白费多 ⇒ 等 `3×rtt`（≤300ms）；白费少（真修复）⇒ **0**（与原来完全一致）；
  中间 ⇒ `rtt`。
- **理由**：同一个原则 —— **不用有歧义的信号，用接收端的报告**。
- **踩过的坑**：第一版"一律等 1 RTT"在仿真里把 **真修复** 一起延迟了（6 连丢 -78%），
  因为仿真里没有乱序。改成证据驱动后，全部场景与基线逐字相同。
- **顺带修掉**：超时退让由"每帧一次"改为"**每往返一次**"（v1.0.0 的 1.3.3 / 1.4 节问题 4）。

#### 2.3.3.4 在途量闸门（真正的刹车）

- **问题**：唯一的刹车是对端缓冲区大小（148~256 帧），而链路只需要几帧 ⇒ **我们自愿把队列灌满**。
- **做法**：在发送循环里按**在途帧数**（只数已首发未确认的帧）限制首发；
  `FFRDP_INFLIGHT_MAX` 为默认上限；重传不受此限制（修复路径永不被挡）。
- **理由**：`RTT = 在途 ÷ 链路速率`（推导见 见 §2.3.2.3）⇒ 在途量就是延迟的来源；而吞吐由链路限速 ⇒
  **收窄在途量可以降延迟而不损失吞吐**（只要仍高于 BDP）。
- **注意**：默认值 64 是**保证不变**的保守值；真正有用的值由 10.3.5 实验得出。

#### 2.3.3.5 延迟探测：把"这 200ms 是不是我的"变成一次实验

- **动机**（"这 200ms"是什么、为什么测不出来，见 见 §2.3.2.3）：常驻队列会让"与历史最小值比较"永远看到 0
  （最小值本身已含队列）⇒ **任何纯观测方案都是瞎的**，只有实验能回答。
- **做法**（`FFRDP_PROBE_ENABLE`，默认开启）：
  1. 触发：`rtts > FFRDP_PROBE_QUEUE_RATIO × rtt_min`（默认 **3×**；有我们撑住的队列）或白费率高；
     并且**砍半后的上限必须严格低于当前上限**（否则问的是同一个问题），且不越过地板
     `FFRDP_INFLIGHT_MIN = 4` 帧；
  2. 探测：把在途上限**砍一半**，保持 `2×rtt + 500ms`；
  3. 判定：**对端确认速率没掉**（不低于"探测前一秒"与"见过的最好一秒"里的较大者的 85%，
     `rate_best` 每秒衰减 1/4）**或** 重传强度明显降了（探测期间"重传/交付"比探测前低 20% 以上）
     ⇒ 保留该上限（并可继续下探）；
     否则**立即还原**（速率掉了 = 砍过头；重传没降 = 不是我们的队列）；
     ⚠️ 判据里**不再要求"看到 RTT 下降"**：2ms 的差在 20ms 的抖动里读不出来 ⇒ 那条要求等于把判定
     交给抖动，而上面两条都是直接量到的（见 [`notes.md`](notes.md) §26.15）；
  4. 队列消失后慢慢放开（giveback），链路变快时能自动回升 —— 但"队列消失"用的是**绝对判据**
     `rtts − rtt_min < FFRDP_PROBE_RTT_DROP_MS`（2ms ✓），而**不是**触发用的 3× 比值 ✗：
     3× 允许最多 12ms 的队列仍算"没在排队" ⇒ 真机上 giveback 会时开时关（300s 里漏过 7 次 ✗，
     每次都把已证明的 4 抬回 5，见 [`notes.md`](notes.md) 11.6 ✓）⇒
     **触发与归还用两把不同的尺子** ✓；还窗口因此还要**连续健康 `FFRDP_PROBE_GIVEBACK_IDLE_S`（5）秒**，
     步长 `+25%`（`×2` 会让"刚降下来又被抬回去"），且按秒 giveback 与这里共用一个周期预算（`last_giveback`）✓；
  5. 失败后探测间隔翻倍（最多 60s）；
  6. ①-39 **内存视角触发**（`FFRDP_MEMPROBE_ENABLE`）：上限比"这一圈真正在线上"高一倍以上也值得试 ——
     那种情况下砍半不降延迟，但能把我们给自己留的在途预算降下来（要求 `out ≥ FFRDP_MEMPROBE_MIN_OUT`）✓。
- **安全网**：还原逻辑保证"砍错"只损失一次 1.5 秒半窗口 ⇒ 不属于负优化。
- **证据（真机）**：`probes 3 keep 3 revert 0`；`rtts` 215ms → 12~19ms（在途 64→8~16 帧）；
  负载 ping 220ms → 18~27ms；服务端吞吐反而 **+40%**；中途一次链路打嗝（461ms）探测**没有乱砍**。
- **收敛不再需要等退避**（通用做法 ✓）：探测**成功**的下一次不再等 10s，而是
  `2 × rtt + 500ms` 后就再问 ✓ ⇒ 没被测量过的路径也能**几秒内**自己收敛 ✓，
  失败仍翻倍 ⇒ 自我限速 ✓。**不需要为任何路径预先填值** ✓（按环境填值的版本见 见 §2.3.4）。
- **门槛降到 3×（真机 ✓✓）**：两方向都收敛到地板 —— 服务端 `rtts` **217 → 10~19ms**（43× → 3×）、
  客户端 **219 → 17~18ms**（**1×**，即贴地板 ✓）；`keep 5~6` / `revert 1`（那一次被速率守门挡下 ✓）；
  `perMB` 服务端 **1.1**（历史最好）/ 客户端方向 **6.9**；服务端吞吐 **574~650KB/s**（新高）；
  好链路每轮最多多一次探测，且**被还原** ✓（`revert 1`, gap 10→60s ✓）。
- **判据与闸门的修正** —— 三处都是"把实验问对"，不改协议、不改帧：
  1. **保留判据由相对改绝对** ✓：原来是"低于探测前值的 85%"，而**那个"探测前值"取的是 `rttm`（最近一次采样）**
     ✗ ⇒ 同一个实验会凭"碰巧前一个采样是多少"通过或失败 ✗。现在基准与探测中跟踪的都是**同一个平滑量
     `rtts`**，要求**低 ≥2ms** ✓ —— 真机那一步的胜负手正好是 `rtts 18 → 14ms`（4ms ✓）；
     相对判据在低延迟链路上也无法使用（地板 5ms 的 15% 只有 0.75ms，远在抖动之下 ✗）。
  2. **尺寸闸门由"≥8 帧在途"改为"砍半后严格低于当前上限"** ✗✓：`8` 是常量，而上限会被探测自己降到 4~5 ⇒
     **`out` 永远到不了 8 ⇒ 之后再也问不了** ✗。实测到的现场正是：giveback 把已证明的 4 抬到 5，
     然后被这个闸门**永久冻在 5**（`inflight, cap = 5, 5`），而 4 帧下的同一链路只有 14ms，
     比 5 帧少排 **4ms** ✗。
  3. **giveback 加"队列还在就不还"** ✗✓：还回去会把下一次查看推后一整个 `PROBE_GAP_MS` ⇒ 刚赢来的 4 帧
     会在 5 帧上挂十秒，等于把收益交回去一半 ✗。而"队列消失"本来就是"路径变快了"的样子 ⇒ 同一个判据 ✓。
     （4 帧的地板提成具名常量 `FFRDP_INFLIGHT_MIN`，与刹车、触发闸门共用，避免三处各写各的而漂移 ✗。）

#### 2.3.3.6 诊断输出（`ffrdp_dump`，便于后续维护）

**先看这一行**（一眼识别"是不是刚编的二进制"——这个坑踩过三次：跑错 `./test` 而不是新构建 ✗）：

```
build: probe 1, queue ratio 3, inflight default 64, compiled Oct  9 2026 21:54:13
```

**延迟有三个量，别混用**：

| 行 | 含义 |
|---|---|
| `rttm` | **最近一次**采样（名字有误导 ✗）|
| `rtt_min, rtts, rttd` | 本区间**最低**（= 这条路的地板）/ 平滑**典型**值 / 抖动 ✓ |
| `rto` | **计时器，不是延迟** ✗（它被下限抬上去，不代表链路变慢 ✓）|

**闸门与探测**：

| 行 | 含义 |
|---|---|
| `inflight, cap` | 真正在途的帧数 / 当前上限（`kept` = 已被实验证明的值；`probes keep revert too-far giveback`）|
| `in-flight limit` | 生效的在途上限（默认 64 = 优化前行为 ✓）|
| `probe trigger` | 触发输入：白费率（pm）、`rtts/rtt_min`、在途帧数 `out`（要 **> 地板 4**，且**砍半后低于下一行的上限**）|
| `queue test` | **门槛本体**：`rtts / rtt_min`（`>3×` 才做实验；在地板或以下显示 `1x` ✓）|
| `probe rtt ref/best` | 探测前（**典型** `rtts`）vs 探测中最低的**典型**值；**低 ≥2ms 且速率保持**才算赢 ⇒ **"队列是不是我们的"的原始证据** ✓ |
| `confirmed rate` | 对端确认速率（帧/秒）—— **吞吐守门人**（砍过头会让它掉 ✗）|

**发送失败的可观测性**：`counter_send_err` 是**按 dump 区间累计**的 `sendto` 失败数 ✓
（数据帧 / ACK / QUERY / FEC 四条路径都计入 ✓）。⚠️ 别用 `counter_udpsenderr` 判"发送缓冲够不够"✗：
它是**连续失败次数**（下一次成功即清零 ✓），一个"十发一失"的 socket 在采样瞬间几乎总读到 0 ✗。

**乱序上报的诊断（纯诊断，不驱动任何行为 ✓）**：

| 行 | 含义 |
|---|---|
| `counter_recv_ooo` | **接收端**：乱序到达的帧数（它下面有洞）|
| `counter_recv_far` | …其中"距洞 > 23 帧"的（**注意它比掩码本身严一帧** ✗：`dist 24` 其实装得下，见下）|
| `counter_ooo_d1_24` / `d25_64` / `dgt64` | **距洞多远**，三档之和恒等于 `counter_recv_ooo` ✓。`d1_24` = 今天的 24 位掩码够得着（bit = `dist − 1`，`dist 24` 是最后一个 bit）；`d25_64` = 一个扩展字（64 位）够得着；`dgt64` = 一个扩展字也不够 |
| `counter_ooo_d65_128` / `dgt128` | 把 `dgt64` 再细分 ✓：`65..128` = **两个扩展字（128 位）够得着**；`>128` = 两个也不够。两档之和恒等于 `dgt64` ✓ ⇒ **扩展字宽就是由这两档定的** ✓（真机上 `>64` 占 8.1%，所以 64 位不够 ✓）|
| `counter_ooo_64reach` / `128reach` | `(d1_24 + d25_64) / recv_ooo` 与再加 `d65_128` 的版本 —— **改用 64 / 128 位掩码各能表达多少乱序**，这就是"值不值得加宽、加多宽"要看的两个数 |
| `counter_mack_bits_tx` / `_rx` | 本端**发出去**的 mack 位数 / 从对端**收到**的 mack 位数。两端各看一份：**差值 = 报告丢在路上** ✓（谁单独看都分不清"没报"和"报了没到" ✗）；`tx / recv_ooo` 看"报告是否真的在发生" |

三点读法：

- `far − (d25_64 + dgt64)` = **恰好 `dist == 24`** 的样本数 ✓ —— 正好用来自检那两个边界（真机上这两个数都很小 ✓）；
- ⚠️ **先确认这些数是累计还是增量** ✗：它们确实落在 dump 的"可清零区间"内，但**清不清零由调用方决定** ——
  `test.c` 传的是 `ffrdp_dump(ffrdp, 0)` ⇒ **不清零，数字是累计的** ✗。
  所以读日志时：要"这一段"就对相邻两块作差 ✓（或把调用改成传 1 ✓），**绝不能把它们当增量去求和** ✗
  （第一版分析就这么错过一次，结论会完全跑偏）；
- 它们**不让协议做任何不同的事** ✓：17 个仿真场景与改动前的基线**逐字相同** ✓。

**读计数的三个坑**：

- **`counter_resend_ratio` 会被"饿死链路"刷低** ✗，也会被**极低频发送**刷高 ✗（它的分母是**累计首发次数**，
  分母小的时候几次重传就能占很大比例）⇒ 所以现在**把绝对数一起印出来**：
  `counter_resend_ratio: 30.00% (6 / 20)` ✓（= 重传 6 次 / 累计首发 20 次）；
  判断浪费仍一律看 **`counter_resend_perMB`**（按交付归一 ✓）。
  注意它**可以超过 100%**：同一帧被重传多次时，分子（重传次数）会大于分母（首发的帧数）✓；
- `counter_resend_waste` 同样带绝对数 ✓（`100.00% (6 / 6)` ✓ = 对端说 6 次重传全部白费 ✓）；
- `counter_resend_waste` 是**对端**说我们白费的比例 ✓ —— 本端计数回答不了这个问题 ✓
  （它原来寄生在 `rto_floor, waste%` 那一行里，现已独立成行 ✓）。
- 三个比例（`counter_resend_ratio` / `counter_resend_waste` / `counter_resend_perMB`）在**分母为 0**
  时打印 `n/a` ✓，不再拿 `1` 兜底 —— 那会印出一个"像测量值"的假数字 ✗（见 [`notes.md`](notes.md) 10.4）。

**未覆盖 / 残余风险（诚实列出）**：

1. **乱序密集链路**：仿真没有乱序模型。10.3.3 的证据来自真机（乱序 26k 次那一轮）；

2. **极快链路**：小上限会压吞吐；但探测的"速率守门"会**还原**，所以只会损失一次半窗口。

5. **探测时序类改动仿真判不了** ✗：仿真一次只跑 6 秒，短于重查间隔（10 秒）
   ⇒ 仿真里的探测从不发生 ⇒ 任何时序改动都会让它变 ✗（与好坏无关）。
   这类改动只能真机判 ✓；仿真只用来确认**干净链路逐字不变** ✓。

### 2.4.1 派生链：一个旋钮决定两块内存

```
FFRDP_MAX_MSS = (1500 - 8) = 1492                    （ffrdp.c 里的字面量；8 = 4 字节帧头 + 4 字节对齐余量）
  ├─ FFRDP_RECVBUF_SIZE = 128 × MSS                  接收缓冲（**协议可见**：rwnd 由它算并报给对端）
  │                                                  ≈ 186 KiB @1500
  ├─ 应用发送队列容量 = MAX_WAITSND × (MSS + 4)       **派生量** —— v1.1.0 没有独立的队列容量常量
  │                                                  ≈ 374 KiB @256 帧 / 1500
  └─ smss ≤ MSS                                      运行期参数：`ffrdp_init()` 的每帧负载
FFRDP_UDPSBUF_SIZE = FFRDP_UDPRBUF_SIZE = 128 × (MSS + 6)   仅作 socket 选项，占内核内存，不占本进程
```

1500 这个默认值是为了不触发 IP 分片；**嵌入式上它是第一个该动的旋钮** ✓ —— 它一降，
`recv_buff` 与"应用发送队列容量"**会一起降** ✓（"一个旋钮决定两块内存"就是这个意思 ✓）。

### 2.4.2 常量表（v1.1.0）

| 常量 | 默认值 | 作用与约束 |
|---|---|---|
| `FFRDP_MAX_MSS` | `(1500 - 8) = 1492` | 每帧最大负载（**字面量**）；下面几块内存都由它算 |

| `FFRDP_MIN_RTO` / `FFRDP_MAX_RTO` | 16 / 2000 ms | RTO 硬上下限；实际取值还要被 `rtt_tail` 与 `rto_floor` 抬起来（见 §2.3.3.2 / §2.3.3.4）|
| `FFRDP_MIN/DEF/MAX_CWND_SIZE` | 1 / 32 / **64** 帧 | 拥塞窗口（流控上限）。真机 A/B：窗口 64 → 128 时两侧吞吐 ×3，拐点是 128 —— 那是与 `WAITSND` **配对调**的结果 ✓，见 §2.4.5 |
| `FFRDP_INFLIGHT_MAX` / `FFRDP_INFLIGHT_MIN` | **64 / 4** 帧 | 在途量闸门的上限 / 地板（真正的"窗口"）。**必须 ≤ `FFRDP_MAX_WAITSND`**（且 ≤ `MAX_CWND_SIZE`）。目标链路 BDP 只有 1~6 帧（源码注释：链路 ~365 KB/s、idle RTT 5~16 ms）⇒ 64 是"哪条路都不出错"的默认值，由探测下探到合适的值 ✓ |
| `FFRDP_PROBE_ENABLE` | **1（打开）** | 延迟探测：把在途砍半，若 `rtts` 明显下降**且**确认速率不低于历史最好值的 85% ⇒ 保留更小的上限（同吞吐、低延迟）✓。安全网：`rate_best` 参考、按秒 giveback、地板 `FFRDP_INFLIGHT_MIN` ⇒ 见 §2.3.3.5 |
| 探测一族 | `HOLD_MS 500` / `RTT_DROP_MS 2` / `RATE_KEEP_PCT 85` / `QUEUE_RATIO 3` / `WASTE_PM 5` / `GAP_MS 10000` / `GAP_MAX_MS 60000` / `HEALTHY_PCT 1` | 探测的保持时长、判据、回路间隔与 giveback |
| RTO 下限一族 | `RTO_FLOOR_MAX 1000` / `RTO_WIN 128` / `WASTE_MIN 16` / `WASTE_HI 80` / `WASTE_LO 40` | 由"对端重复上报"驱动 `rto_floor`（见 §2.3.3.2 ✓）|

### 2.4.3 应用发送队列容量（派生量）

**它只决定两件事**：能发送的**单条消息**上限（= 容量 − 4，超出者 `ffrdp_send` 直接返回 -1，不会空等），
以及**背压何时出现**（非阻塞调用更早返回 -1，阻塞调用等得更久）。

- **它与帧数闸门 `FFRDP_MAX_WAITSND` 绑死** ✗（容量 = `WAITSND × (MSS+4)` = 374 KiB）：改 `WAITSND` 会
  **同时**改"在途上限"与"这块纯应用侧缓冲" ⇒ "省内存"与"掉吞吐"被捆在一起，那是个**假取舍** ——
  真机 A/B 里 ×3 的那一刀是 `WAITSND` 64→256，而队列容量**从头到尾不需要跟着动** ✓（见 §2.4.6 ✓）。
- **典型值**：374 KiB（默认派生值，≈ 250 帧）。要跑更大的单条消息就按"最大消息 + 4"配。
- **配到极限的代价**（实测，保留）：容量压到 4 条消息（5984 B）时，回环吞吐从 ~300 MB/12s 降到约 180 KB/s ✗，
  但 `seq_gap / crc_err / len_err / partial_err` 全为 0 ✓ ⇒ 正确性不受影响，只是背压来得极早。
- **它不随 `smss` 单独变**：它由 `MAX_WAITSND × (MSS + 4)` 算出 ⇒ 只有 `MSS` 或 `WAITSND` 动了它才动 ✓。

### 2.4.4 两条受理判据（都在 `ffrdp_send` 里）

> **2026-10-16（§26.15）**：应用发送队列已删除 ⇒ `ffrdp_send` 在锁内**直接成帧**，
> 受理判据改成三条（都在循环里判，见 `ffrdp_send`）：① 未发出帧预算 `FFRDP_UNSENT_MAX`；
> ② 在途上限 `wait_snd < FFRDP_MAX_CWND_SIZE`；③ 帧数闸 `need + wait_snd ≤ FFRDP_MAX_WAITSND`。
> 下面这一节描述的是删除之前的形态，保留作为背景。

1. **帧数**：`ceil(len / smss) + wait_snd > FFRDP_MAX_WAITSND` ⇒ 拒绝。
   （v1.1.0 里读的是协议发布的镜像 `pub_wait_snd`；镜像已随队列一起删除，现在直接读锁内的 `wait_snd`。）
2. **字节**：`len + 4 + 队列里现有字节 > 队列容量`（队列容量 = 64 KiB ✓） ⇒ 拒绝或等待（按 `timeout_ms`）。


### 2.4.5 `FFRDP_MAX_WAITSND`（帧数闸门，默认 256）

它**只**管帧数：`ffrdp_send` 的受理判据（`ceil(len/smss) + wait_snd > WAITSND` ⇒ 拒）用它。
（v1.1.0 里它同时乘出应用队列容量，那是个假取舍；2026-10-16 队列删除后这个乘法没了，见 §26.15 ✓。）

内存上它只影响 `send_list` 里的帧节点数（每帧 ≈ `smss + 54` 字节，堆上），而且是"在途量"本身 ——
**在途字节 = 带宽 × RTT（BDP）是物理需求**，不是浪费：要跑满高 BDP 链路就必须留得住这些帧。

**约束（重要）**：必须 `WAITSND ≥ FFRDP_INFLIGHT_MAX`（且 ≥ `FFRDP_MAX_CWND_SIZE`）。比协议的闸门还小的
话就成了更紧的刹车：在途永远填不满窗口，高 BDP 链路上掉速 ✗。真机实测（同一链路、同一晚）：

| `WAITSND` / 窗口 | 客户端 发 / 收 | 服务端 发 / 收 | 服务端被拒 | 判定 |
|---|---|---|---|---|
| 256 / **64** | 2.2~2.8 / 2.9~4.5 MB/s | 2.6~4.8 / 2.1~3.0 | 3369 → **9120** ✗ | 窗口是天花板 ✗ |
| 256 / **128** | **6.2~7.7 / 10.1~11.9** | **10.1~12.0 / 6.3~7.7** | 722 → 1166 | **拐点** ✓ |
| 256 / 256 | 6.3~7.4 / 10.8~12.0 | 10.8~12.1 / 6.3~7.5 | 254 → 318 | 不再涨 ✓ |

⇒ 60 帧 ≈ 77 KiB，在 RTT 10~30 ms 的链路上只能撑 ~2.5~7 MB/s ✗ ⇒ 那不是"省"，是"压"。**回环测不出这一条**
（BDP 只有几 KB ⇒ 64/128/256 四组实测 59.7~64.1 MB/s，没有差别 ✗），别拿回环结论当安全证据。

其它代价：

- **最大单条消息 = `WAITSND × smss`**：帧数判据在循环之前，超了立即返回 -1（不会空等）；
- 应用被拒的次数上升：实测（16 KB 消息、回环、12s）`WAITSND` = 256/64 时 0 次，32 时 24 次，16 时 2911 次
  ⇒ 调用方必须按契约处理 -1（重试），否则就是丢数据；
- 线上无影响：`wait_snd` 是本端量，从不进任何帧 ⇒ 没有互操作风险（与 `recv_buff` → `rwnd` 不同）。

单独说明：接收侧乱序暂存的上限是**另一个**旋钮 `FFRDP_RECV_QUEUE_MAX`（默认 256，超了直接丢），
它不随 `WAITSND` 变 —— 要省那块内存得单独降它，代价是重排链路上丢帧变多、重传变多。

### 2.4.6 内存 vs 吞吐：哪些是真取舍，哪些不是

| 旋钮 | 影响内存 | 影响吞吐 | 性质 |
|---|---|---|---|
| `FFRDP_MAX_MSS`（由字面量 1500 定）| ✓ `recv_buff` 与队列容量都由它派生 | ✓ 每帧 6 字节开销 / MSS 大小 | **真取舍**（小 MSS ⇒ 更多帧、更多 ack）|
| `FFRDP_RECVBUF_SIZE`（≈186 KiB）| ✓ | ✓ **它决定我们广告的 `rwnd`** ⇒ 影响对端发来的速率 | **真取舍**，且要**和对端成对考虑** |
| 应用发送队列容量（374 KiB，= `WAITSND×(MSS+4)`）| ✓ | ✗ 只决定"单条消息上限"与背压时机 | **假取舍** —— 它与 `WAITSND` 绑死，动吞吐的其实是 `WAITSND` ✓ |
| `FFRDP_MAX_WAITSND`（256）| ✓ 帧节点（在途量）| ✓ ✓ **真闸门** | **真取舍**：在途字节 = BDP，物理需求 |
| `MAX_CWND_SIZE` / `INFLIGHT_MAX`（64 / 64）| ✗（受 `WAITSND` 约束）| ✓ ✓ **真闸门** | 与 `WAITSND` 配对改 ✓ |
| `MIN_RTO` / `rtt_tail` | ✗ | ✓ 伪超时与真丢包恢复速度 | 与内存无关 |
| `PROBE_ENABLE` | ✗ | ✓ 延迟（设计意图：不自己造排队）| 与内存无关 |

⇒ 本版默认配置的账：每端应用内存约 **560 KiB**（`recv_buff` 186 KiB + 应用队列 374 KiB ✓），
在目标链路上以重传率 1.1~1.3% 跑出上行 0.30~0.35 MB/s ✓（见 §2.3.5 ✓）。

## 2.5 每端内存账（v1.1.0）

| 项 | 量 | 说明 |
|---|---|---|
| `recv_buff` | `128 × MSS` | 在 `FFRDPCONTEXT` 里（该结构体是 `calloc` 的），≈186 KiB @1500 |
| 应用发送队列 | `MAX_WAITSND × (MSS + 4)` | 同上，**≈374 KiB @256 帧 / 1500**（派生量，见 §2.4.1）|
| 帧节点 | ≈ `smss + 54` 字节/个 | `calloc(1, sizeof(NODE) + 4 + smss + 2)`；同时在途上限 `FFRDP_MAX_WAITSND`，接收侧乱序暂存上限 `FFRDP_RECV_QUEUE_MAX` |
| socket 收发缓冲 | 内核内存 | `SO_SNDBUF/SO_RCVBUF` 的请求值（`FFRDP_UDPSBUF_SIZE` / `FFRDP_UDPRBUF_SIZE`）；MCU 上没有这两行 |

应用内存合计（`recv_buff` + 应用发送队列）随 `FFRDP_MAX_MSS` 的变化 —— **本版两块都由 MSS 派生** ✓
⇒ 降 MSS 会同时降两块 ✓：

| MSS | `recv_buff` | 应用发送队列 | 合计 |
|---|---|---|---|
| 1492 | 186.5 KiB | 374.0 KiB | **≈560 KiB** |
| 1016 | 127.0 KiB | 255.0 KiB | 382 KiB |
| 504 | 63.0 KiB | 127.0 KiB | 190 KiB |
| 248 | 31.0 KiB | 63.0 KiB | 94 KiB |

⇒ 嵌入式（MCU）的调整顺序：① 降 `FFRDP_MAX_MSS`（**一个旋钮同时压两块** ✓）；
② 还要更省，再一起降 `FFRDP_MAX_WAITSND` 与 `FFRDP_RECV_QUEUE_MAX`（它们管帧节点的数量）。
代价：MSS 变小后同样的字节要走更多帧 —— 每帧固定 6 字节开销，且每帧都要一个 ack。

# 第三部分：v1.2.0 —— 传输层重构与协议改进（§3.1 ~ §3.3）

## 3.1 v1.2.0 相对于 v1.1.0 的改动

> 本章给出 v1.2.0 与 v1.1.0 的全部差异 —— **架构改进、传输层（lowlevel）接口约定、
> 随之在协议上做的改进、参数、兼容性与实测读数**。
> 结论先给：**帧格式、ACK 语义未变 ✓**；`ffrdp.h` 的 **API 改了三处** ✗（见 §3.1.6 ✓），两版**可以直接对接** ✓（收益只在两端都升后出现）。

### 3.1.1 总览（一张表看完）

| 类别 | v1.1.0 | **v1.2.0** | 详见 |
|---|---|---|---|
| **驱动方式** | 应用线程里同步发送 | **工作线程 + `timer()` 期限驱动** | §3.1.2 |
| **传输层** | 协议直接使用 socket | **抽象成可替换的 lowlevel 接口**（tx / rx / timer + 一个线程）| §3.1.3 |
| **发送节流** | 天然靠"应用驱动" ✓ | 显式的**在途量闸门**（`INFLIGHT_MAX`）| §3.1.4 |
| **立刻叫醒判据** | 无此路径（应用每写一次就发一次）| 必须用**本圈现数的在途帧数** ✗ | §3.1.4 |

| **参数** | `INFLIGHT_MAX 64` / `MIN 4` / `PROBE 1` | **5 / 4 / 0** | §3.1.5 |

### 3.1.2 架构改进：从"应用驱动"到"工作线程驱动"

| | v1.1.0（同步）| **v1.2.0（异步）** |
|---|---|---|
| 谁决定"什么时候发" | **应用线程**：`ffrdp_send()` 里成帧并 `sendto` ✓ | **工作线程**：应用只入环形队列；发送由传输层线程 + `timer()` 期限驱动 ✓ |
| 应用接口行为 | 队列满时 `ffrdp_send()` 被背压 | 只入队、非阻塞 ✓（背压由队列容量 `APP_TX_SIZE` 决定 ✓）|
| 协议与 socket 的关系 | 协议自己碰 socket | **解耦**：协议只认 lowlevel 接口 ⇒ 传输实现可替换 ✓ |
| 天然节流器 | **有** ✓（写一个走一个 ⇒ 驱动/AP 队列近乎空 ✓）| **无** ✗ ⇒ 必须靠**在途量闸门**补上 ✓ |
| "排队"发生的位置 | 应用侧与 ack 处（协议层可见 ✓）| 可能在**内核 / 驱动 / 后端自己的队列**里（协议层看不见 ✗）|

**改动动机** ✓：让传输实现可替换（UDP / 串口 / 其它），并让协议由传输层驱动而不是由应用循环驱动。
**随之而来的代价** ✗：丢掉了"应用驱动"这个天然节流器 ⇒ 必须有显式闸门（§3.1.4 第 1 条 ✓），
且"帧交出去之后还要排多久"变成协议看不见的事 ⇒ **换传输实现时要重验**（§3.3 ✓）。

### 3.1.3 传输层（lowlevel）接口约定

传输层只提供**三件事 + 一个线程** ✓（`lowlevel.h`）：

| 项 | 约定 |
|---|---|
| `send()` | 交出**一帧**；返回 `0` = 已交给传输层、`-1` = 没收下。**两种结果都表示这帧在传输层已经没了** ⇒ 重传是协议的事 ✓ |
| 回调 `RECV` | 每帧一次；`buf` 只在本次调用内有效（要留就自己拷 ✓）；`msg->addr` 可以原样回送 ✓ |
| 回调 `TIMER` | 到期的活在这里做；回调返回前应当再调一次 `timer()` ✓ |
| `timer(deadline_ms)` | 请求"不晚于该绝对毫秒"回调；`0` = 无期限（睡到有包 ✓）；**可从任意线程调用** ✓ |
| 线程模型 | 传输层**拥有自己的线程** ✓；回调**一次一个、不重入** ✓；一圈可以把就绪的多帧连着回调（上限由后端自定 ✓），在 `RECV` 里调的 `timer()` 会在**同一圈**被交付 ✓ |
| 禁止项 | 回调里**不许阻塞**（那是收包路径 ✓）；`exit()` 不能从回调里调（自 join ✓）|

**接口的两个常量** ✓：`FFRDP_LOWLEVEL_FRAME_MAX`（决定每帧字节数 ⇒ **影响性能** ✓）、
`FFRDP_LOWLEVEL_BUFFER_SIZE`（socket 缓冲的请求值 ⇒ **安全余量，不是旋钮** ✓）—— 详见 §3.3.4 ✓。

**实现 `timer()` 最常踩的四个坑** ✓（括号里是 UDP 后端的做法 ✓）：

| 坑 | 怎么避免 |
|---|---|
| **丢唤醒** | 睡着时"期限被改早"必须能立刻醒来 ✓ —— `select()` 不会因变量变了而返回 ⇒ 自连一个 loopback UDP socket 当闹钟 ✓。顺序必须是"**先置 `asleep = 1` → 再读期限 → 再 `select()`**" ✓ ⇒ 落在缝里的 `timer()` 会看到 `asleep = 1` 并发闹钟 ✓，那个字节已被缓冲 ⇒ 紧接着的 `select()` 立刻返回 ✓ |
| **闹钟没排空** | 醒来要把闹钟 socket **读空** ✓：留一个字节就会让 `select()` 一直报可读 ⇒ 循环全速空转 ✗ |
| **用固定小超时轮询** | 超时应取 `期限 − now`（`≤ 0` 取 0 ✓），**没有期限就无限睡** ✓ —— 轮询既压低精度，又让空闲端点每秒空醒十次 ✗ |
| **时钟与收包的顺序** | 一圈里**先收包、后走时钟** ✓ ⇒ 在 `RECV` 回调里新设的期限**同一圈**就交付 ✓（攒批回 ack 靠这条 ✓）；交付前先把 `deadline` 清 0 ✓ ⇒ 回调里重设的期限不被覆盖 ✓、不设新期限就停表 ✓ |

⚠️ 契约**没有**规定"最坏静默"上限 ✗（即"期限已到、协议有活 ⇒ 最晚 N ms 内必回调"）——
这条属于"换实现时要重验"的清单，见 **§3.3.1** ✓。

### 3.1.4 协议上的改进（引入新架构后）

| # | 改进 | 为什么必须做 | 明细 |
|---|---|---|---|
| 1 | **在途量闸门**（`INFLIGHT_MAX`，当前 5）| 新架构没有"应用驱动"这个天然节流器 ⇒ 不设闸门就会把窗口开多大、就往驱动/AP 里堆多大 ⇒ 自己造出常驻队列（延迟 ✗）| §3.2.1、§3.2.4 |
| 2 | **立刻叫醒判据用本圈现数的在途帧数** | 判据原来读的是**上一圈**刷新过的旧值，而 ack 在 DATA / TIMER 两条不刷新它的路径上处理 ⇒ "ack 刚空出槽位"时判成"发不出去" ⇒ 线程睡到最远的期限（**1 秒** ✗）| §3.2.1 |
| 3 | **兜底：有活时最多睡 4 ms** | 防"该醒没醒"复发（真机曾出现 59 / 114 / 222 ms 的空档 ✗）| §3.2.2 |
| 4 | **收到帧当圈就把 ack 发掉** | 原来是打个标记、等下一圈 TIMER 才发 ⇒ 整整一圈的延迟进了**对端测到的 RTT** ✗ | §3.2.2 |
| 5 | **`ack latency` 仪表**（只打印 ✓）| 让"协议层回 ack 慢不慢"变成可读的数 —— 真机实测 **14~16 µs** ⇒ 证明下行吞吐的瓶颈不在协议层 ✓ | §3.2.4、§3.2.6 |

⇒ 有意思的是：**两版最终落在同一个量级** ✓ —— v1.1.0 的探测在目标链路上把上限 keep 到 **4~7 帧** ✓
（旧二进制自己的 dump 写着 `in-flight limit : 4 frames (default 64; the probe lowers it ...)` ✓），

## 3.2 v1.2.0 的改动明细与依据

> 本节是第三部分的详细依据：**根因 → 改动清单 → 真机结果 → 参数纪律 → 被否掉的路线 → 未解决项**。v1.2.0 与 v1.1.0 的差异一览在上面 **§3.1** ✓。

### 3.2.1 根因：立刻叫醒的判据读的是"上一圈"的在途帧数

`ffrdp_next_due()` 决定"工作线程最晚什么时候必须再跑一圈"。其中最贵的一条判据是：
**现在就有发得出去的东西**（应用队列非空，或有还没首发的帧）**且发得出去**（有信用、在途没到限）
⇒ 立刻叫醒（`due = now`）。

它读的是 `ffrdp->inflight_used`，而那个值**只在 `ffrdp_tick()` 里刷新** ✗。但 ack 并不在 tick 里处理 ——
它在 **DATA 回调**（`ffrdp_apply_acks()`）和 **TIMER 的纯 ack 分支**里处理，这两条路径都**不刷新**它 ✗
⇒ **ack 刚把槽位空出来、正该马上补下一帧的那一刻，判据读到的是旧值** ⇒ 判成"发不出去" ⇒ 不叫醒
⇒ 工作线程一直睡到 `ffrdp_next_due()` 里最远的那条期限（`rate_tick + 1000`，**整整 1 秒**）✗。

讽刺的是：**同一个循环里刚刚已经数好了这个数** —— `n_sent`（在 `ffrdp_next_due()` 自己的遍历里，
只对已首发的帧自增，口径与 tick 里刷新 `inflight_used` 时**完全一致**），它没有被用 ✗。
修复就是把判据换成 `n_sent`（**一行** ✓）。

真机指纹（`y-run1`，`lap period avgmax` = 工作线程两圈之间的间隔）：

| 构建 | lap 平均 | **lap 最大** | 两端吞吐 |
|---|---|---|---|
| 修复前 · 小窗口（8 / 16 帧）| 18~51 ms ✗ | **1002 / 1003 ms** ✗ | 32~48 帧/s ✗ |
| 修复前 · 大窗口（128 帧）| 0 ms | 999 ms ✗ | 正常 ✓（靠自旋掩盖）|
| **修复后** | **2~3 ms** ✓ | **11~18 ms** ✓ | 正常 ✓ |

注意 `cost max 1 ms`（一圈本身只要 1 ms ✓）而**圈间隔最大 1002 ms** ✗ ⇒ 这不是"tick 慢"，
是**根本没被叫醒** ✓。

**为什么这个 bug 之前一直没暴露**：大窗口（`limit = 128`）让旧值判据几乎永远成立 ⇒ 工作线程**自旋**
（实测 64 万圈/run）⇒ 停顿被掩盖 ✗。也就是说：**大窗口一直是这个 bug 的遮羞布** ✓ ——
这正是"新架构必须用大窗口才跑得动"的真实原因 ✗。

#### 3.2.4.2 四条"别这么改"（都有真机证据）

1. **不要把 `FFRDP_MAX_CWND_SIZE` 跟着窗口一起调小** ✗
   它同时是 `ffrdp_send` 受理判据的一条（`wait_snd < MAX_CWND_SIZE` ⇒ 否则拒收）。
   实测把它和窗口一起设成 8 / 16 时：**`inflight` 恒为 0** ✗、两端吞吐塌到 **0.03~0.13 MB/s** ✗。
   **降窗口只改 `INFLIGHT_MAX` / `INFLIGHT_MIN`** ✓。
2. **不要把窗口设大**（16 / 32 / 128）✗
   真机交错实测：窗口 16 / 8 / 6 的吞吐**完全相同**（0.34 / 0.34）✓，而 RTT 分别是 **53 / 25 / 17 ms** ✗
   ⇒ 多出来的窗口**全部变成我们自己撑住的排队**（= §2.3.2.3 的 bufferbloat ✓）。
   窗口大了还会**掐住反方向**：`x-run1` 里新架构当发送方时，把对端（老架构）的上行从 0.34 压到 0.22~0.27、
   把它的 RTT 从 11 ms 抬到 40 ms ✗。
3. **不要在没有复核的情况下打开 `PROBE_ENABLE`** ✗
   它的"砍半 → 验证 → 保留"判据与地板是在**唤醒坏掉**的时期调出来的 ✓；今天唤醒已修，动力学需要重验 ✓。
   打开前至少确认：`lap period avgmax` 最大 **≤ 20 ms** ✓、`probe rtt ref/best` 出现"低 ≥ 2 ms 且速率不掉" ✓、
   `inflight, cap` 不长期钉死 ✓。若打开，`INFLIGHT_MIN` 不要低于 **4** ✗（历史上设成 4 时曾被 keep 成"天花板" ✗）。
4. **不要用 RTO 去治延迟** ✗
   `rto` 是**计时器不是延迟**（§2.3.3.6）✓；抬它只压重传率，代价是真丢包的恢复变慢 ✓。
   延迟只由**在途量**决定：`RTT = 在途 ÷ 链路速率`（§2.3.2.3）✓。

#### 3.2.4.3 症状 → 先看哪个量（这张表能拦下大多数乱改）

| 症状 | 先看（`ffrdp_dump` 里的行）| 常见误判 |
|---|---|---|
| 重传率高 ✗ | `counter_resend_perMB`（按交付归一 ✓）、`counter_resend_waste`（**对端**说白费多少 ✓）、`rtt_tail`、`rto` | 去**加大窗口** ✗（只会让"迟到"更多 ⇒ 白费更多 ✓）|
| 延迟高 ✗ | `inflight, cap`、`rtt_min`、`rtts`、**`lap period avgmax` 的最大值** | 把 `rto` 当延迟看 ✗（它是计时器）|
| 吞吐低 ✗ | `confirmed rate`、`inflight` 是否**钉在 cap**、`rtts` 与 `rtt_min` 的差 | 一上来就加大窗口 ✗（先分辨"窗口不够"✗还是"链路到顶"✓：`waste` 高且 `rtts ≫ rtt_min` ⇒ 是排队 ✓）|
| 只有一个方向慢 ✗ | 两端的 `发 / 收` 四列、`peer wnd raw/clamped` | 只调本端窗口 ✗（可能是对端窗口或对端延迟 ✓）|
| 偶发停顿 / 延迟尖刺 ✗ | **`lap period avgmax` 的最大值** ✓ | 忽略它 ✗（今天那 1002 ms 就是这么找到的 ✓）|

#### 3.2.4.4 改参数的最小验证流程

- **同一 session 内交错跑**（A / B / A / B，两端各夹一个参照版本）✓ —— **不要分块跑** ✗：
  这条链路的可用容量在几分钟内就会变（实测同一晚参照版本自己的下行在 **0.33~0.90 MB/s** 之间摆 ✗）；
- 每条至少 **120 s** ✓；
- 只读四行：`counter_resend_ratio`/`perMB`、`rttm/rtts`、`confirmed rate`、`lap period avgmax`（最大）✓，
  外加 `inflight, cap` ✓（确认闸门真的生效 ✗）；
- 判定：**重传不升 且 延迟不升**才算赢 ✓；吞吐是第三位，用它确认"没掉"即可 ✓。

### 3.2.5 本轮已试并否掉的做法（同一条链路，交替对照）

| 做法 | 实测结果 | 为什么不行 |
|---|---|---|
| 窗口 16 / 8 / 6 | 吞吐**完全相同**（0.34 / 0.34），RTT **53 / 25 / 17 ms** ✗ | 窗口只买延迟 ✓（§3.2.4.2 第 2 条）|
| 每圈首发配额（1 帧 / 2 帧）| 零增益 ✗ | 真机 `lap` 是 **2000~2400 圈/秒** ⇒ "每圈 1 帧" = 每秒 2000+ 帧 ⇒ **等于没限** ✓ |
| 按时间的发送节拍器（两次首发间隔 ≥ 2 ms）| 下行 0.37 → 0.38 ✗，`rttm` 反升到 16 ms ✗ | 收益被自身延迟吃掉 ✓ |
| ack 攒批（1 ms 或 4 帧）| `rttm` **32 ms** ✗、下行不动 ✗ | 真机帧间隔 ~3.8 ms ≫ 1 ms 窗口 ⇒ 每帧照样一个 ack ⇒ **只赔了延迟** ✓ |
| ack 时延仪表（新加）| **14~16 µs** ✓ | 诊断用：证明协议层回 ack 不是瓶颈 ✓ |

### 3.2.6 仍未解决：下行吞吐（已定位在 `sendto` 之后）

- 本版下行 **0.37 MB/s** vs 参照版本 **0.66~0.90** ✗（上行已持平 ✓、延迟持平或更好 ✓、重传好 10 倍 ✓）；
- **协议层无罪**：ack 生成 14~16 µs ✓、`lap` 平均 2~3 ms ✓、窗口只买延迟 ✓、四种节流做法都无效 ✗；
- 因此差距在 **`sendto` 之后**（内核 / 驱动 / 空口）或**我们写包的形态**上 ⇒ 下一步用空口数据区分三种可能：
  AP 给我们的 MCS 更低 ✗ / 空口重传更多 ✗ / 我们的发送形态（突发）不同 ✗；
- 待核实的线索：**快 AP 上连上行也落后 2~3 倍**（参照版本 3000 / 5000 KB/s vs 本版 1500 / 1500 ✗），
  而慢 AP 上行持平（两边都撞到设备上限 ✓）⇒ 我们的发送速率可能被"每圈大致推进一个包"的结构性上限卡住
  （真机 `lap` ≈ 2000~2400 圈/秒 ⇒ 约 1.2 MB/s ✗），与快 AP 上实测的 1.5 MB/s 吻合 ✓。

### 3.2.7 为什么老架构的吞吐反而更好（通俗版）

一句话：**老架构用"应用驱动"白拿了一个节流器** ✓；新架构把发送搬进工作线程，**只有 CPU 更省** ✓（160% vs 180% ✓），
而**吞吐在实测过的三个场景里都还是老架构更好** ✗ —— lo（本机回环）✗、慢 AP（下行 **500** vs **300 KB/s** ✗）、
快 AP（上行/下行 **3000 / 5000** vs **1500 / 1500 KB/s** ✗），数字与口径见 §3.2.3 ✓。

⇒ 所以新架构要追上老架构，**唯一正路是自己补上那个节流器** ✗（不能指望换窗口 ✓，窗口只买延迟 ✓）。

| | 老架构（同步）| 新架构（异步 + 工作线程）|
|---|---|---|
| 谁决定"什么时候发" | **应用线程**：`ffrdp_send()` 当场成帧、当场 `sendto` ✓ | 应用只入环形队列就返回；真正发送在工作线程的 tick 里 ✓ |
| 发送节奏 | **天然被应用和 ack 拉着**（写一个走一个）| 只要窗口允许就往外推 ✗（不受应用节奏约束）|
| 驱动 / AP 缓冲里有什么 | 几乎总是空的 ✓ | **我们放出去、还没被确认的那几帧全在里面** ✗ |
| 我们测到的往返 | ≈ 链路本身（6~7 ms ✓）| 链路 + 自己那几帧的排队（窗口 16/8/6 ⇒ 53 / 25 / 17 ms ✗）|
| 对端等我们 ack 的时间 | 短 ✓（它的数据没排在我们前面）| **长 5~7 ms** ✗（我们的 ack 排在**自己刚推出去的数据**后面）|
| 后果（下行）| `窗口 ÷ RTT` ≈ `7 ÷ 0.007` ≈ **0.84 MB/s** ✓ | `5 ÷ 0.013` ≈ **0.37 MB/s** ✗ |

⇒ **老架构的"极品"并不神秘**：它没有自己堆出来的那条队列，所以它的 `RTT` 一直贴着链路地板，
于是 `窗口 ÷ RTT` 自然就大 ✓。新架构窗口开多大就堆多大 ✗ —— 而"开大窗口"恰好是它以前**被迫**做的事
（唤醒坏掉时不开大就跑不动 ✗，见 §3.2.1）。

⇒ **唤醒修好之后**，窗口第一次变成**纯粹的延迟旋钮** ✓：`INFLIGHT_MAX = 5` 拿到了老架构的"不排队" ✓，
**延迟与重传都追平或更好** ✓；**但吞吐没有跟着回来** ✗ —— 慢 AP 下行差 ~1.7 倍 ✗、快 AP 差 2~3 倍 ✗、
lo 也没赢 ✗（数字见 §3.2.3 ✓）。已定位的那部分在 **`sendto` 之后**（§3.2.6 ✓）；未定位的部分如实留在这里 ✓。

## 3.3 换 lowlevel（传输实现）时要重验什么

> 传输层是可替换的：它只提供 **tx / rx / timer 三件事 + 一个线程**（`lowlevel.h`）。
> 但"**协议算期限、外部循环负责叫醒**"这个结构，决定了有几件事**换了实现就必须重新验证**。
> 本节把它们列全，并给出**判定用的读数**（这些读数就是 §3.2 那一轮破案用的那几列 ✓）。

### 3.3.1 契约（`lowlevel.h` 已写明）+ **需要补的一条**

**已经写明** ✓：

- 拥有自己的线程；回调**不重入**、一次一个 ✓；
- 一圈**可以把当前就绪的多帧连着回调**（上限由后端自定）✓；在 RECV 回调里调 `timer()`，会在**同一圈**被交付 ✓；
- `timer(deadline_ms)` 可用**任意线程**调用、**不晚于**该绝对毫秒回调；`0` = 无期限（睡到有包为止）✓；
- `send()` 的返回值要**如实汇报**：`0` = 已交给传输层，`-1` = 这一帧没收下；**两者都意味着这帧在传输层已经没了** ⇒ 重传是协议的事 ✓；
- 回调里**不许阻塞**（那是收包路径 ✓）；`exit()` 不能从回调里调（自 join ✓）。

**需要补的一条** ✗（§3.2.1 那个 bug 就藏在这里）：

> **契约没有给出"最坏静默"的上限。** 应补一句：
> *当协议请求的期限已到、且协议仍有未确认帧或应用队列非空时，传输层必须在下一次回调里把 TIMER 交给协议，
> 不得晚于 `deadline + X ms`。做不到的后端要显式写出自己的边界。*

理由（真机）：一个判据读了旧值，就让工作线程**静默 1002 ms** ✗（`lap period avgmax`），
而契约里**没有任何上限** ⇒ 这在契约上是"合法"的 ✗ ⇒ 只能靠人肉推理去找 ✗。

### 3.3.2 换了 lowlevel 必须重验的三件事

| # | 要重验什么 | 为什么与实现绑定 | 判定读数（`ffrdp_dump`）|
|---|---|---|---|
| 1 | **谁唤醒谁 / 最坏静默** | 协议只"给期限"，真正的叫醒由传输层的循环负责 | `lap period avgmax` 的**最大值**：有活时应 **≤ 20 ms** ✓（§3.2.1 的 1002 ms ✗ 就是这一列异常）|
| 2 | **帧交出去之后还要排队多久** | 帧离开协议后可能先躺在**内核 / 驱动 / 后端自己的队列**里（UDP 是 socket 缓冲；别的后端可能完全没这一段 ✗ 但也可能有别的）| `rtts − rtt_min`：**≤ 2~3 ms** ✓ 说明没在排；`confirmed rate ≈ 窗口 ÷ rtts` ✓ 说明"窗口就是闸门" |
| 3 | **ack 什么时候真的出去** | ack 与数据共用同一发送路径时，它会排在数据后面 | 对端看到的 `rttm`（**同 session 交替**与参照版本比 ✓）；本端 `ack latency` 只覆盖到"`sendto` 返回"为止 ✓ |

**本版在目标链路上已达的目标读数** ✓：`lap` 最大 **11~18 ms**、`ack latency` **14~16 µs**、
`inflight, cap` 钉在窗口且 `confirmed rate ≈ 窗口 ÷ rtts` ✓。

### 3.3.3 验收清单（换完跑一轮就够）

1. **同一 session 内与参照实现交替跑**（A / B / A / B，两端各夹一个 ✓）—— 不要分块 ✗（链路容量几分钟内就会变 ✓）；
2. 每条 ≥ **120 s** ✓；
3. 只看四行：`lap period avgmax`（最大）✓、`ack latency` ✓、`inflight, cap` ✓、`confirmed rate` ✓，
   外加 `counter_resend_ratio` / `counter_resend_perMB` ✓ 与 `rttm/rtts` ✓；
4. **判据**：① `lap` 最大 **≤ 20 ms** ✓；② `ack latency` 仍是**几十微秒** ✓；
   ③ `inflight` 钉在 `cap` 且 `confirmed rate ≈ 窗口 ÷ rtts`（或能判定"链路已到顶"✓）；
   ④ 重传与延迟**不劣于**参照 ✓。

### 3.3.4 lowlevel 里的两个常量会不会影响性能（最常被问）

| 常量 | 影响性能吗 | 机制 / 边界 |
|---|---|---|
| `FFRDP_LOWLEVEL_FRAME_MAX`（默认 1500）| **会，而且是双向的** ✓ | 它派生 `FFRDP_MAX_MSS = (FRAME_MAX − 6) & ~3` ⇒ 决定**每帧字节数** ⇒ 决定"同样的字节要走多少帧、发多少个 ack、上多少个包"。<br>**调小** ✗：每帧固定 6 字节开销占比上升（1492 时 0.4% ✓、504 时 1.2% ✓），更贵的是**每个包的固定空口开销**（前导 / 回退 / 帧间隙）⇒ 吞吐掉 ✗；本链路又是 **1 帧 1 个 ack** ⇒ ack 包数成比例变多 ✗。<br>**调到 > 1500** ✗：加上 UDP/IP 头就超以太长 ⇒ **IP 分片** —— 分片在 WiFi 上代价很大 ✗（它选 1500 就是为了躲开分片 ✓）。<br>对 **MCU / 串口** 这类后端，它**必须等于后端一次能收下的长度** ✓：接口规定超出即**静默截断** ✗。<br>⇒ **能大就大**（不超后端上限、不触发分片 ✓）；小是**拿吞吐换内存** ✓。|
| `FFRDP_LOWLEVEL_BUFFER_SIZE`（默认 `128 × (FRAME_MAX + 6)` ≈ 188 KiB）| **基本不会** ✓ —— 它是**安全余量，不是旋钮** | 它只是 `SO_SNDBUF / SO_RCVBUF` 的**请求值**（内核内存，不是进程内存 ✓；Linux 会翻倍并受 `wmem_max / rmem_max` 夹 ✓）。<br>**只要不触发** `sendto` 的 `EWOULDBLOCK`、接收侧也不丢包，它的大小对吞吐/延迟**没有可测影响** ✓ —— 本机限速中继复现时的实测：内核发送队列**从未超过 64 KB**、`counter_send_err = 0` ✓；真机同向证据是 `counter_send_err` 一路为 0 ✓ ⇒ 那 188 KiB 从没被填满 ✓。<br>**调太小** ✗：`sendto` 失败 ⇒ 帧被"内核没收下"打回（`counter_cwnd_sfail` ⇒ 拥塞窗口被打回 ✗），接收侧还会**静默丢包** ✗ ⇒ 重传上升 ✗。<br>**调太大** ✗：多出来的部分会变成协议**看不见的队列**（延迟 ✗ —— 就是 §2.3.2.3 的 bufferbloat，只不过藏在 socket 里 ✓）；好在这条路瓶颈在空口、协议自己的在途闸门先到顶，所以今天没踩到 ✓。<br>⇒ **按"在途量 + 一点余量"给即可** ✓。|

### 3.3.5 建议：给 lowlevel 加一个"契约桩测试"

把协议换成一个**记账桩** ✓（不跑真协议）：记录 `timer()` 被请求的**期限序列** ✓、记录每次回调**实际发生的时刻** ✓，然后断言三条：

1. 无"**超期静默 > X ms**" ✓（即 §3.3.1 要补的那条契约 ✓）；
2. RECV **不重不漏**，且 `msg->addr` 能原样回送 ✓；
3. `send()` 的 `0 / -1` **被如实汇报**（不许吞 ✓）。

⇒ 这类 bug 从此是**单测**（秒级 ✓），而不是"真机跑一天才发现" ✗。
（`tools/sim` 测的是"协议在假链路上"✓，两者互补 ✓。）

### 3.3.6 一页清单（换 lowlevel 时照着走）

| 步骤 | 做什么 | 通过条件 |
|---|---|---|
| 1 | 对照 §3.3.1 契约，**补上"最坏静默上限"** ✗ | 契约里有一句明确的 ms 上限 ✓ |
| 2 | 跑 §3.3.5 的契约桩测试 | 三条断言全过 ✓ |
| 3 | 真机与参照实现**交错**跑（§3.3.3）| `lap` ≤ 20 ms、`ack latency` 几十微秒、`inflight` 钉住 ✓ |
| 4 | 检查 §3.3.4 的两个常量是否按后端能力设对 | 不超后端上限、不触发分片、不出现 `sendto` 失败 ✗ |
| 5 | 与参照版本比 `rttm/rtts`、`resend`、`confirmed rate` | 不劣于参照 ✓ |

### 3.3.7 为什么这些参数不该跟着 lowlevel 一起调

**参数只管链路，不管传输实现** ✓：

- **物理参数**（在途上限 / BDP、MSS 权衡、RTO 尾部）随**链路**变 ⇒ 交给自适应（延迟探测，§2.3.3.5 ✓）；
- **实现参数**（唤醒期限、批量大小、ack 何时发）随 **lowlevel** 变 ⇒ 固化成常量 + 契约 ✓，
  换实现时只重验 §3.3.2 那三条 ✓。

⇒ 换 lowlevel **不会**改变"窗口该等于 BDP"这个目标 ✓；但它可能改变"帧交出去之后还要等多久" ✗
⇒ 所以 §3.3.2 第 2、3 条必须重验 ✓（就是验收里的第 ③ 条 ✓）。
