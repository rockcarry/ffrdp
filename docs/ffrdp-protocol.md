# ffrdp 协议说明（v1.0.0 / v1.1.0）

本文是 ffrdp 的**协议说明**：帧格式、通信流程、mack/FEC 语义，以及两个协议版本之间的差异。

- **第一部分（v1.0.0）**：帧格式与基本协议 —— 提交 `55ead4a` 及之前的行为。
- **第二部分（v1.1.0）**：协议**逻辑**优化 —— `55ead4a` 之后（`58167b3` 起）到现在的全部改动。
  **帧格式未变**，只新增了一个可选字节（见第 8 节），两版可以直接对接。

配套文档：根目录 [`readme.md`](../readme.md)（概述/编译/测试/目录）、
[`notes.md`](notes.md)（逐次改动的调试与上机记录）、[`sim-test.md`](sim-test.md)（差分仿真工具用法）。

**怎么确认手上跑的是哪一版**：dump 第一行有
`build : probe 1, queue ratio 3, inflight default 64, compiled ...` 的是 v1.1.0；
v1.0.0 没有这一行 ✓（这个自证行是踩过三次"跑错二进制"之后加的）。

# 第一部分：v1.0.0 —— 帧格式与基本协议

## 1. 帧格式

### 1.1 帧头（4 字节，所有帧统一）

```
byte 0      : 帧类型 type
byte 1 ~ 3  : 帧序号 seq（24 bit，小端）
```

- 访问宏：`GET_FRAME_SEQ(f) = *(uint32_t*)(f)->data >> 8`，
  `SET_FRAME_SEQ(f, seq)` 保留 byte 0 的 type，只写高 24 位 ⇒ **类型与序号共用一个 4 字节头**。
- `seq` 为 24 bit ⇒ 回绕周期 2^24 帧，序号比较一律用"距离"（`seq_distance`）而不是大小。

### 1.2 数据帧

```
data_full  frame: 0x00 seq0 seq1 seq2 data ...              ← 装满 MSS 的数据帧
data_short frame: 0x01 seq0 seq1 seq2 data ...              ← 未装满就发出的数据帧
```

- **两种数据帧都不带 FEC 尾部的 2 字节**，载荷长度 = 帧长 − 4。
- `data_short` 的产生：应用送来的数据没填满一个 MSS 时，帧会先攒着；
  等 `FFRDP_FLUSH_TIMEOUT`（500ms）超时、或应用显式 `ffrdp_flush()` 时，
  以 `SHORT` 类型发出（避免小包被无限期攒住）。
- 接收端用 `FULL` 帧的长度学习对端 MSS（`rmss = 帧长 − 4`），
  用 `SHORT` 帧仅计数 —— 两者都**不进入接收数据流**（它们是用来测量与维持链路的）。

### 1.3 FEC 帧

```
data_fecN frame: 0xN seq0 seq1 seq2 data ... fec_seq0 fec_seq1     (N = 2 ~ 32)
```

- 帧类型值**就是**冗余度 N（每 N 个数据帧附 1 个 FEC 帧）；
  `N = 2` 时同时是 `FEC2`（类型 2），最大 `32`（`FEC32`，类型 0x20）。
- 载荷长度 = 帧长 − 4 − 2（末 2 字节是 16 bit 的 `fec_seq`）。
- 详见第 5 节。

### 1.4 ACK 帧

```
ack frame: 0x21 una0 una1 una2 mack0 mack1 mack2 rwnd [dups]
```

| 字节 | 内容 |
|---|---|
| `[0]` | 类型 `0x21` |
| `[1..3]` | `una`（24 bit）：**第一个还缺的帧号**（该号之前全部已收到）|
| `[4..6]` | `mack`（24 bit）：乱序到达位图，见第 2 节 |
| `[7]` | `rwnd`（8 bit）：本端接收缓冲还能装多少帧（0~255）|
| `[8]` | **v1.1.0 新增，可选**：自上一个 ACK 以来收到的重复帧数（`dups`），见 8.3 |

- 基本长度 **8 字节**；只有"有内容可报"时才发第 9 字节。
- `rwnd = (接收缓冲剩余字节) / rmss`，上限 255。

### 1.5 QUERY 帧

```
query frame: 0x22                      ← 只有 1 个字节
```

- 发送端在**没有数据要发**、且距上次询问超过 `FFRDP_QUERY_CYCLE`（500ms）时发出；
- 对端收到 QUERY 会**立刻回一个 ACK**（即"非延迟 ACK"的另一面：确认不靠定时器攒）。
- 用途：让发送端在空闲时也能持续获得对端窗口与 `una` 信息。

### 1.6 帧类型取值

| 取值 | 帧 |
|---|---|
| `0x00` | `data_full` |
| `0x01` | `data_short` |
| `0x02 ~ 0x20` | `data_fecN`（N = 2~32，类型值 = N）|
| `0x21` | `ack` |
| `0x22` | `query` |

⇒ **数据帧占 `0x00~0x20`，控制帧从 `0x21` 起**。

## 2. mack 语义（怎么表达"缺哪一帧"）

`mack` 是 24 bit 位图，`bit i`（i = 0..23）对应帧号 **`una + 1 + i`**：

```
una  = 16, mack = 0x000003
  ⇒ bit0 = 1 ⇒ 帧 17 已收到
  ⇒ bit1 = 1 ⇒ 帧 18 已收到
  ⇒ 更远的位为 0 ⇒ 19 及以后尚未收到
  ⇒ 帧 16 尚未收到（una 就是"第一个还缺的帧"，不在位图里）
```

- 发送端据此**只重传确实缺失的帧**（选择重传），而不是"从 una 开始整段重发"。
- 位图只有 24 位 ⇒ 只能报出 `una` 之后 24 帧以内的乱序；
  **更远的乱序报不回去**（这是 v1.1.0 明确记录的一条局限，见 10.7）。
- `una + mack` 同时支撑**快速重传**：位图里出现"洞"（某位为 0 而更高位为 1）即知该帧可能丢失。

## 3. 通信流程

### 3.1 发送

- 应用数据被切进帧、入发送链表，首发的帧消耗**对端信用**（`swnd`，见 3.4）；
- 首发时打 `FLAG_FIRST_SEND` 标记；此后该帧的"是否已首发"决定它算不算"在途"。

### 3.2 接收与确认

- 收到数据帧 ⇒ 插入**按序号排序的接收链表**（重复帧丢弃并计数）；
- 连续可交付的部分搬进应用接收缓冲，`recv_seq` 前移；
- 只要收到数据或 QUERY（`got_data || got_query`）就**立刻回 ACK** ⇒ 非延迟 ACK。

### 3.3 重传（两种）

| 方式 | 触发 | 行为 |
|---|---|---|
| 超时重传 | `now > tick_timeout` | 重发该帧，并触发拥塞控制事件 `CEVENT_ACK_TIMEOUT` |
| 快速重传 | ACK 的 mack 报出"洞" | 打 `FLAG_FAST_RESEND`，在下一次 `ffrdp_update()` 里立即重发 |

- v1.0.0 的快速重传是**立刻**执行的（v1.1.0 加了等待纪律，见 9/10.3.3）。

### 3.4 流控与窗口（三个不要混用的量）

| 量 | 含义 | 谁决定 |
|---|---|---|
| `rwnd` | 对端**接收缓冲**还剩多少帧（经 ACK 传回）| 接收端 |
| `swnd` | 对端授予的**信用**，每个 ACK **重新授予**一次 | 接收端（随 ACK 更新）|
| `wait_snd` | 应用侧排队帧数（`FFRDP_MAX_WAITSND = 256`）| 本端 |

- `ffrdp_send()` 在发送队列满时返回失败（应用被背压）；
- **`swnd` 是缓冲区大小，不是链路能跑多少** —— 这条认识是 v1.1.0 的起点（见 10.2）。

## 4. RTT / RTO 计算（v1.0.0）

**测量**：

```
rttm = 当前时间 - 报文发送时间
```

关键限制：**不能对重传报文测量** `rttm` —— 收到 ACK 时无法判断它确认的是原始报文还是重传报文
（Karn 规则）。

**初始化 / 迭代**（EWMA）：

```
rtts = rttm;                                  rttd = rttm / 2;
rtts = (1 - 1/8) * rtts + (1/8) * rttm;       rttd = (1 - 1/4) * rttd + (1/4) * |rttm - rtts|;
```

**RTO**：

```
正常：  rto = rtts + 4 * rttd;
超时：  rto = 1.5 * rto;                 ← v1.0.0：每个超时帧各退让一次
      rto = max(rto, FFRDP_MIN_RTO);     ← v1.0.0 为 20 ms
      rto = min(rto, FFRDP_MAX_RTO);     ← 2000 ms
```

两个重要推论（后面反复用到）：

1. **`rtts` 恒 ≤ `rto`** —— 因为 Karn 规则只统计"从未超时"的帧
   ⇒ 想用 RTT 统计量把 RTO 抬上去是**无效**的（v1.1.0 的 step20 空转就是这个原因）；
2. v1.0.0 的超时退让是"**每帧一次**"：同一轮里多个帧同时超时，
   `rto` 会被连续乘 1.5 直到上限（v1.1.0 改为**每往返一次**，见 10.3）。

## 5. FEC（前向纠错）

- **异或方式**：发送端把连续 N 个数据帧逐字节异或，得到 1 个 FEC 帧；
- 只对 **`data_full`（满 MTU 长度）** 的帧做（长度相同才能异或）；
- `data frame` 的**最后 2 字节**用作 FEC 的 `fec_seq`（16 bit）；
- 冗余度 N 由**帧类型**携带（`data_fecN`，N = 2..32）；默认 0（不启用）。
  发送端每 N 帧发一个 FEC 帧，接收端用同一分组内的帧做异或恢复丢失的那一帧。

**实测结论：默认关闭。** 目标链路真丢包仅 ~0.2%，而 FEC **只救"丢"、不救"迟到"**；
5 倍空口换来的是更多超时（实测重传率反而升到 7.9%）⇒ 关掉是净收益。

## 6. v1.0.0 参数表

| 常量 | 值 | 含义 |
|---|---|---|
| `FFRDP_MAX_MSS` | `1500 - 8` = 1492 | 4 字节帧头 + 2 字节 FEC seq（需 4 字节对齐）|
| `FFRDP_MIN_RTO` | 20 ms | RTO 下限（v1.1.0 改为 16）|
| `FFRDP_MAX_RTO` | 2000 ms | RTO 上限 |
| `FFRDP_MAX_WAITSND` | 256 帧 | 应用侧发送队列上限 |
| `FFRDP_QUERY_CYCLE` | 500 ms | 空闲时发 QUERY 的周期 |
| `FFRDP_FLUSH_TIMEOUT` | 500 ms | 未填满的帧最多等多久（之后按 SHORT 发出）|
| `FFRDP_DEAD_TIMEOUT` | 5000 ms | 判定对端失联的时间 |
| `FFRDP_MIN/DEF/MAX_CWND_SIZE` | 1 / 32 / 64 帧 | 拥塞窗口（本端发送侧面）|
| `FFRDP_RECVBUF_SIZE` | 128 帧 × MSS ≈ 186KB | 接收缓冲 ⇒ 决定了 `rwnd` 的上限（255 帧夹一下）|

## 7. v1.0.0 的已知问题（v1.1.0 的出发点）

1. **重传几乎全是白费的**：对端确认"重复帧"的数量 ≈ 本端重传次数 ⇒
   帧其实早就到了，只是**迟到** ⇒ "丢包"这个信号分不清"丢"与"迟到"；
2. **RTO 落在延迟分布中位数附近** ⇒ 长尾（迟到帧）引发大量伪超时；
3. **唯一的刹车是对端缓冲区大小**（`rwnd/swnd` 有 148~256 帧），而链路只需要几帧 ⇒
   发送端会**自愿把路径上的队列灌满**，形成约 200ms 的常驻排队延迟
   （`ping` 可见：跑传输时 217~228ms，传输一停立刻回到 4~7ms）；
4. 超时退让"每帧一次" ⇒ 突发超时会把 RTO 连乘到上限。

⇒ 第二部分逐个说明 v1.1.0 怎么处理它们。

# 第二部分：v1.1.0 —— 协议逻辑优化

## 8. 先说结论：帧格式不变

### 8.1 逐项对比（v1.0.0 → v1.1.0）

| 项 | v1.0.0 | v1.1.0 | 是否变化 |
|---|---|---|---|
| 帧头 | 4 字节：type + 24 bit seq | 完全一致 | **未变** ✓ |
| 帧类型取值 | `0x00/0x01/0x02~0x20/0x21/0x22` | 完全一致（**无新帧类型**）| **未变** ✓ |
| 数据帧（full/short）| 4 + 载荷 | 完全一致 | **未变** ✓ |
| FEC 帧 | 类型 = N(2~32)，末 2 字节 `fec_seq` | 完全一致 | **未变** ✓ |
| ACK 帧 | 8 字节：`0x21 + una(24) + mack(24) + rwnd(8)` | **前 8 字节逐字节相同**；尾部**可选**第 9 字节 `dups` | **兼容扩展** ✓ |
| QUERY 帧 | 1 字节 `0x22` | 完全一致 | **未变** ✓ |
| `seq` / `una` / `mack` 位宽 | 24 / 24 / 24 bit | 完全一致 | **未变** ✓ |
| `rwnd` 位宽 | 8 bit | 完全一致 | **未变** ✓ |
| 对外 API（`ffrdp.h`）| 8 个函数 | **逐字相同** | **未变** ✓ |

代码级证据（`git show 55ead4a:ffrdp.c` vs 当前 `ffrdp.c`）：
`SET_FRAME_SEQ` / `GET_FRAME_SEQ` 宏、帧类型枚举、帧分配与长度计算
（`4 + size + (type <= SHORT ? 0 : 2)`）、FEC 异或与 `fec_seq` 处理、ACK 前 8 字节的构造
（`*(uint32_t*)(data+0) = (ACK << 0) | (una << 8)`、`*(uint32_t*)(data+4) = mack | (rwnd << 24)`）
**全部逐字相同** ✓。

### 8.2 为什么是"兼容扩展"而不是"新版本帧"

`dups` 放在 ACK 尾部，两个方向都安全：

| 方向 | 行为 |
|---|---|
| **新发送端 ← 老接收端** | 老对端只发 8 字节 ⇒ 解析时 `ret >= 9` 不成立 ⇒ `dups` 读到 0 ⇒ **RTO 下限永不移动，行为退回 v1.0.0** ✓ |
| **老发送端 ← 新接收端** | 老对端解析 ACK 只读前 8 字节（不校验长度）⇒ **多出来的第 9 字节被忽略** ✓ |
| **新 ↔ 新** | 只有"确实有重复帧"时才多花这 1 字节；链路干净时 ACK 长度与 v1.0.0 **完全相同** ✓ |

⇒ 因此 v1.1.0 的改动**可以在两端不同时升级的情况下上线**（收益只在两端都升后出现）。

### 8.3 唯一新增的线上字段：`dups`

| 项 | 说明 |
|---|---|
| 位置 | ACK 帧第 9 字节（下标 8）|
| 含义 | 自上一个 ACK 以来，接收端收到**它早就有的**重复帧个数（夹到 255）|
| 发送条件 | `dup_seen != 0` 才发（否则 ACK 保持 8 字节）|
| 用途 | 发送端据此算 `waste = 对端重复上报 / 本端重传`，驱动 RTO 下限与快重传纪律 |
| 为什么必须来自对端 | 本端的重传计数器只知道"我重传了几次"，不知道"对端是不是早就有" ⇒ 这是链路上**唯一**不被本端计数污染的证据 |

## 9. v1.1.0 规格摘要

v1.1.0 在**协议逻辑**上有四处改动，全部作用于发送端的内部决策，**不改变帧的格式**：

| # | 机制 | 触发 | 动作 | 参数（默认）| 详见 |
|---|---|---|---|---|---|
| 1 | **RTO 下限** `rto_floor` | 证据窗口（128 次重传 / 约 1 秒）结束时 | 白费多 ⇒ 抬下限；白费少 ⇒ 归还；再施加相对上限 `max(3×rtts, 100ms)` | `WASTE_HI/LO = 80/40%`、上限 1000ms | 10.3.2 |
| 2 | **快重传纪律** `hole_wait` | ACK 报出"洞" | 白费多 ⇒ 等 `3×rtt`（≤300ms）再重传；白费少 ⇒ **立刻**（= v1.0.0 行为）| 同上 | 10.3.3 |
| 3 | **在途量闸门** | 每次首发 | 限制"已首发未确认"的帧数；**重传不受限** | `FFRDP_INFLIGHT_MAX = 64`（保守默认）| 10.3.4 |
| 4 | **延迟探测** | `rtts > 3 × rtt_min` 且 ≥8 帧在途 | 把在途上限砍一半，保持 `2×rtt + 500ms`；延迟掉了且确认速率没掉 ⇒ 保留，否则立刻还原 | `QUEUE_RATIO = 3`、`85%/85%` | 10.3.5 |

另外两处**非协议**改动（v1.1.0 一并做了）：

- **超时退让改为"每往返一次"**（v1.0.0 是每帧一次 ⇒ 突发超时会连乘到上限）；
- **诊断输出**（`ffrdp_dump`）补上 `build`/`rtt_min`/`inflight`/`cap`/`probe` 等行，便于维护与自证版本。

以下第 10 节给出这些改动的**依据、证据与被否掉的路线**。

## 10. 依据与证据

### 10.1 目标与优先级

项目要求：**低延迟** + **弱网下带宽稳定**。据此确定取舍顺序（项目方拍板）：

**① 优先降低重传率 → ② 然后保证低延迟 → ③ 然后保吞吐量**

可量化判据：

| 优先级 | 判据 | 对设计的要求 |
|---|---|---|
| ① 重传率 | 客户端 `counter_resend_ratio`：38.7% → **< 5%** | 允许为此适度延长 RTO / 牺牲修复延迟 |
| ② 低延迟 | 平均延迟不恶化；RTO 取"能压住重传率的最小值" | 不接受"用秒级 RTO 换重传率"；需要快修复路径 |
| ③ 吞吐量 | 有效载荷吞吐不下降 | 不作否决项，但不能明显掉 |

### 10.2 诊断：问题真正的成因

#### 10.2.1 观测手段

`ffrdp_dump()` 输出的关键字段（本轮新增的用 ★ 标注）：

| 字段 | 含义 |
|---|---|
| `rttm` | **最近一次**往返采样（名字有误导，**不是最小值**） |
| ★ `rtt_min` | 本区间内的**最低**往返 —— 判断"这条路最快能多快" |
| `rtts` | 平滑往返（EWMA 1/8）—— **典型延迟** |
| `rttd` | 平均偏差 —— **抖动** |
| `rto` | `rtts + 4·rttd`，并受下限约束 —— **是计时器，不是延迟** |
| ★ `inflight` | **真正在途的帧数**（只数已首发、未确认的帧） |
| ★ `in-flight limit` | 当前生效的在途上限 |
| `swnd` | 对端广告的接收窗口（**信用**，不是速率） |
| `wait_snd` | 应用侧排队帧数（钉满 = 应用被背压） |
| `counter_resend_perMB` | **每交付 1MB 的重传次数**（按交付归一，比 `ratio` 更可信） |
| `rto_floor` | RTO 下限（本端计时器）|
| `counter_resend_waste` | **对端**确认"我的重传里有多少是白费的"比例 ✓（链路上唯一不被本端计数污染的判据）|

#### 10.2.2 结论（按发现顺序，含被推翻的假设）

1. **目标链路的重传 99% 是白费的**：`counter_ack_dup`（对端确认"重复帧"）≈ 重传次数 ⇒
   帧其实早就到了，只是**迟到**。所以"丢包"信号在这条链路上分不清"丢"与"迟到"。
2. **`rttm/rtts/rttd` 恒 ≤ RTO**（Karn 规则只统计"从未超时"的帧）⇒
   任何"用 RTT 统计量去抬高 RTO 下限"的做法**永远越不过 RTO**（step20 空转的代码级原因）。
3. **`swnd` 不是闸门**：它每个 ACK 都被重新授予（= 对端缓冲区大小），夹它**从未生效**。
   实测证据：`inflight 63` 而 `cap 22` —— 上限形同虚设。
4. **那 200ms 是"我们自己撑住的队列"**（最后才被证实）：

```
空载 ping                 4~7 ms
跑 ffrdp 时 ping          217~228 ms     ← 与 rtts 219ms 完全一致
传输一停 ping             4~7 ms         ← 立刻回落
iperf3 TCP 跑时 ping      374~704 ms     ← TCP 用 550~700KB 在途，自残更狠
关系式：RTT = 在途量 ÷ 链路速率
  我们：64 帧 × 1280B = 80.7KB ÷ 365KB/s = 221ms ✓ 与实测 219ms 吻合
  TCP ：550~700KB ÷ ~1000KB/s = 550~700ms ✓ 与 ping 实测吻合
```

⇒ **在途量就是延迟的来源**；`rtt_min = 4ms` 是这条路的地板。（通俗解释见 10.2.3）

#### 10.2.3 "这 200ms" 到底是什么

全文反复出现的"这 200ms"，指的是**一次往返里多出来的排队时间**。先说数字：

```
空载 ping（没有任何传输）   4 ~ 7 ms     ← 这是这条路"最快能有多快"
跑传输时 ping              217 ~ 228 ms  ← 多出来的 ~215ms 就是"这 200ms"
传输一停 ping 立刻回到       4 ~ 7 ms     ← 队列消失（两次独立测量都如此 ✓）
```

##### 它花在哪里：不是花在路上，是花在排队上

无线电/光纤的**传播时间只有几毫秒**（空载 ping 就是这么来的 ✓）。多出来的 200ms
**全部花在"排队"上**：包已经发出去了，但卡在路径上某个设备（这里是 AP/路由器）的
**发送缓冲区**里，等着被真正送出去。

##### 队列是怎么被排出来的（用实测数算一遍）

```
链路出口的速率（它每秒只能送走这么多）        ≈ 365 KB/s   ← 由链路决定，改不了
我们同时放在路上、还没被确认的数据            = 在途量 = 64 帧 × 1280B ≈ 80 KB
把这 80KB 全部送出去需要的时间                = 80KB ÷ 365KB/s ≈ 221 ms
                                            ↑ 与实测往返 219ms 吻合 ✓
```

一条式子就够：**排队时间 = 积压量 ÷ 出口速率**。
我们**放出去的比出口能消化掉的多**，多出来的部分只能堆在缓冲区里；堆得越多，
每帧的往返就越长。空载时没有积压 ⇒ 4~7ms；开始传输后积压 80KB ⇒ 221ms ✓。

##### 类比（高速收费站）

| 名词 | 对应 |
|---|---|
| 收费站的通行速度 | 链路速率（≈365KB/s）|
| 我们同时在路上的车数 | 在途量（64 帧）|
| 收费站前排队的车 | AP/路由器缓冲区里积压的包 |
| 每辆车通过收费站要花的时间 | 我们观测到的往返（219ms）|

**要缩短它，唯一要做的是"少放一些车同时上路"** ✓ —— 不是修路（路没坏：空载只要 4ms ✓）。

##### 为什么说"是我们自己撑住的"

- 排队时间**正好等于**"我们的在途量 ÷ 链路速率" ✓（不是巧合，是定义 ✓）；
- **传输一停，队列立刻排空**，ping 当秒从 220ms 掉回 4~7ms ✓；
- 换成 iperf3（在途量 550~700KB ✗）测，ping 就涨到 **374~704ms** ✓
  ⇒ **谁把在途量放得多，谁的队列就更长** ✓。

##### 为什么它会拖累别人、也拖累自己

`ping` 是 ICMP，和我们的数据包毫无关系，却被同样延迟了 219ms ✓
⇒ 队列是**共享**的，摆在路径上的同一个位置 ⇒ 我们自己把同一时刻的其他流量
（包括同一连接上的交互流量）一起拖慢了 ✓。

##### 为什么它很难被发现（关键）

```
队列不是在"跑了一会儿之后"才出现的，而是从第一秒就被填满 ✗
⇒ 我们记录到的"最小往返"（rtt_min = 16ms；对照组"好链路"只有 4ms，见 10.5 开头）本身就已含这个队列 ✗
⇒ 所有"拿当前往返和历史最小值比较"的算法（延迟梯度那一类）都会得出
  "没有拥塞"的错误结论 —— 它们被这个常驻队列结构性地蒙住了 ✗
⇒ 只有在传输停止的那一刻队列才排空，这时才能看到地板（4~7ms）✓
```

这就是为什么判断"这 200ms 是不是我们的"**不能靠观测，只能靠实验**（见 10.3.5 ✓）。

##### 这个现象的标准名字：bufferbloat（缓冲膨胀）

链路设备给的缓冲远大于"链路速率 × 往返时间"：

```
这条路：设备缓冲 ≈ 对端广告的 148 帧 ≈ 185KB
        链路真正需要的 ≈ 5 帧 ≈ 6KB
        ⇒ 相差 30 倍，多出来的缓冲必然被发送方填满 ⇒ 常驻队列 ✗
```

典型表现就是**带宽没变、延迟暴涨** ✓。所以"这 200ms 是不是我的"=
"这 ~215ms 排队，是不是我自己放太多帧造成的" ✓ —— 只有两种答案，且必须用实验区分 ✓。

### 10.3 改动清单

一个改动一个提交，各自附仿真/真机证据。

#### 10.3.1 ACK 扩展：回传"我的重传有多少是白费的"（可变长 ACK）

- **问题**：发送端无法从自身计数判断"重传是否必要"（它只知道自己重传了几次，不知道对端是否早就有）。
- **做法**：接收端统计"收到的重复数据帧"数，追加 1 字节在 ACK 尾部（`data[8]`，`ret >= 9` 时才发）；
  老对端不发这一字节 ⇒ 发送端读到 0 ⇒ 行为退回原样（**向后兼容** ✓）。
- **理由**：这是链路上**唯一**无法被本端计数污染的证据 —— 来自接收端的事实。
- **协议层细节见 8.3**。

#### 10.3.2 RTO 下限由"对端重复上报"驱动（`rto_floor`）

- **问题**：往返分布有长尾（迟到帧），固定倍数的 RTO 落在中位数附近 ⇒ 大量伪超时。
- **做法**：以证据窗口为单位统计"重传次数"与"被对端确认白费的次数"；
  白费占比高（≥ `FFRDP_WASTE_HI`）⇒ 抬 `rto_floor`（×5/4，上限 1000ms）；
  白费低 ⇒ 归还下限；并施加相对上限 `max(3×rtts, 100ms)`，让链路变快时下限自动回落。
- **关键教训**：**安静窗口不能触发衰减** —— 在限速链路上"安静"往往正是下限在起作用，
  对它衰减会让环路自我拆台（曾用 v5 犯过这个错）。
- **证据**：目标链路重传 28% → 2.3%（`perMB` 230 → 19），且好链路逐字不变。

#### 10.3.3 快重传纪律（`hole_wait`）

- **问题**：对端报的"洞"多数是**乱序**，不是丢包 ⇒ 立刻快重传 = 白费（占重传 65%）。
- **做法**：等待时长 `hole_wait` **由对端重复上报决定**：
  白费多 ⇒ 等 `3×rtt`（≤300ms）；白费少（真修复）⇒ **0**（与原来完全一致）；
  中间 ⇒ `rtt`。
- **理由**：同一个原则 —— **不用有歧义的信号，用接收端的报告**。
- **踩过的坑**：第一版"一律等 1 RTT"在仿真里把 **真修复** 一起延迟了（6 连丢 -78%），
  因为仿真里没有乱序。改成证据驱动后，全部场景与基线逐字相同。
- **顺带修掉**：超时退让由"每帧一次"改为"**每往返一次**"（v1.0.0 的 3.3/第 4 节问题 4）。

#### 10.3.4 在途量闸门（真正的刹车）

- **问题**：唯一的刹车是对端缓冲区大小（148~256 帧），而链路只需要几帧 ⇒ **我们自愿把队列灌满**。
- **做法**：在发送循环里按**在途帧数**（只数已首发未确认的帧）限制首发；
  `FFRDP_INFLIGHT_MAX` 为默认上限；重传不受此限制（修复路径永不被挡）。
- **理由**：`RTT = 在途 ÷ 链路速率`（推导见 10.2.3）⇒ 在途量就是延迟的来源；而吞吐由链路限速 ⇒
  **收窄在途量可以降延迟而不损失吞吐**（只要仍高于 BDP）。
- **注意**：默认值 64 是**保证不变**的保守值；真正有用的值由 10.3.5 实验得出。

#### 10.3.5 延迟探测：把"这 200ms 是不是我的"变成一次实验

- **动机**（"这 200ms"是什么、为什么测不出来，见 10.2.3）：常驻队列会让"与历史最小值比较"永远看到 0
  （最小值本身已含队列）⇒ **任何纯观测方案都是瞎的**，只有实验能回答。
- **做法**（`FFRDP_PROBE_ENABLE`，默认开启）：
  1. 触发：`rtts > FFRDP_PROBE_QUEUE_RATIO × rtt_min`（默认 **3×**；有我们撑住的队列）或白费率高；
  2. 探测：把在途上限**砍一半**，保持 `2×rtt + 500ms`；
  3. 判定：**延迟掉了 且 对端确认速率没掉** ⇒ 保留该上限（并可继续下探）；
     否则**立即还原**（延迟没掉 = 不是我们的；吞吐掉了 = 砍过头）；
  4. 队列消失后慢慢放开（giveback），链路变快时能自动回升；
  5. 失败后探测间隔翻倍（最多 60s）。
- **安全网**：还原逻辑保证"砍错"只损失一次 1.5 秒半窗口 ⇒ 不属于负优化。
- **证据（真机，step29）**：`probes 3 keep 3 revert 0`；`rtts` 215ms → 12~19ms（在途 64→8~16 帧）；
  负载 ping 220ms → 18~27ms；服务端吞吐反而 **+40%**；中途一次链路打嗝（461ms）探测**没有乱砍**。
- **收敛不再需要等退避**（step31，通用做法 ✓）：探测**成功**的下一次不再等 10s，而是
  `2 × rtt + 500ms` 后就再问 ✓ ⇒ 没被测量过的路径也能**几秒内**自己收敛 ✓，
  失败仍翻倍 ⇒ 自我限速 ✓。**不需要为任何路径预先填值** ✓（按环境填值的版本见 10.4）。
- **门槛降到 3×（step30，真机 ✓✓）**：两方向都收敛到地板 —— 服务端 `rtts` **217 → 10~19ms**（43× → 3×）、
  客户端 **219 → 17~18ms**（**1×**，即贴地板 ✓）；`keep 5~6` / `revert 1`（那一次被速率守门挡下 ✓）；
  `perMB` 服务端 **1.1**（历史最好）/ 客户端方向 **6.9**；服务端吞吐 **574~650KB/s**（新高）；
  好链路每轮最多多一次探测，且**被还原** ✓（`revert 1`, gap 10→60s ✓）。

#### 10.3.6 诊断输出（`ffrdp_dump`，便于后续维护）

**先看这一行**（一眼识别"是不是刚编的二进制"——这个坑踩过三次：跑错 `./test` 而不是新构建 ✗）：

```
build               : probe 1, queue ratio 3, inflight default 64, compiled Oct  9 2026 21:54:13
```

**延迟有三个量，别混用**：

| 行 | 含义 |
|---|---|
| `rttm` | **最近一次**采样（名字有误导 ✗）|
| `rtt_min, rtts, rttd` | 本区间**最低**（= 这条路的地板）/ 平滑**典型**值 / 抖动 ✓ |
| `rto` | **计时器，不是延迟** ✗（它被下限抬上去，不代表链路变慢 ✓）|

**闸门与探测（step28~30 的核心）**：

| 行 | 含义 |
|---|---|
| `inflight, cap` | 真正在途的帧数 / 当前上限（`kept` = 已被实验证明的值；`probes keep revert too-far giveback`）|
| `in-flight limit` | 生效的在途上限（默认 64 = 优化前行为 ✓）|
| `probe trigger` | 触发输入：白费率（pm）、`rtts/rtt_min`、在途帧数，以及三个门槛 |
| `queue test` | **门槛本体**：`rtts / rtt_min`（`>3×` 才做实验；在地板或以下显示 `1x` ✓）|
| `probe rtt ref/best` | 探测前 vs 探测中的**最低**往返 ⇒ **"队列是不是我们的"的原始证据** ✓ |
| `confirmed rate` | 对端确认速率（帧/秒）—— **吞吐守门人**（砍过头会让它掉 ✗）|

**乱序上报的诊断（纯诊断，不驱动任何行为 ✓）**：

| 行 | 含义 |
|---|---|
| `counter_recv_ooo` | **接收端**：乱序到达的帧数（它下面有洞）|
| `counter_recv_far` | …其中"距洞 > 23 帧"的（**注意它比掩码本身严一帧** ✗：`dist 24` 其实装得下，见下）|
| `counter_ooo_d1_24` / `d25_64` / `dgt64` | **距洞多远**，三档之和恒等于 `counter_recv_ooo` ✓。`d1_24` = 今天的 24 位掩码够得着（bit = `dist − 1`，`dist 24` 是最后一个 bit）；`d25_64` = 一个扩展字（64 位）够得着；`dgt64` = 一个扩展字也不够 |
| `counter_ooo_d65_128` / `dgt128` | 把 `dgt64` 再细分 ✓：`65..128` = **两个扩展字（128 位）够得着**；`>128` = 两个也不够。两档之和恒等于 `dgt64` ✓ ⇒ **扩展字宽就是由这两档定的** ✓（真机上 `>64` 占 8.1%，所以 64 位不够 ✓）|
| `counter_ooo_64reach` / `128reach` | `(d1_24 + d25_64) / recv_ooo` 与再加 `d65_128` 的版本 —— **改用 64 / 128 位掩码各能表达多少乱序**，这就是"值不值得加宽、加多宽"要看的两个数 |
| `counter_mack_bits_sent` / `_recv` | 本端**发出去**的 mack 位数 / 从对端**收到**的 mack 位数。两端各看一份：**差值 = 报告丢在路上** ✓（谁单独看都分不清"没报"和"报了没到" ✗）；`sent / recv_ooo` 看"报告是否真的在发生" |

三点读法：

- `far − (d25_64 + dgt64)` = **恰好 `dist == 24`** 的样本数 ✓ —— 正好用来自检那两个边界（真机上这两个数都很小 ✓）；
- ⚠️ **先确认这些数是累计还是增量** ✗：它们确实落在 dump 的"可清零区间"内，但**清不清零由调用方决定** ——
  `test.c` 传的是 `ffrdp_dump(ffrdp, 0)` ⇒ **不清零，数字是累计的** ✗。
  所以读日志时：要"这一段"就对相邻两块作差 ✓（或把调用改成传 1 ✓），**绝不能把它们当增量去求和** ✗
  （第一版分析就这么错过一次，结论会完全跑偏）；
- 它们**不让协议做任何不同的事** ✓：17 个仿真场景与改动前的基线**逐字相同** ✓。

**读计数的三个坑**：

- **`counter_resend_ratio` 会被"饿死链路"刷低** ✗，也会被**极低频发送**刷高 ✗（它的分母是**累计首发次数**，
  分母小的时候几次重传就能占很大比例）⇒ 所以现在**把绝对数一起印出来**：
  `counter_resend_ratio: 30.00% (6 / 20)` ✓（= 重传 6 次 / 累计首发 20 次）；
  判断浪费仍一律看 **`counter_resend_perMB`**（按交付归一 ✓）。
  注意它**可以超过 100%**：同一帧被重传多次时，分子（重传次数）会大于分母（首发的帧数）✓；
- `counter_resend_waste` 同样带绝对数 ✓（`100.00% (6 / 6)` ✓ = 对端说 6 次重传全部白费 ✓）；
- `counter_resend_waste` 是**对端**说我们白费的比例 ✓ —— 本端计数回答不了这个问题 ✓
  （它原来寄生在 `rto_floor, waste%` 那一行里，现已独立成行 ✓）。
- 三个比例（`counter_resend_ratio` / `counter_resend_waste` / `counter_resend_perMB`）在**分母为 0**
  时打印 `n/a` ✓，不再拿 `1` 兜底 —— 那会印出一个"像测量值"的假数字 ✗（见 [`notes.md`](notes.md) 10.4）。

### 10.6 普适性：仿真覆盖与边界

**结论：探测默认开启后，全部 17 个场景与改动前的基线逐字相同**（零回归）。
另外单独验证过：**默认值 64 帧**时同样逐字相同（闸门等效于原有的隐式上限）。

**未覆盖 / 残余风险（诚实列出）**：

1. **乱序密集链路**：仿真没有乱序模型。10.3.3 的证据来自真机（乱序 26k 次那一轮）；
   探测不触碰这条路径，不会改变其行为。
2. **极快链路**：小上限会压吞吐；但探测的"速率守门"会**还原**，所以只会损失一次半窗口。
3. **判定阈值**：若某链路上砍一半后延迟掉、而速率掉幅 < 15%，会保留一个略亏的上限
   （有界，且下一次 giveback 会放开）。
4. **探测开销**：每 10~60 秒一次 1.5 秒半窗口（占空比 1~3%）；真机实测吞吐反而更高。
5. **探测时序类改动仿真判不了** ✗：仿真一次只跑 6 秒，短于重查间隔（10 秒）
   ⇒ 仿真里的探测从不发生 ⇒ 任何时序改动都会让它变 ✗（与好坏无关）。
   这类改动只能真机判 ✓；仿真只用来确认**干净链路逐字不变** ✓。

### 10.7 后续可做

- **24 位乱序掩码偏窄**（先量化，再决定 —— 诊断已就位，见 10.3.6 与 [`notes.md`](notes.md) 5.20）：
  1. **距离没有"结构上限"** ✗ —— 这里原先写过一个错的推断（"在途闸门 ≤64 ⇒ 距离 ≤64"），
     已被真机数据证伪 ✓。错在：闸门限的是**未确认**帧数，而**被对端位图确认过的帧会立刻从发送链表里
     摘掉** ⇒ 洞还开着、发送端却继续往前发 ⇒ 接收端连续位置到队尾的距离**没有上限** ✓。
     真机实测（服务端侧看到的"客户端→服务端"方向，累计 1831 次乱序 ✓）：
     `1..24` **46.6%** ✓ / `25..64` **45.2%** ✓ / `>64` **8.1%** ✗（`dgt64 = 149`）
     ⇒ 今天的 24 位只能表达 **46.6%**；加一个扩展字到 **91.9%**；
     **要连那 8.1% 的尾巴一起覆盖，就得两个扩展字（128 位）** ✓。
     宽度就由 `d65_128` / `dgt128` 两档定 ✓（它们**只报数、不驱动行为** ✓）。
  2. **不必新帧类型** ✓：直接在 `0x21` 尾部**按需**加 5 字节（bytes 9~13 = `mack[24:63]`），
     手法与 `dups`（byte 8）完全相同 —— 老发送端只读前 8 字节、`dups` 那字节有 `ret >= 9` 门槛 ✓
     ⇒ 多出的字节**既不读也不校验** ✓；新发送端用 `ret >= 14` 拦住 ✓ ⇒ 老对端不发的部分读作 0 ⇒
     **行为退回今天** ✓；两端都新且无乱序时**线上零变化** ✓。
     只是 ACK 的长度语义从"8 或 9"变成"8 / 9 / 14" ✓ —— 仍属 v1.1.0 的**可选字段扩展** ✓
     （不是新版本帧，更不是新帧类型）。
  3. 真要动手，代码有**四处边界必须先改**（否则尾巴白挂 ✗）：发送端 `dist > 24` 的那个 `break`、
