## 0. 三条铁律（先看；它决定很多"看起来能赚"的事能不能做）

1. **一次只上一个行为改动，且必须"无负优化"** ✓（notes §5.3）。理由不是洁癖：仿真与真机的单跑噪声
   有 ±20%（notes §26.48 / §26.51），混着改就分不出因果 ✗。
2. **目标平台是 ARM Linux 嵌入式；默认配置下不希望再多占内存** ✗（notes §26.53 / §26.54）。
   ⇒ **"加内存换吞吐"一律不算候选修复** ✗，只能当**诊断读数** ✓。这一条直接给下面几项定了性：
   套接字缓冲那 +60%~250%（notes §26.50~§26.53）、在途上限抬到 256 那些数字，**都不是交付候选** ✓；
   而且它已经被反证过：**v1.1 用同样的 188 KB 缓冲请求跑出 80.7 MB/s** ✓（notes §26.54）
   ⇒ 缓冲不是根因，它只是掩盖了别的 ✗。
3. **lo 上的吞吐只是"照妖镜"** ✓（notes §26.54）—— 用来和 v1.1 对照、定位根因；**验收必须回到真机** ✓。

**项目方拍板的取舍次序**（notes §1.1，此后一切设计按它判断）：**① 降重传率 → ② 保低延迟 → ③ 保吞吐量** ✓。
① 已达成（目标链路重传率 ~28% → ~1% ✓、稳态 0 次/秒 ✓）；本文的候选基本都落在 ②③ 上 ✓。

## 4. 候选 B：ACK 那一层（2026-10-16 讨论，结论最完整的一节 ✓）

### 4.1 成本账（`test.c` 的 `mss:1280` 场景）

ACK 是**独立数据报**（`ffrdp.c` 的 `ffrdp_recvdata_and_sendack` ✓），载荷 8 字节（带 `dup_seen` 证据时 9 ✓）：

| 项 | 值 | 说明 |
|---|---|---|
| ACK 载荷 / 线上 | **8~9 B / 36~37 B** | +UDP 8 +IPv4 20 ⇒ **78% 是网络头** ✗ |
| 数据满帧线上 | **1312 B** | 4 + 1280(smss) + 28 |
| 字节占比 | **2.7%** | 36 / 1312 ✓（可忽略 ✓）|
| **包数** | **+100%** | `FFRDP_ACK_COALESCE = 0` ⇒ **每收一个数据帧当场回一个 ACK**；双向全速 ⇒ 两个方向都翻倍 ✗ |
| sendto | **+100%**，且**发生在收包回调里** ✗ | 不是"多发一包"，是直接压在接收路径上 |
| 对端额外代价 | 每个 ACK 走一遍完整收帧路径 ✗ | `frame_node_new(FEC2, 1500)` + `memcpy` + 分发 ⇒ **8 字节的包付 1500 字节的处理费** ✗ |
| WiFi 空口（54 Mbps / 1284 B 帧，估 ✓）| ≈ **+65 µs/帧 ≈ +26% 时隙** | 帧越小越亏：400 B 音频帧 ≈ +53% ✗ |

**⇒ ACK 的成本是"每包固定成本"，不是"字节成本"** ✓ —— 2.7% 的字节、100% 的包数 ✓。

**现成的量法（都不改代码 ✓）**：`udp lowlevel tx: sendto <N> calls` 与帧数比（双向全速应 ≈ **2** ✓）、
`ack latency: <x> us avg`（`ffrdp.c` 里 `ack_lat_*` ⇒ 正是"收帧→交给内核"那一段 ✓）、
`udp lowlevel lap cost: ... mid(...rx)` ✓。

### 4.2 已经量过的那一半（别再重做 ✗）

notes §26.45 试过 **ACK 的时机**（`FFRDP_ACK_COALESCE=1`，一圈一个 ACK ✓）× RX 批上限一起扫：

- 机制成功 ✓（`ack coverage: on data 0, on tick 143001`，每个 ACK 覆盖 ~1.8 帧 ✓）；
- **吞吐没动** ✗（coal2 **25.3** vs base **21.9** / base2 **23.3** MB/s ⇒ 噪声带内 ✓）；
- 副作用：`fire`（要求"现在"的圈）**涨 5 倍** ✗ ⇒ 默认保持 0 ✓；
- 顺带否掉一条归因 ✗：`lowlevel-udp.c` 文件头说"RX 批上限=2 的主因是 ack 节奏"，**已过期** ⚠️
  （§26.45 证明"攒了 ack 再加大批还是更差" ✗）；批上限的真实最优后来由 §26.53 重扫为 **4** ✓。

### 4.3 三种形状（按"风险 / 收益比"排 ✓）

**(a) ACK 帧就地解析** ✓ —— **零协议风险** ✓，且削掉 ACK 最大那块成本（那个 1500 B 节点 ✗）。
- 做法：ACK 只有 8~9 字节 ⇒ 栈上直接解析，不走 `frame_node_new` + `memcpy` + 分发 ✓；
- 收益来源：§4.1 表里"对端额外代价"整行 ✓；
- 风险：改的是**收包主路径** ⇒ 必须用 `tools/check.sh` 全量 + 敌意输入那一套 ✓（notes §12 ✓）；
- **它不改线上格式** ✓ ⇒ v1 互通那格不受影响 ✓。

**(b) 事件驱动 ACK + `ack_delay`** ⚠️ —— 省的是**包数**（§4.1 的 +100% ✓），但有前提 ✗：
- **强触发**（新发现洞 / 窗口要更新）：**立刻**回 ✓（今天的形状 ✓）；
- **弱触发**（只推进进度）：给一个**真期限** `now + δ`（δ ≈ 0.25~1 ms ✓），
  **绝不能用 0 / "现在"** ✗✗ —— 这正是 §26.45 那 5× 空转的来源（`ffrdp_next_due` 一见到
  "欠着对端 ack" 就返回 now ✓）；
- **必须同时带 `ack_delay`** ✗：sender 的 `rttm` 把我们的 δ 算进去了 ⇒
  `rtts/rtt_min` 的排队判据（探测 ✓，`FFRDP_PROBE_QUEUE_RATIO = 3` ✓）与
  **绝对 2 ms 判据**（`FFRDP_PROBE_RTT_DROP_MS` ✓）会被 δ 污染 ✗。做法同 QUIC（RFC 9002 §5.3：
  `adjusted_rtt = latest_rtt − ack_delay`，并夹到 `max_ack_delay` ✓，防对端虚报 ✓）；
  单位要细 —— 默认路径 `rtt_min` 只有 1~5 ms ⇒ **ms 分辨率不够** ✗，建议 0.25 或 0.5 ms/单位 ✓。

**(c) 洞报告加宽：掩码扩展字 vs 区间列表** ⚠️ —— **先看 §2 的重评条件** ✗，
两次真机会话 `fast = 0%` 已把它否掉 ✓。若将来满足条件，两种形状：

| | 掩码扩展字（设计已留档 ✓）| 区间列表（SACK 形状 ✓）|
|---|---|---|
| 依据 | `ffrdp-v1.md` §2.3.4 附 | 本节 |
| 线上增量 | **+5 B**（bytes 9~13 = `mack[24:63]` ✓）| **+2 B/洞**（偏移 + 长度 ✓）|
| 覆盖 | 到 64；要尾巴齐全上 **128 位**（再 +9 B ⇒ ACK 最长 23 B ✗）| 不受 128 限制（偏移 1 字节 ⇒ 到 ~255 ✓）|
| 稀疏时 | 只要洞在 25~64 就**带满 5 字节** ✗ | 有 1 个洞就只付 2 字节 ✓ |
| 复用 | **复用手法完全等同 `dups` 那 1 字节** ✓（老端只读前 8 字节 ✓）| 新编码：收方要构造区间、发方要一套区间匹配 ✗ |
| 长度语义 | `8 / 9 / 14`（若做 128 位：`8 / 9 / 14 / 23` ✓）| `8 / 9 / ≥10`（`len >= 10` 即"有扩展" ✓）|
| 结论 | **改动小、机制现成 ⇒ 若重评，先做这个** ✓ | 只在"洞多且稀疏"时才更省 ✓ |

> ⚠️ 两处**必须知道**的实现细节（无论选哪种）✗：
> 1. **`dup` 那 1 字节不能被动** ✗✗ —— 它会经 `win_dup → waste → RTO 地板`（`ffrdp.c` 的
>    `ffrdp_apply_acks` ✓）⇒ 老对端把它当 flags 读就会**污染地板学习** ✗ ⇒ 扩展只能接在它**之后** ✓；
> 2. **发方有个早退陷阱** ✗✗：`ffrdp_apply_acks` 扫发送表时 `dist > 24` 就 `break` ✓ ⇒
>    对端报告"距 `una` 200 的洞"，这个循环**根本走不到那一帧** ✗ ⇒ 早退上界必须改，
>    但**不能退化成 O(窗口) 扫描** ✗（`ffrdp.c` 里那条注释记着：该分支每次 ack 都重走发送表 ✗，
>    所以才有了 `FFRDP_HOLE_CUT_ONCE` ✓）⇒ 正确形状是 **O(K)**：先把 ≤6 个区间平移成绝对 seq，
>    发送表只走**一趟**、用区间做成员判断 ✓。

### 4.4 附带一条（成本已被承认，但没人算过 ✓）：ACK 搭车

把 8 字节 ACK 挂到数据帧尾部（类型字节的高位空着 ✓）。**对症** ✓ —— §4.1 里占 100% 的"每包固定成本"
正好被省掉 ✓，还能让丢掉的 ACK 跟着重传自愈 ✓。**但收益与场景反相关** ✗：双向全速搭得上（那里 ACK 不是瓶颈 ✗）、
单向音视频搭不上（最需要省的地方省不到 ✗）⇒ 必须保留"没有数据帧可搭就当场独立回" ✓。
**结论：排在 (a) 之后，与 (b) 一起评估** ✓（细节：载荷长度算术 `frame_payload_size` ✓、
`data[0] <= FEC32` 那类判断会被 `0x80|type` 打穿 ✗、FEC 的异或尾要显式排除 ✓）。

## 5. 候选 C：pacing（状态最复杂，先把前提和判别器说清 ✓）

### 5.1 它为什么被搁置（**根因是一条信号歧义，不是"调不出来"** ✗）

notes §5.2 / §5.3：**"丢包 / 超时"这一个信号同时承载了"限速"和"抖动"两种含义** ✗：

| 链路 | 降速后发生什么 | 判别器看到的 |
|---|---|---|
| **被限速**（浅缓冲）| 超过硬顶的部分不再被丢 ⇒ 吞吐保持 ✓ | "限速" ⇒ 该降速 ✓ |
| **抖动** | 在途变少 ⇒ 迟到超时也变少 ⇒ **丢包也下降** | **看起来一样** ✗ ⇒ 误判 |

⇒ 任何基于丢包/超时的判别器都会被骗 ✗（v1~v8 八个控制律全试完 ✓，
最好的一版目标场景 +113% 但抖动场景 −60% ✗）。**要安全拿到那 ~17% 被限速浪费掉的上行，
需要"只削掉确切的那部分浪费"，那是重新设计，不是调参** ✓（notes §5.2 结论）。

### 5.2 与"延迟梯度控速"的区别（**别合并** ✗✓）

- **延迟梯度控速**（已被否 ✗，notes §7 / §8.3 #4）：用**延迟做反馈** ⇒ 常驻队列让"最小值"本身含队列 ⇒ 结构性失效 ✗；
- **pacing**（本文这条）：**按速率整形**，不靠延迟做判别 ✓。
- ⚠️ 注意：notes §1.1 准则 1 的**替代准则**是"**不让瓶颈排队**" ✓ —— 那正是这一条要做的事 ✓，
  与 §2 里被否掉的那个"延迟梯度"不是同一件东西 ✓。

### 5.3 三个**前提变了**（这是重启它的理由 ✓，不是"再试一次" ✗）

1. **闸门这条线已收工** ✓（notes §11.7：稳态 cap = 4、排队 6~7 ms ✓）⇒
   `ffrdp-v1.md` §2.3.7 里那句"**pacing 要等闸门修好才有意义**（此前窗口不是真闸门 ⇒ 收效甚微 ✓）"
   —— **这个前提第一次成立** ✓✓。
2. **当前瓶颈被定性为"等"** ✓（notes §26.54）—— 而 pacing 是"等"的**替代品**：
   把突发摊开 ⇒ 少丢 / 少排队 ⇒ 少超时 / 少重传 ⇒ 少等 ✓（方向一致 ✓）。
3. **量法变了** ✓：notes §11.7 明说"**固定窗口的 sweep 量不到 pacing 能碰的那部分（突发峰值）**" ✗
   ⇒ 需要一个**面向突发/瞬时队列**的量法 ✓（否则会像 §11.5 那样"判据说没有收益，其实没测到" ✗）。

### 5.4 三个**没试过**的形态（v1~v8 试的是"降均值" ✗）

| 形态 | 一句话 | 依据 / 起点 |
|---|---|---|
| **C1 削峰型**（速率不变，只压排队峰值 ✓）| 不改均值速率，只把"一圈内的成串发送"摊开 ⇒ 直接对着 §5.3 的第 3 条（量法）✓ | notes §11.4 结尾的"形态建议" ✓（原文就这么写的 ✓）|
| **C2 "实得速率 + 小余量"，且绝不低于 `cwnd` 隐含速率** ✗ | 只削掉确切的浪费，不整体降速 ✓ | notes §5.2 结论 ✓ |
| **C3 判别器换成"丢包 + RTT 不涨"** | 浅缓冲限速的特征是"**丢包出现但 RTT 不涨**" ✓，深缓冲才是 RTT 暴涨 ⇒ 判别器歧义比"丢包率"小得多 ✓ | notes §8.1 ✓（**pacing 系列从没用过这个判别器** ✗✓）|

### 5.5 ffrdp 里**已经有一层**粗粒度整形（别当成空白 ✗）

- `FFRDP_UNSENT_MAX = 24`：**未发出帧预算**，注释写明"接管原应用队列的突发整形" ✓
  ⇒ 现有的"pacing"是**帧预算级别、没有时间轴** ✗（一遍把 24 帧推出去还是突发 ✓）；
- ⚠️ **FEC 帧绕过闸门** ✗：`sfec = 5` 时每 4 个数据帧附 1 个 FEC 帧，**它直接 `sendto`、不进发送链表** ✓
  ⇒ 闸门数的是数据帧，实际**空口帧数 ×(1 + 1/N)** ✗ ⇒ 排队被整体抬高 ✓（notes §11.6 前置条件 2 ✓）。
  ⇒ **任何 pacing 评估都必须先固定 `sfec`（交付配置 = 0 ✓）** ✗。

### 5.6 验收线（沿用 §5.2 的三条，**缺一不可** ✓）

1. 目标场景（Apical 那条被限速 + 抖动的链路）**≥ +100%** ✓；
2. **干净链路 0 损耗** ✓；
3. **随机丢包 / 抖动场景不退化** ✓（这一条是 v1~v8 全部失败的地方 ✗）。

### 5.7 排序：**必须排在候选 A 之后** ✗

理由（notes §26.54）：v1.1 用同样的内存账跑到 80.7 MB/s、**CPU 打满 91%** ✓，v2 只有 46% ✗
⇒ **pacing 是"整形"，它不能把 46% 的 CPU 变成 91%** ✗。它是"等"的**替代品**，不是"等"的**替代修复** ✓。
