# ffrdp v2.0.0 接口说明

> 设计稿在 `ffrdp-v2.h` ✓（临时文件：v2.0.0 定稿后并入 `ffrdp.h` 再删 ✓）。
> 本文写的是**已经落地**的样子 ✓ —— 已经接线的、还是设计中的，都在这里标清楚 ✓。

## 一、和 v1.2.0 的差别

| | v1.2.0 | v2.0.0 |
|---|---|---|
| 一个上下文 | = 一条连接 | = **一张连接表**（服务端 accept 多客户端 ✓）|
| 建连 | 收到第一帧即视为连通 | **三次握手**（`hs` ✓，**默认开** ✓）|
| 接口 | `init(addr, txkey, rxkey, server, smss, sfec)` | `init(params, callback, cbctx)` + **句柄式** `send`/`recv` ✓ |
| 加密 | 内置 AES（位置参数传密钥）| **应用回调**（`FFRDP_ENCRYPT` / `FFRDP_DECRYPT` ✓），只做机密性 ✓ |
| 返回值 | `-1` 一律表示错 | 编码进返回值：`FFRDP_CLOSED` / `FFRDP_EAGAIN` / `FFRDP_EINVAL` ✓ |

## 二、params 配置串

```
ffrdps://0.0.0.0:8000,maxconn:16,handshake_ms:10000,idle_ms:5000,mss:1024,fec:0,hs:1
```

| 键 | 含义 | 默认 |
|---|---|---|
| `maxconn` | 连接表上限（服务端；含内嵌的主连接 ✓）| 16 |
| `hs` | 三次握手开关：`1` 走握手 / `0` 走 v1 那条老路 | **1** |
| `handshake_ms` | 等 SYN-ACK 的时限（握手重传间隔同此）| 10000 |
| `idle_ms` | 空闲判死 / keep-alive 超时 | 5000 |
| `mss` | 单帧最大载荷 | 由对端学习 + 上限 |
| `fec` | FEC 冗余 | 0 |

- 超时类键**单位一律毫秒** ✓，且**写进键名**（`_ms` ✓）—— 与 `ffrdp_send` 的 `timeout_ms` 同一套风格 ✓。
- 解析失败 ⇒ `ffrdp_init` 返回 `NULL` ✓，**原因打在 log 里** ✓（用户从 log 判断 ✓）；成功后 dump 会打印解析结果 ✓。
- ⚠️ **`hs` 默认是 1** ✓：v2 默认不与 v1.2.x 互通 ✗；要跟 v1 对测/互通，必须显式写 `hs:0` ✓。

## 三、连接与句柄

- 句柄就是**连接表的下标** ✓。**0 号是内嵌的主连接** ✓ —— 客户端用的就是它 ✓。
- 服务端的应用句柄来自 **`FFRDP_ACCEPT` 事件** ✓：被 accept 之前，服务端**没有**可用的应用句柄 ✓
  （拿 0 号去收发不会串到别人，但也不是那条新连接 ✓）。
- **索引永不复用** ✓：陈旧句柄只会查到"已关闭"的连接 ⇒ 返回 `FFRDP_EINVAL` ✓
  （代价：句柄用满（= `maxconn`）就不再接新连接 —— 第一阶段接受这个取舍 ✓）。
- 未握手的地址送来的帧**一律丢弃** ✓；服务端达 `maxconn` 后，未连接对端的包同样丢弃（并计数 ✓，不静默 ✗）。

## 四、事件与回调

| 事件 | 何时触发 | 载荷 |
|---|---|---|
| `FFRDP_ACCEPT` | 服务端：新连接建立 ✓ | `conn` = 新句柄 ✓，`addr` = 对端地址 ✓ |
| `FFRDP_CONNECT` | 客户端：握手完成 ✓ | — |
| `FFRDP_DISCONN` | 连接断开 ✓（也可由 send/recv 的返回值得知 ✓）| — |
| `FFRDP_ENCRYPT` | 发帧**定稿**时 ✓ | `buf`/`len` = 帧载荷 ✓ |
| `FFRDP_DECRYPT` | 收到帧、**即将交付给应用**时 ✓ | `buf`/`len` = 帧载荷 ✓ |
| `FFRDP_RECVDATA` | 收到应用数据（异步通知 ✓）：**入接收缓冲之前**报一次 | `buf`/`len` = 本次交付的数据 ✓ |

- **回调持着协议锁**被调用 ✓ ⇒ 回调里**不许**再调 `ffrdp_*` ✗（会自锁 ✗）。记状态/做原地变换可以 ✓。
- 返回值**只对 `FFRDP_RECVDATA` 有意义** ✓（`FFRDP_CONSUMED` / `FFRDP_NOT_CONSUMED` ✓）；
- `FFRDP_RECVDATA` 的两个返回值都会**照常确认这一帧** ✓（`recv_seq` 推进、ack 照发 ✓）⇒
  "取走"只影响**这段字节归谁保管** ✓，不影响传输 ✓（不然发送侧就会卡住 ✗）。
  其余事件忽略返回值 ✓。

### 4.1 加密回调（`FFRDP_ENCRYPT` / `FFRDP_DECRYPT`）

- **放在协议层** ✓（密钥状态本来就是每连接的 ✓；lowlevel 不认识 conn ✗）；作用在**帧载荷**上 ✓
  ⇒ 对 `ffrdp_send` / `ffrdp_recv` **完全透明** ✓（应用只看见字节流 ✓）。
- 语义：**原地修改** ✓ —— 帧长由协议定 ✓，回调只在 `buf` 的前 `len` 字节里原地改 ✓。
  ⇒ "要不要加密"完全由应用决定 ✓（协议不强制 ✓）。
- ⚠️ 帧有**两条出口**，两条都必须挂上 ✗✓：
    - ①**攒满一个 mss** 的整帧 ✓
    - ②**超时 / `ffrdp_flush` 的短帧** ✓
  只挂一条 ⇒ 另一种帧明文出去 ✗，对端却按密文解 ⇒ 数据直接坏掉 ✗。（`t_crypto` 就是钉这个的 ✓）
- **只加密一次** ✓：定稿时做 ✓，帧节点之后会被**原样重传** ✓ ⇒ 重传的是同一份密文 ✓
  （重传再加密一次的话，对有状态 / 随机 IV 的密码就是解不开 ✗）。
- 第一阶段**只做机密性** ✓，不做完整性/防篡改 ✗ ⇒ 需要完整性请在上层加 MAC ✓。
- v1 的内置 AES 已停用 ✓（`CONFIG_ENABLE_AES256` 那套不再是接入点 ✗）⇒ 接入点只有回调这一条 ✓。
- **块要求由应用自己处理** ✓：协议交给你的是**整段载荷、任意长度** ✓。你的算法支持字节级 ⇒ 随便加 ✓；
  有块要求 ⇒ 自己覆盖**块整数倍**的那段 ✓，余下不足一块的字节**留明文** ✓
  （协议**不**替你对齐 ✗、也**不**知道块大小 ✗）。
- **对称是唯一的原则** ✓：同一段缓冲区先过 `ENCRYPT`、再过 `DECRYPT`，能**恢复原样**就算合格 ✓。
  两个回调**都不处理** ⇒ 等于没有加密 ✓，但**通信照常** ✓ —— "要不要加密"完全由应用决定 ✓。

## 五、握手 / 挥手

- 只占**一个**帧类型号：`FFRDP_FRAME_TYPE_HANDSHAKE = 35` ✓；载荷第 1 字节是子类型 ✓
  （SYN / SYN-ACK / ACK / FIN ✓）⇒ 将来加字段只扩载荷 ✓，不用再吃类型号 ✓。
- 构造方式照抄 QUERY ✓（不走 `frame_node_new` ✗ ⇒ 绕开"type > SHORT 就多 2 字节 FEC 尾巴"的规则 ✓）；
  **不进数据 ARQ** ✓ —— 它有自己的重传计时器（就是 `handshake_ms` ✓）。
- 半开连接有**上限** ✓（`handshake_ms` 计时 + 计数封顶 ✓）⇒ 伪造源地址的 SYN 不能一路吃内存 ✓。
- 收到 **FIN** ⇒ 报 `FFRDP_DISCONN` 并放掉那条连接 ✓（表槽清空 ✓、水位不回收 ✓）。
- v1 收到 v2 的握手帧会**静默丢弃** ✓（正好符合"不互通、但能识别并丢弃" ✓）。

## 六、接口清单与接线状态

| 接口 | 状态 |
|---|---|
| `ffrdp_init` / `ffrdp_exit` | ✅ 已落地 ✓（`exit` 会关掉全部连接并 join 传输层线程 ✓）|
| `ffrdp_send` / `ffrdp_recv`（带句柄 ✓）| ✅ 已落地 ✓（`send` 原子 ✓；`recv` 有序字节流、有数据就返回 ✓）|
| `ffrdp_flush` / `ffrdp_dump`（`conn < 0` = 全局 ✓）| ✅ 已落地 ✓ |
| `FFRDP_ACCEPT` / `CONNECT` / `DISCONN` | ✅ 已接线 ✓ |
| `FFRDP_ENCRYPT` / `FFRDP_DECRYPT` | ✅ 已接线 ✓（协议**原样**交付载荷 ✓，长度不改 ✓；两条出口都挂 ✓，`t_crypto` 验收 ✓）|
| `FFRDP_RECVDATA` | ✅ 已接线 ✓（`t_recvdata` 验收 ✓）——`FFRDP_CONSUMED` ⇒ 应用在回调里取走、协议不留 ✓；`NOT_CONSUMED` ⇒ 照旧留在缓冲里等 `ffrdp_recv` ✓ |
| `ffrdp_isdead` | ⚠️ 仍是 v1 形状 ✓（无句柄 ✗ —— 多连接下该按句柄问 ✓，待并进 v2 签名）|

## 七、怎么验

```
bash build.sh                 # 真机侧（ffrdp.c + lowlevel-udp.c + socket.c + utils.c + test.c）
bash tools/sim/run.sh         # 仿真侧：7 个测试 + 场景组（详见 docs/sim-test.md）
```

- `tools/sim/run.sh` 会把每个测试编两份：**HEAD 那份**与**工作区那份** ✓ ⇒ 新旧行为可直接逐字对照 ✓。
- 目前仍靠"**老路径逐字不变**"当回归网 ✓（`e2e-raw` 组 ✓，`hs:0` ✓）—— 见 `docs/sim-test.md` ✓。
