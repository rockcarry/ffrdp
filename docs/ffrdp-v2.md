# ffrdp v2.0.0 接口说明

> **语言** ✓：本文档**只有中文版** ✗（英文版只有仓库根目录的 [`readme.md`](../readme.md) ✓）。
> 需要其它语言请**用 AI 自行翻译** ✓ —— 记得让它保留宏名、命令、代码块与 `✓ / ✗` 符号原文 ✓。

## 一、和 v1.2.0 的差别

| | v1.2.0 | v2.0.0 |
|---|---|---|
| 一个上下文 | = 一条连接 | = **一张连接表**（服务端 accept 多客户端 ✓）|
| 建连 | 收到第一帧即视为连通 | **三次握手**（`hs` ✓，**默认开** ✓）|
| 接口 | `init(addr, txkey, rxkey, server, smss, sfec)` | `init(params, callback, cbctx)` + **句柄式** `send`/`recv` ✓ |
| 加密 | 内置 AES（位置参数传密钥）| **应用回调**（`FFRDP_ENCRYPT` / `FFRDP_DECRYPT` ✓），只做机密性 ✓ |
| 返回值 | `-1` 一律表示错 | 编码进返回值：`FFRDP_CLOSED` / `FFRDP_EAGAIN` / `FFRDP_EINVAL` ✓ |

## 二、params 配置串

```
ffrdps://0.0.0.0:8000,maxconn:16,handshake_ms:10000,idle_ms:5000,mss:1024,fec:0,hs:1
```

| 键 | 含义 | 默认 |
|---|---|---|
| `maxconn` | 连接表上限（服务端；含内嵌的主连接 ✓）| 16 |
| `hs` | 三次握手开关：`1` 走握手 / `0` 走 v1 那条老路 | **1** |
| `handshake_ms` | 等 SYN-ACK 的时限（握手重传间隔同此）| 10000 |
| `idle_ms` | keep-alive：**半程**（`idle_ms/2`）没听到对端就发一个 QUERY 去确权 ✓；整整 `idle_ms` 没听到 ⇒ 判死（报 `DISCONN` 并收摊 ✓）。只在 `hs:1` 下生效 ✓ | 5000 |
| `mss` | 单帧最大载荷 | 由对端学习 + 上限 |
| `fec` | FEC 冗余 | 0 |

- 超时类键**单位一律毫秒** ✓，且**写进键名**（`_ms` ✓）—— 与 `ffrdp_send` 的 `timeout_ms` 同一套风格 ✓。
- 解析失败 ⇒ `ffrdp_init` 返回 `NULL` ✓，**原因打在 log 里** ✓（用户从 log 判断 ✓）；成功后 dump 会打印解析结果 ✓。
- ⚠️ **`hs` 默认是 1** ✓：v2 默认不与 v1.2.x 互通 ✗；要跟 v1 对测/互通，必须显式写 `hs:0` ✓。

## 三、连接与句柄

- 句柄 = **代号 × `FFRDP_MAXCONN` + 槽号** ✓（不是表的下标 ✗）；应用只把它当**不透明 int** 用 ✓。
  **0 号槽固定给内嵌主连接**（句柄 0 ✓）—— 客户端用的就是它 ✓。
- 服务端的应用句柄来自 **`FFRDP_ACCEPT` 事件** ✓：被 accept 之前，服务端**没有**可用的应用句柄 ✓
  （拿 0 号去收发不会串到别人，但也不是那条新连接 ✓）。
- **槽位回收 ✓、句柄不复活 ✓**：连接释放后槽位**立刻**可复用；复用时代号 +1 ⇒ 同一槽的句柄变了
  ⇒ 陈旧句柄查表必然失败（`send`/`recv` 返回 `FFRDP_CONN_INVALID`、`ffrdp_isdead` 报已断 ✓），
  绝不会打到新连接上 ✓。所以"服务端一生只接 `maxconn-1` 条"这个旧限制**已经没有了** ✓
  （`notes.md` §26.101）。
- 未握手的地址送来的帧**一律丢弃** ✓；服务端连接表**全满**时才拒 accept，未连接对端的包同样丢弃
  （并计数 ✓，不静默 ✗；dump 里有 `hs refused (no free slot)` 一行 ✓）。

## 四、事件与回调

| 事件 | 何时触发 | 载荷 |
|---|---|---|
| `FFRDP_ACCEPT` | 服务端：新连接建立 ✓ | `conn` = 新句柄 ✓，`addr` = 对端地址 ✓ |
| `FFRDP_CONNECT` | 客户端：握手完成 ✓ | — |
| `FFRDP_DISCONN` | 连接断开 ✓（也可由 send/recv 的返回值得知 ✓）| — |
| `FFRDP_ENCRYPT` | 发帧**定稿**时 ✓ | `buf`/`len` = 帧载荷 ✓ |
| `FFRDP_DECRYPT` | 收到帧、**即将交付给应用**时 ✓ | `buf`/`len` = 帧载荷 ✓ |
| `FFRDP_RECVDATA` | 收到应用数据（异步通知 ✓）：在**交付点**报一次（帧已落进接收环的槽、还没交给 `ffrdp_recv` ✓）| `buf`/`len` = 本次交付的数据 ✓ |

- **回调持着协议锁**被调用 ✓ ⇒ 回调里**不许**再调 `ffrdp_*` ✗（会自锁 ✗）。记状态/做原地变换可以 ✓。
- 返回值**只对 `FFRDP_RECVDATA` 有意义** ✓（`FFRDP_CONSUMED` / `FFRDP_NOT_CONSUMED` ✓）；
- `FFRDP_RECVDATA` 的两个返回值都会**照常确认这一帧** ✓（`recv_seq` 推进、ack 照发 ✓）⇒
  "取走"只影响**这段字节归谁保管** ✓，不影响传输 ✓（不然发送侧就会卡住 ✗）。
  其余事件忽略返回值 ✓。

### 4.1 加密回调（`FFRDP_ENCRYPT` / `FFRDP_DECRYPT`）

- **放在协议层** ✓（密钥状态本来就是每连接的 ✓；lowlevel 不认识 conn ✗）；作用在**帧载荷**上 ✓
  ⇒ 对 `ffrdp_send` / `ffrdp_recv` **完全透明** ✓（应用只看见字节流 ✓）。
- 语义：**原地修改** ✓ —— 帧长由协议定 ✓，回调只在 `buf` 的前 `len` 字节里原地改 ✓。
  ⇒ "要不要加密"完全由应用决定 ✓（协议不强制 ✓）。
- ⚠️ 帧有**两条出口**，两条都必须挂上 ✗✓：
    - ①**攒满一个 mss** 的整帧 ✓
    - ②**超时 / `ffrdp_flush` 的短帧** ✓
  只挂一条 ⇒ 另一种帧明文出去 ✗，对端却按密文解 ⇒ 数据直接坏掉 ✗。（`t_crypto` 就是钉这个的 ✓）
- **只加密一次** ✓：定稿时做 ✓，帧节点之后会被**原样重传** ✓ ⇒ 重传的是同一份密文 ✓
  （重传再加密一次的话，对有状态 / 随机 IV 的密码就是解不开 ✗）。
- 第一阶段**只做机密性** ✓，不做完整性/防篡改 ✗ ⇒ 需要完整性请在上层加 MAC ✓。
- v1 的内置 AES **代码已删除** ✓（`CONFIG_ENABLE_AES256` 那套连同 `frame_node_encrypt` 与两个 `FLAG_*_AES256` 一起清掉了 ✗）⇒ 接入点只有回调这一条 ✓。
- **块要求由应用自己处理** ✓：协议交给你的是**整段载荷、任意长度** ✓。你的算法支持字节级 ⇒ 随便加 ✓；
  有块要求 ⇒ 自己覆盖**块整数倍**的那段 ✓，余下不足一块的字节**留明文** ✓
  （协议**不**替你对齐 ✗、也**不**知道块大小 ✗）。
- **对称是唯一的原则** ✓：同一段缓冲区先过 `ENCRYPT`、再过 `DECRYPT`，能**恢复原样**就算合格 ✓。
  两个回调**都不处理** ⇒ 等于没有加密 ✓，但**通信照常** ✓ —— "要不要加密"完全由应用决定 ✓。
- **怎么落地** ✓：由这些约束推出的方案（内置 ChaCha20 流密码 / TLS 架在 ffrdp 之上 + OpenSSL 代码骨架）、
  上层要写的伪代码、以及 `test.c --key` 的编译与用法，见 [`ffrdp-crypto.md`](ffrdp-crypto.md) ✓。

## 五、握手 / 挥手

- 只占**一个**帧类型号：`FFRDP_FRAME_TYPE_HANDSHAKE = 35` ✓；载荷第 1 字节是子类型 ✓
  （SYN / SYN-ACK / ACK / FIN ✓）⇒ 将来加字段只扩载荷 ✓，不用再吃类型号 ✓。
- 构造方式照抄 QUERY ✓（不走 `frame_node_new` ✗ ⇒ 绕开"type > SHORT 就多 2 字节 FEC 尾巴"的规则 ✓）；
  **不进数据 ARQ** ✓ —— 它有自己的重传计时器（就是 `handshake_ms` ✓）。
- 半开连接有**上限** ✓（`handshake_ms` 计时 + 计数封顶 ✓）⇒ 伪造源地址的 SYN 不能一路吃内存 ✓。
- 收到 **FIN** ⇒ 先**回一个** FIN（我方还没发过的话 ✓），再报 `FFRDP_DISCONN` ✓；
  服务端把那条连接放掉 ✓（表槽清空 ✓、水位不回收 ✓）；客户端只有主连接 ⇒ **不摘表** ✗，
  而是置 `HS_FAILED` ✓（`isdead` 报 1 ✓、`send`/`recv` 报 `CLOSED` ✓）。
- 主动关：**`ffrdp_close(ctxt, conn)`** ✓（v2 新增 ✓）⇒ 发 FIN、进 `FIN_WAIT` ✓ ⇒ 等对端的 FIN
  才 `DISCONN` + 收摊 ✓；FIN 也走重传（与 SYN 同一套计时器 ✓），实在等不到就按 `handshake_ms` 收尾 ✓。
  ⚠️ `hs:0` 下没有 FIN 这东西 ✗ ⇒ `ffrdp_close` 只做**本地拆除** + 报 `DISCONN` ✓。
- 空闲探活（`idle_ms`）与 FIN 是**两件事** ✓：前者是"对端还在不在"的确认（QUERY + ack ✓），
  后者是"我要走了"的通知 ✓ —— 空闲但活着的连接**不会被误杀** ✓（`t_keepalive` 钉住 ✓）。
- v1 收到 v2 的握手帧会**静默丢弃** ✓（正好符合"不互通、但能识别并丢弃" ✓）。

## 六、接口清单与接线状态

| 接口 | 状态 |
|---|---|
| `ffrdp_init` / `ffrdp_exit` | ✅ 已落地 ✓（`exit` 会关掉全部连接并 join 传输层线程 ✓）|
| `ffrdp_send` / `ffrdp_recv`（带句柄 ✓）| ✅ 已落地 ✓（`send` 原子 ✓；`recv` 有序字节流、有数据就返回 ✓）|
| `ffrdp_flush` / `ffrdp_dump`（`conn < 0` = 全局 ✓、`conn >= 0` = **只那一条** ✓；dump 每块带块头：句柄 + 对端 + 握手状态 ✓）| ✅ 已落地 ✓ |
| `FFRDP_ACCEPT` / `CONNECT` / `DISCONN` | ✅ 已接线 ✓ |
| `FFRDP_ENCRYPT` / `FFRDP_DECRYPT` | ✅ 已接线 ✓（协议**原样**交付载荷 ✓，长度不改 ✓；两条出口都挂 ✓，`t_crypto` 验收 ✓）|
| `FFRDP_RECVDATA` | ✅ 已接线 ✓（`t_recvdata` 验收 ✓）——`FFRDP_CONSUMED` ⇒ 应用在回调里取走、协议不留 ✓；`NOT_CONSUMED` ⇒ 留在接收环那一槽里等 `ffrdp_recv`（读完才还槽 ✓）|
| `ffrdp_isdead` | ✅ 已按句柄收口 ✓：`ffrdp_isdead(ctxt, conn)` ✓（1 = 失联（句柄指向已关闭的连接也算 ✓）/ 0 = 活着 / -1 = 参数错或句柄越界 ✓）|
| `ffrdp_close` | ✅ 已落地 ✓（`t_handshake` 阶段 6/7 验收 ✓）——`0` = 受理 ✓ / `-1` = 无效句柄 ✓；走 FIN 挥手（`hs:1`）或本地拆除（`hs:0`）✓ |
| `idle_ms`（keep-alive）| ✅ 已接线 ✓（`t_keepalive` 验收 ✓）——探活用 QUERY ✓；判死时服务端收摊 ✓、客户端置 `HS_FAILED` ✓ |
| 句柄失效后的 `send`/`recv` | ✅ 已明确 ✓：**对端 FIN / keepalive 判死之后**，旧句柄上 `send`/`recv` 返回 `FFRDP_CONN_INVALID`（-1 ✓，表槽已清）/ `FFRDP_CLOSED`（0 ✓，正是"等的时候断的"）⇒ **不会崩** ✓（真机上这里曾经是空指针/释放后使用 ⇒ SIGSEGV ✗，已修 ✓）|

## 八、与 v1.x 的互通（`hs:0`）

**结论：`hs:0` 就是"与 v1.2.x 互通"的那条路 ✓ —— 两个方向都实测通了 ✓。**

| 组合（本地两进程 ✓ 各 8~9s ✓）| 结果 |
|---|---|
| **v1 服务端 ← v2 客户端**，两侧 `FFRDP_HS=0` | 双方 `verify: OK` ✓，客户端实收 **341 MB / 41330 条** ✓ |
| **v2 服务端 ← v1 客户端**，两侧 `FFRDP_HS=0` | 双方 `verify: OK` ✓，**238 MB / 28811 条** ✓ |
| v2 ↔ v2（都 `hs:0` 或都默认 `hs:1`）| 双方 OK ✓（⇒ `hs:0` 不是"降级"，是完整走老路径 ✓）|
| v2 服务端**默认**（`hs:1`）← v1 客户端 | **0 / 0** ✗（v1 侧发出几十条就停 ✓）= 下面那条"默认不互通" ✓ |

为什么能通（不是巧合 ✓）：

- **帧类型号只往后追加** ✓：v1 用 `0/1/2..32/33(ACK)/34(QUERY)` ✓，v2 只加了 `35(HANDSHAKE)` ✓，老号一个没改 ✓；
- **数据面两个函数逐字等价** ✓：`ffrdp_send_data_frame` / `ffrdp_recv_data_frame` 归一化后（把 `c->` 折回上下文级 ✓）v1 24/41 行 vs v2 24/41 行 ✓，唯一差异是签名多了连接参数 ✓；
- **ACK 8 字节布局一模一样** ✓（`type | recv_seq<<8` + `mack` + `wnd<<24` ✓）；v2 往 mack 的空闲位多写一个"重传白费"计数 ✓，老对端不填 ⇒ 字段为 0 ⇒ 保持安全 ✓（代码里有注释 ✓）；
- **`QUERY = 34` v1 本来就收发都认** ✓（它自己的信用探测就是它 ✓）；
- **`hs:0` 时 v2 不发任何新帧** ✓：握手帧（35）、FIN、keepalive 探活**都被 `hs_enable` 挡住** ✓ ⇒ 线上就是 v1 那一套 ✓。

必须同时知道的边界 ✓：

- **两侧要一致** ✗：一侧 `hs:1`、一侧 v1 ⇒ 连不上 ✓（v1 二进制不认 `hs` 键 ✓ —— 它用位置参数 ✓，所以只需在 **v2 那一侧**写 `hs:0` ✓）；
- `hs:0` 下 v2 的新能力本来就关着 ✓（设计如此 ✓）：**不发** `FFRDP_ACCEPT` / `CONNECT` ⇒ 服务端的应用句柄就是 **0** ✓；`ffrdp_close` 只做**本地拆除** ✓（不发 FIN ✓）；`idle_ms` 的 keepalive 判死**不生效** ✓（靠 v1 那套 dead 检测 + ARQ ✓）；服务端只服务**一个**对端 ✓（多客户端是 `hs:1` 专属 ✓）。

例行判据 ✓（把它变成命令，而不是"记得测" ✗）：

## 九、v2.x 相对 v1.1.x 的协议改进

> 本章回答"**v2 的数据面与 v1 同构，那 v2 究竟强在哪**" ✓。每一条都带**验收口径**（口径不对的数字不用 ✗）
> 与**已知边界**（什么情况下它不管用 ✗）。原始计数在 [`notes.md`](notes.md)，本文只留结论。

### 9.0 三条判据（先看，它决定很多"看起来能赚"的事能不能做）

1. **一次只上一个行为改动，且必须"无负优化"** ✓ —— 仿真与真机的单跑噪声有 ±20%，混着改就分不出因果 ✗。
2. **目标平台是 ARM Linux 嵌入式，默认配置不靠"加内存换吞吐"** ✓ —— 加缓冲那类改动只能当**诊断读数** ✗；
   而且已被反证：v1.1 用同样的约 188 KB 缓冲跑出 80.7 MB/s（notes §26.54）⇒ 缓冲不是根因 ✗。
3. **lo 上的吞吐只是"照妖镜"** ✓（用来与 v1.1 对照、定位根因）；**验收必须回真机** ✓。

**项目方拍板的取舍次序**（此后一切设计按它判断）：**① 降重传率 → ② 保低延迟 → ③ 保吞吐量** ✓。
v2 已经把①做到目标链路重传率 ~28% → ~1%、稳态 0 次/秒 ✓；下面的改动基本都落在 ②③ 上 ✓。

### 9.1 拥塞窗口与在途闸门

| 改进 | 一句话 | 验收口径（实测） |
|---|---|---|
| **在途闸门"能升"** | v1.1 的闸门只会往下探（探测只会降）⇒ 高 BDP 链路永远停在默认 64 帧 ✗。v2 增加 `FFRDP_INFLIGHT_CEIL` + "顶死 + 没队列 + 没浪费"连续 5 秒才 +25%（revert 后一个周期不升、`swnd` 吃不下不升）| 仿真 60 s：200 ms 链路 **+33%**、20 ms **+15%**、丢包链路不变 ✓；天花板最终停在**对端窗口**（~100 帧），不是 CEIL ✓ |
| **pacing（ms 令牌桶，C1 削峰型）** | 不改均值速率，只把"一圈打一梭子 + 静默"这个**锯齿形状**摊平 ✓（`rtts < FFRDP_PACE_MIN_RTT = 5 ms` 时直接**不整形** —— 那个尺度上没有锯齿可修，见下 ✓）；补充速率 = 在途上限 / RTT × 125%（**不用**实得速率 —— 那会掉进"一压就降"的反馈陷阱 ✗）；平台没有微秒钟 ⇒ 令牌按整数毫秒补 ✓ | 真机 200 ms 链路、120 s/轮：不开整形 W=128 **重连 2 次**（重传 0.85/1.55%）、W=192 **重连 4 次**（2.53/6.30%）；开整形后同样两档 **0 次重连**、重传 0.07/0.11% ✓ |
| **RTT 地板离群保护** | `rtt_min` 不再被一个假的小样本钉死（只在 `sample*2 ≥ rtts` 时才下调）| 200 ms 链路吞吐 **359 → 525 KB/s（+46%）** ✓ |

pacing 的三个**必须知道**：

- **极小 RTT 上不整形** ✓：`rtts < FFRDP_PACE_MIN_RTT`（5 ms，含"还没采样"）⇒ `pace_fps = 0`，整条判据失效。
  理由：锯齿的周期就是 RTT，几百微秒的尺度上它不成问题；而整形的兑现靠 1 ms 期限、平台实际唤醒是几毫秒
  ⇒ 只剩"一桶 ÷ 唤醒周期"的代价（lo 实测 47.3 → 35.9 MB/s，`notes.md` §26.99）✓。
- **桶深下限 = 2 帧** ✗✗：小于 1 帧时令牌永远够不到"一帧"的 16 个单位 ⇒ 首发全被挡、链路静默 ⇒
  上层判对端失联并重连（W=96 实测 **5 次重连**；日志特征 `pace tok 14 … waited 171289 frames`）✓ 已修。
- **它挡不住"对端 ACK 被自己的上行队列压住"** ✗：双向满速时本端 TX 队列会把回程 ACK 一起排到后面，
  对端测到 1~2.4 s 的 RTT ⇒ 对端 RTO 顶到 2000、窗口塌到地板 ⇒ 静默重连。实测 W=256 在**不限速**下
  仍会崩（服务端 `cwnd 1~7`、`rtts 1122~2433 ms`、`ack_hole 700`）；把应用限速到 400 KB/s 即 0 次重连 ✓。
  ⇒ **W=256 不是"坏窗口"，是"要用就得配限速"** ✓。

**吞吐档（v2.x 真机定档，曾长期是默认；现用于高带宽 / 长 RTT 链路）**：`RX_WINDOW 128`、`INFLIGHT_MAX 128`、
`MAX_CWND 128`、`PACE_ENABLE 1`，完整宏集见 §9.7。真机复验：单连接 119 s、**0 次重连**、`verify OK`、
重传 0.06/0.49%、双向 **0.70/0.56** 与 **0.54/0.68 MB/s**（200 ms 链路）✓。

**当前代码默认是 64 档**：窗口 / 受理闸 / cwnd / 在途闸 / 在途天花板 / 乱序窗全 64，两环 64 / 64 ⇒
**191 KB/连接**（详见 §9.7）。它按"11 Mbps 级链路（RTT ≲ 68 ms）够跑满线速"定，内存只有吞吐档的 1/3；
要跑长肥链路就整组回到 128（`-D` 覆盖，不用改源码）。

**在途上限的两级自适应（①-49，`FFRDP_CAP_ADAPTIVE=1` 默认开；它同时关掉了 B2 探测，
`-DFFRDP_CAP_ADAPTIVE=0` 可回到探测）**

静态 cap 只能在"低重传"和"高吞吐"之间二选一（1019 交叉实测：cap 64 ⇒ resend 26.7%；cap 8 ⇒ 4.6%，
但收向吞吐 0.81 → 0.45 MB/s）⇒ 改成每 3 s 结算一次的控制器，四条规则共用 `cap_kept`：

| 规则 | 触发 | 动作 |
|---|---|---|
| **重传强度**（主）| `EMA(重传/首发) ≥ 13%`（EMA 系数 1/4，单窗会被噪声带偏 ✗）| 按比例降到 10%，一窗最多砍半，地板 `INFLIGHT_MIN` |
| **延迟**（副，只在重传 ≤7% 时）| `rtts − rtt_min ≥ 12 ms` **且**窗口真在用（`inflight ≥ 3/4 cap`）| 降到 "`rtt_min` + 4 ms" 对应的在途量；地板 = 当前交付速率 × 该目标（BDP）|
| **还账** | 延迟刀之后下一窗 `rtts` 没降 ≥5 ms | cap 还回去，**30 s 内不再按延迟砍**（队列是别人的，砍自己没用）|
| **升档** | 重传 ≤7% 连续两窗，且（`rtts − rtt_min ≤ 7 ms` **或**延迟控制已判无效）| +12.5%，上限 `INFLIGHT_CEIL` |

延迟规则是**单连接**的命门：不限速单流的重传只有 0.05~0.29%，重传规则一次都不会介入，全靠这条把
"cap 64 天生排出的 20 ms"收掉。它必须靠 `KEEP / GAP` 这组"砍了就验、验不出就退"的配对来防止在多流
共享队列时误伤（阈值全在 `ffrdp.c` 文件头的 `FFRDP_ADAPT_*`，注释只引用宏、不再抄数字）。

真机验收（2026-10-19，同一二进制，两档 AP，6 轮全部 `verify OK` 且 0 次重连）：

| 场景 | rtts | resend | 发/收 MB/s | 终值 cap |
|---|---|---|---|---|
| 慢 AP 单连接（不限速）| 7 ms | 0.29% | 0.33 / 0.68 | 5 |
| 快 AP 单连接（不限速）| 2 ms | 0.05% | 2.74 / 5.88 | 64 |
| 慢 AP 15 连接（SPEED=30）| 105 ms（`rtt_min` 3）| 7.7% | 0.30 / 0.45（合计）| 4~16 |
| 慢 AP 15 连接（不限速）| 22~379 ms | 5.7% | 0.33 / 0.38（合计）| 8~64 |
| 快 AP 15 连接（不限速）| 1~19 ms | 6.0% | 3.14 / 7.65（合计）| 4~64 |
| 快 AP 15 连接（SPEED=512）| 0~39 ms | 2.7% | 3.95 / 5.28（合计）| 4~64 |

两处**容易误读**的地方（读这几行前先看这里）：

- 慢 AP 15 连接那行的 `rtts 105` 是 15 条流共享的约 102 ms 常驻队列（`rtt_min` 只有 3 ms），由
  15 × 30 KB/s = 450 KB/s 对约 340 KB/s 上行容量（单流实测上限）的 1.3× 超卖造成 ⇒ **与 cap 无关**：
  每连接实际只拿到 23 KB/s = 345/15，说明卡的是链路；再收紧延迟阈值也压不下去，只会伤到单连接 ✗。
- 同一档的重传 7.7% 里 **89% 是白费**（`counter_resend_waste`；①-48b：85.6% 的重传在 1 RTT 内被确认、
  `counter_rto_behind` 143）⇒ 真丢包约 1%，性质是"RTO 抢在排队中的 ack 前面"。15 连接档一律看
  resend / `verify`，**不看 MB/s**：合计吞吐由空口容量决定（快 AP 单流 8.6 MB/s ↔ 15 流 10.8 MB/s）。

**三个实验开关（默认关，只用于定位）**：

| 开关 | 做什么 | 结论 |
|---|---|---|
| `FFRDP_CA_RTT_STEP=1` | 拥塞避免改成"每 RTT +1 帧"（标准 CA）| 能消掉崩溃，但窗口长期停在 10~50，吞吐掉到 **0.10 MB/s**（约 1/4）✗ 不作为默认 |
| `FFRDP_SSTHRESH_FLOOR=4` | 减窗时 `ssthresh` 地板从 1 抬到 4 | 限速场景下有效（400 KB/s 轮 0 次重连）；不限速 W=256 仍崩（只是把塌到底的 `cwnd` 从 1 变 4）✗ |
| `FFRDP_CA_NOQUEUE=1` | `rtts > rtt_min + 25 ms` 时不再加窗 | **反向**：它检测到的是**对端**上行队列（本端 `cwnd 1~7` 却 `rtts 2.4 s`），冻结本端窗口只会把自己的发送饿死（0.16 MB/s）✗ |

### 9.2 延迟

| 改进 | 一句话 | 验收口径 |
|---|---|---|
| **半帧按"空闲"发走**（`FFRDP_FLUSH_TIMEOUT 500` → `FFRDP_FLUSH_IDLE 2`）| 一帧的尾巴不再等下一帧来填满，也不等 500 ms | 饱和档吞吐无回归（74~80 → 81~84 MB/s）；默认档 **max 延迟 486 ms → 4 ms**、消息数 ×2.5 ✓ |
| **尾丢探针（TLP 的镜像）** | 洞之后的帧也全丢时，收方手里没有"更高序号"证据 ⇒ 谁也报不出洞 ✗。v2 在 RTO 的 3/4 处发一个 **QUERY**（不带数据序号 ⇒ 不污染 dup / RTO 地板证据）：对端有 ⇒ 连重传都省、也不进退避；对端没有 ⇒ 只把到期时刻拨到"现在" | `t_probe` 123 → **77 步**；`t_sweep` 12 组 **−29%~−47%**，无一组变差；健康链路 **0 探针** ✓ |
| **keepalive**（`idle_ms`）| 半程没听到就发 QUERY 确权；整整 `idle_ms` 没听到才判死 | `t_keepalive` 钉住（空闲但活着的连接不被误杀）✓ |

### 9.3 ACK 与 CPU 成本

| 改进 | 一句话 | 验收口径 |
|---|---|---|
| **ACK 合并**（`FFRDP_ACK_COALESCE=1`）| 一圈回一个 ack，不再每包回一个（ACK 的成本是"每包固定成本"，不是字节成本 ✗）| 收包回调 **2.78 → 1.50 µs/包（−46%）**、发出 ack **−60%**、协议环 CPU **−25%** ✓ |
| **ACK / QUERY 就地解析** | 8~9 字节的 ACK 走栈上解析，不再 `frame_node_new(1500)` + `memcpy` + 分发 | x86 上 ≈0 ✗（freelist 快）；保留理由：嵌入式堆慢时才有得赚 + 顺手修掉未初始化内存 ✓ |
| **整圈冻结时钟** | 一圈只读一次钟（52 处 `get_timestamp32_ms()` → `NOW_MS()`）| `clock_gettime` 原本占整进程 **4.4%**；同 CPU 吞吐 **+2.8%**、同吞吐 CPU **−3.2 点** ✓ |
| **发送叫醒合并**（`FFRDP_SENDWAKE_COALESCE=1`）| "队列由空变非空"才叫醒工作线程 | wakes/call **0.87 → 0.25**、吞吐 **+10%**、零内存 ✓ |

### 9.4 线程模型：成本在"交班"，不在 syscall

一个 `FFRDPCONTEXT` = **一条工作线程**（由 `lowlevel` 拥有）+ **一条数据 socket + 一条唤醒 socket**；
全部连接复用同一条 socket（连接是 addr，不是 fd ✓）。

| # | 限制 | 对"优化"的影响 |
|---|---|---|
| L1 | 回调一次一个、不嵌套，且都在同一条线程上 | 一条连接的慢回调会**阻塞该上下文里所有连接** ✗ |
| L2 | 回调里不许阻塞、不许 `ffrdp_exit` | 任何"在回调里等一等"的优化不成立 ✗ |
| L3 | 应用回调在 `ffrdp->lock` 里被调 | 回调里**绝不能**再调 `ffrdp_send/recv/close/dump`（自锁 ✗）|
| L4 | 应用回调跑在两条线程上（`ENCRYPT` 在应用线程，其余在工作线程）| 回调里的共享状态必须自己加锁 ✓ |
| L5 | 整圈冻结时钟是 TLS | 只对工作线程的回调生效；应用线程永远读真钟 ✓（设计约束，不是 bug ✗）|
| L6 | 每圈至少一对跨线程唤醒（notify 字节 / `pthread_cond_broadcast`）| 这是与 v1.1 的 CPU 差距主项（lo 上 +30 点，归一化后 1.8 倍）✗ |
| L7 | 应用 API 阻塞式 + 同一把锁 | 多应用线程并发写同一连接只会互相抢锁 ✗；没有 lock-free 路径 ✗ |
| L8 | `ffrdp_recv` 是有序字节流、无消息边界 | 应用要自己分帧 ✓ |
| L9 | 平台差异只在 Linux 一支（唤醒用 socket 不用 pipe）| 批量 syscall 只能算 Linux 的账 ✗ |
| L10 | `hs:0` 老路径没有握手 / FIN | 不能假设对端会回 FIN ✗ |

⇒ 这条线的结论：**成本在跨线程交班，不在系统调用条数** ✗ —— 所以 `recvmmsg` / `sendmmsg` 一类
"把 syscall 合成批量"被判为**不值得增加底层复杂度** ✓（见 9.5）。真实的 60 MB/s 以上吞吐需求很少，
这条线到此为止 ✓；将来真上高吞吐链路再回看 ✓。

### 9.5 已否 / 暂缓（避免重复劳动）

| 路线 | 状态 | 重评条件 |
|---|---|---|
| 调宽 24 位乱序掩码（`ACK2`，+5 B）| **暂不做** ✗ | `fast` 占比有明显分量（>20%）**且**接收侧乱序非零 —— 两次真机会话实测 `fast = 0%`、乱序 0 ✗ |
| `recvmmsg` / `sendmmsg` 批量收发 | **否** ✗（用户拍板）| 不再重评（实测收益 ~7~9 点 CPU，但把复杂度压进最底层 ✗）|
| RX 批 16 / 32 | **否** ✗ | 批 32 总 CPU +14.4 点、空圈 +70% ✗；批 4 已是扫描最优点 ✓ |
| 延迟梯度控速（bufferbloat）| **结构性失效** ✗ | 常驻队列让"最小值"本身含队列 ⇒ 没有干净基线 ✗（与 pacing 不是一回事 ✓）|
| 抬高 RTO 去覆盖往返尾部 | ✗ | 只在"几乎无真丢包"的链路有效；有真丢包时延迟真修复 ⇒ 净亏 ✗。**窄化版本仍待试**（`todo.md` P2：只在 `waste ≥ 80%` 且窗口未满时放开 `rto_floor` 的 4×rtts 天花板）|
| RTO 估计家族（step13~21）| **用尽** ✗ | 不再动"怎么估 RTO" ✓ |
| 固定 BDP 封顶 / 固定小上限（16 帧）| ✗ | 丢包链路一致退步 ✗ |
| FEC **默认开** | ✗ | 真丢包仅 ~0.2%、FEC 只救"丢"不救"迟到" ⇒ 5 倍空口换重传率反升 7.9% ✗；**"按需 FEC"仍开放** ✓ |
| 缩短探测重查间隔（1 s）| ✗ | 首次探测落在爬升期 ⇒ 退避翻倍，反而慢 20 s ✗ |
| `cond` 广播条件化 | **暂不做** ⏸ | 先量"有等待者时"的 skip 数并证明 >1% ✓ |
| 发送叫醒时间窗（`FFRDP_SENDWAKE_WINDOW_MS`）| **否** ✗ | W=1 ms：圈率 −86% 但吞吐 −92% ✗ |
| 探测的绝对 2 ms 判据（E5）| **否** ✗ | 前提已过时（keep 现在判 `rate_kept ‖ waste_down`）；放宽只会让 giveback 提前 ✗ |

| 定时器内部化 | 中性 ✓ | 只买 API 便利，无可见收益 ✓ |

> ⚠️ 一处常见误读 ✗：notes §26.48 A 的"大窗口下 59~65% 超时帧落在 24 格位图之外"是
> `inflight 256/512` + 应用突发灌入的工作点，**不是**"掩码必须加宽"的证据 ✓；同一实验默认档
> 的超时帧距离是 `<=7`、`max 4~6` ✓，与真机结论（`fast 0%`）一致 ✓。

### 9.7 内存账

**一句话**：常驻部分**没有任何收发缓冲**；连接一有帧就建两块定长环，此后**不再 malloc/free**（没有峰值、没有碎片 ✓）。
两块环的槽数**各自独立**：发送环受受理闸约束、接收环受乱序窗口/通告窗约束，不必再按大的那个一起付钱 ✓。
所有数字由 `bash tools/size.sh` 现场算 —— 它 `#include ffrdp.c`，用的就是代码里的 `ring_block_size()` ✓，不是文档里的手抄值。
下文按**当前默认（64 档）**给数：窗口 64 + 两环 64 / 64 ⇒ **191 KB/连接**；括号里的对照是吞吐档（窗口 128 + 两环 256 / 128 ⇒ 571 KB）。

#### 每连接

| 块 | 尺寸（MSS 上限） | 何时分配 |
|---|---|---|
| 发送环 | `FFRDP_SND_FRAME_RING(64) × 1512 B` = **94 KB** | 第一次 `ffrdp_send` 成帧（`snd_ring_init` ✓）|
| 接收环 | `FFRDP_RCV_FRAME_RING(64) × 1544 B` = **96 KB** | 第一帧到达（`rcv_ring_init` ✓）|
| FEC 临时落点 `rx_scratch` | `1544 B` | 只在这条连接**收到 FEC 帧**时 ✓ |
| `FFRDPCONN` 本体 | 456 B（FEC 开 3424 B / dev 3768 B，FEC 收发缓冲是内联数组 ✗ 白占）| 每条按需连接 |

- 每槽 = `节点头 40 + 4 帧头 + 载荷 + 2 FEC 尾`，再 8 对齐 ⇒ 发送按**该连接的 `smss`**（1464 → 1512 B），接收按**收方向上限** `MAX_RX_MSS`（1492 → 1544 B）。
- **全双工 191 KB**（`mss:1280` 时 83 + 96 = **179 KB**）；只跑一个方向时是 94 / 96 KB。
- 这是**默认（64 档）**的数字；吞吐档（两环 256 / 128、窗口 128）是 378 / 193 KB = **571 KB**（`mss:1280` 时 332 + 193 = 525 KB）。
- **懒分配**：空闲连接、以及握手期的半开连接都是 **0 B**（运行时可验：dump 里 `recv ring ①-46 : 0 bytes actually allocated over 0 conn(s)` ✓；输出行名里的 `①-xx` 是内部改动批次号，与用法无关，忽略即可）。

#### 每端点常驻

| 项 | 出货（DIAG=0, FEC=0） | dev（DIAG=1, FEC=1） |
|---|---|---|
| `FFRDPCONTEXT`（含 `table[16]` + `gen[]` + 0 号槽那条**内嵌**连接）| 928 B | 4,240 B |
| `UDP_LOWLEVEL` | 160 B | 440 B |
| **合计** | **≈ 1 KB** | **≈ 4.6 KB** |

#### 和之前几版比

| 版本 | 每端 / 每连接的缓冲 | 峰值形状 |
|---|---|---|
| v1.2.0 | `recv_buff` 186.5 KiB + `app_tx` 64 KiB ≈ 250 KiB/端 | 静态（内联在结构体里）|
| v2 HEAD（双环拆分之前）| `recv_buff` 190,976 B/连接 + **每帧 calloc 一块节点**（在途 ≤128 发 + ≤256 收）| 随在途量起伏；malloc/free 一直跑，堆驻留不可预测 ✗ |
| **现在（双环各自定容，默认 64 档）** | 双环 **191 KB**（懒分配；单向 94 / 96 KB；吞吐档 128 / 128 两环 = 571 KB）| **定值**：既不涨也不还，无 190 KB 常驻、无每帧节点 ✓ |

> 拆分之前两环共用一个 `FFRDP_FRAME_RING = 256` ⇒ 双环 764 KB。两个方向的约束其实完全不同：
> **接收环只要装下通告窗（1×），发送环还得装下"表头的洞 + 洞之后一整个窗口的进度"（2×）**。
> 共用只能按大的那个配；拆开之后接收侧直接省掉 193 KB ✓。

#### 想省内存，动这几个旋钮（按顺序）

| 旋钮 | 现在 | 说明 |
|---|---|---|
| `FFRDP_LOWLEVEL_FRAME_MAX`（1500，在 `lowlevel.h`）| 派生 `MAX_RX_MSS 1492` / `MAX_MSS 1464` | 直接缩每槽载荷 ⇒ 两块环同比缩（1500→1200 ⇒ 省 ≈20%）|
| `FFRDP_RCV_FRAME_RING`（64 槽）| 必须 ≥ `FFRDP_RECV_QUEUE_MAX` 且 ≥ 通告窗；2 的幂 | 线性缩/放接收环（96 KB）。1× 窗口是下界，**不能再小** ✗ |
| `FFRDP_SND_FRAME_RING`（64 槽）| 必须 ≥ `FFRDP_MAX_WAITSND`；2 的幂 | 线性改发送环（94 KB）。默认 64 = 1× 窗口；给 128（= 2× 窗口）⇒ 双环 285 KB，丢包时更顺（1× 时饱和吞吐 lo 实测 −13%：48.7/57.9 vs 59.6/62.9 MB/s，因为表头的洞会和后续帧挤同一个窗口）|
| `FFRDP_RX_WINDOW_FRAMES`(64) / `FFRDP_MAX_WAITSND`(64) | 通告窗 / 受理闸 | **要升降就得成组**改（cwnd / 在途 / 乱序窗 / 两环一起），完整清单见下面的「配置配方」：默认 64/64 = **191 KB**，吞吐档 128 窗 + 环 256/128 = **571 KB** |
| `FFRDP_RECV_QUEUE_MAX`（跟通告窗走）| 乱序窗口 | 默认 = 通告窗（最小安全值）；显式调小时必须 ≥ 通告窗 |

> ⚠️ 别把 `FFRDP_RECV_QUEUE_MAX` 单独调小于通告窗：窗口内的合法乱序会被当谎言丢掉（`ffrdp.c` 里那条编译期校验就是拦这个 ✓）。
> ⚠️ 也别把 `FFRDP_SND_FRAME_RING` 调到 `FFRDP_MAX_WAITSND` 以下：环形容量闸会变成比协议受理闸更紧的硬上限（同样有编译期校验 ✓）。
> ⚠️ 发送环的容量闸按 **seq 跨度**（`send_seq - snd_first`）算，不能按 `wait_snd`：对端乱序确认会让
> `wait_snd` 小于跨度，按它算就会在新帧落槽时盖掉表头那一帧（crc 错、流失去同步 ✗，已修）。

#### 配置配方：默认 64 档 / 吞吐档 128（照抄即可）

**代码默认就是 64 档**（下表「默认」那一列），所以嵌入式场景**什么都不用给**；只有想要吞吐档才需要整组
`-D` 覆盖。两档的关系只有三步，记住它就不会配错：

1. 先定**窗口** `W = FFRDP_RX_WINDOW_FRAMES` —— 它同时是内存与吞吐的主旋钮（吞吐上限 ≈ `W × smss / RTT`）；
   反过来推：`W ≥ 需要的吞吐 × RTT / 1464`（11 Mbps 线速 = 1.375 MB/s ⇒ RTT ≤ 68 ms 时 64 帧就够打满）；
2. 四个"跟着窗口"的闸门都设成 `W`：`FFRDP_MAX_CWND_SIZE` / `FFRDP_INFLIGHT_MAX` / `FFRDP_INFLIGHT_CEIL` /
   `FFRDP_RECV_QUEUE_MAX`（最后这个必须 ≥ 窗口）；`FFRDP_MAX_WAITSND` 也设成 `W`（它必须 ≥ 在途上限）；
3. 两个环都取 **2 的幂**：**发送环 ≥ W**（推荐 2W —— 1× 时表头的洞会和后续帧抢同一个环）、
   **接收环 ≥ max(W, 乱序窗)**。

> 漏了第 2/3 步会怎样？**编译期直接 `#error`**，报错原文就写着该调哪个、调到多少，
> 并指向本节 —— 例如 `FFRDP_RCV_FRAME_RING < FFRDP_RECV_QUEUE_MAX：调大了乱序窗就要同步调大接收环…`。
> 不存在"编过了、但悄悄变慢/丢包"的中间状态 ✓。
>
> 自检两处：`bash tools/size.sh`（每连接多少 KB）、运行时 `dump` 的
> `frame ring ①-46 : snd … slots x … B, rcv … slots x … B`（两个环确实按你配的槽数建了 ✓）。

下面这份是**完整**的，一条都不少；两列都可以用 `-D` 覆盖，不需要改源码 ✓。

| 宏 | 默认（64 档）| 吞吐档（128）| 作用 / 为什么必须一起改 |
|---|---|---|---|
| `FFRDP_RX_WINDOW_FRAMES` | **64** | 128 | 通告窗；吞吐上限 ≈ `W × smss / RTT` |
| `FFRDP_RECV_QUEUE_MAX` | = 通告窗（**64**）| 128 | 乱序窗；**必须 ≥ 通告窗**（编译期校验 ✓）|
| `FFRDP_MAX_WAITSND` | **64** | 128 | 受理侧帧数闸；必须 ≥ 在途上限 |
| `FFRDP_MAX_CWND_SIZE` | **64** | 128 | 拥塞窗上限；比窗口还大 ⇒ `wait_snd` 读数失去意义 |
| `FFRDP_INFLIGHT_MAX` | **64** | 128 | 在途闸门；源码注释就是"与窗口对齐" |
| `FFRDP_INFLIGHT_CEIL` | **64** | 128 | B2 探测天花板；比闸门大才有可升空间 |
| `FFRDP_SND_FRAME_RING` | **64**（= 1× 窗口）| 256（= 2 × 受理闸）| 发送环槽数：94 KB / 378 KB。1× 在丢包时更容易短暂停手 |
| `FFRDP_RCV_FRAME_RING` | **64**（= 1 × 乱序窗）| 128 | 接收环槽数：96 KB / 193 KB。1× 窗口是下界，**不能再小** ✗ |
| `FFRDP_FEC_ENABLE` | 0 | 0 | 默认已是 0；=1 会给每条连接加 ~3 KB 内联 FEC 缓冲 |
| `FFRDP_UNSENT_MAX` | 24 | 24 | 未发出帧预算；24 < 64，仍在窗口内 ✓ |
| `FFRDP_INFLIGHT_MIN` | 4 | 4 | 在途探测地板 |
| `FFRDP_MAXCONN` | 16 | 16 | 连接表上限；16 × 191 KB ≈ 3 MB ⇒ 按实际客户端数调小（不影响环大小）|

构建 / 看账 / 跑仿真（三处都认 `EXTRA_CFLAGS` ✓）：默认档直接跑就行；下面是**吞吐档**的覆盖示例。

```bash
CFG='-DFFRDP_RX_WINDOW_FRAMES=128 -DFFRDP_RECV_QUEUE_MAX=128
     -DFFRDP_MAX_WAITSND=128 -DFFRDP_MAX_CWND_SIZE=128
     -DFFRDP_INFLIGHT_MAX=128 -DFFRDP_INFLIGHT_CEIL=128
     -DFFRDP_SND_FRAME_RING=256 -DFFRDP_RCV_FRAME_RING=128'

EXTRA_CFLAGS="$CFG" TOOLCHAIN_NAME=gcc bash build.sh ship                  # 出货构建
EXTRA_CFLAGS="$CFG" bash tools/size.sh                                     # 内存账
EXTRA_CFLAGS="$CFG" TESTS='t_recvdata t_fec t_fuzz t_readpath' bash tools/sim/run.sh   # 仿真
```

配方速查（数字都是 `tools/size.sh` 的实测口径）：

| 目标 | 关键宏 | 发送 / 接收环 | 每连接 | 吞吐上限（200 ms RTT）|
|---|---|---|---|---|
| **默认（嵌入式 / 11 Mbps 级链路）** | 不给任何 `-D`（窗口与闸门 64）| 94 / 96 KB | **191 KB** | ≈ 470 KB/s（RTT ≤ 68 ms 就能跑满 11 Mbps）|
| 吞吐档（桌面 / 服务器 / 长 RTT 链路）| 整组 128（见上面的 `CFG`）| 378 / 193 KB | 571 KB | ≈ 940 KB/s |
| ≤ 128 KB | 窗口 32 + 环 32 / 32 | 47 / 48 KB | **95 KB** | ≈ 234 KB/s |
| ≈128 KB、但保留 64 帧窗口 | 64 档 + `FFRDP_LOWLEVEL_FRAME_MAX=1000` | 63 / 65 KB | **128.5 KB** | ≈ 470 KB/s（包数 ×1.5）|

- 「窗口 32」那一行把 `RX_WINDOW_FRAMES` / `RECV_QUEUE_MAX` / `MAX_WAITSND` / `MAX_CWND_SIZE` / `INFLIGHT_MAX` /
  `INFLIGHT_CEIL` / 两个环**一起**改成 32 就行（窗口 ≥ 2 是硬下限）。
- `FFRDP_DEF_CWND_SIZE`（32，`ffrdp.c` 里的裸 `#define`，不能 `-D`）在窗口 32 时正好等于整个窗口 ⇒
  慢启动退化成"一步到位"，不算错；想更保守才需要改源码（16）。
- 最后一行的 `FFRDP_LOWLEVEL_FRAME_MAX`（`lowlevel.h`，已支持 `-D` 覆盖）会同时改 `MAX_RX_MSS / MAX_MSS`
  ⇒ 协商出来的 `smss` 被夹到 964（`mss:1024` 实际变成 964，包数变多）。两个仿真用例（`t_fec` / `t_readpath`）
  里写死的 `mss:1024` 帧数断言会因此对不上 —— 那是测试常量问题，不是协议回归 ✓。

#### 默认 64 档的代价（相对吞吐档，不只是"吞吐下降"）

1. **吞吐上限 ≈ W × smss / RTT**（在途量 = 窗口 × 每帧载荷）：64 帧 ≈ 94 KB 在途 ⇒ 200 ms 链路 ≈ 470 KB/s；
   32 帧 ≈ 234 KB/s；128 帧 ≈ 940 KB/s。**LAN / 短 RTT 基本看不出来**（lo 实测 64/64 仍有 40~53 MB/s）。
2. **发送环 = 1× 窗口**：表头那个洞要和洞之后的一整个窗口挤同一个环 ⇒ 丢一个包时发送侧更容易短暂停手
   （128/128 时 lo 实测饱和 −13%；想稳就把发送环给到 2× = 128 槽，多 94 KB）。
3. **乱序窗 = 64 / 32**：越过洞比这更远的乱序帧会被直接丢掉等重传（对乱序 / 丢包链路是额外重传，按序链路无影响）。
4. **正确性不受影响**：`环 ≥ 通告窗`、`乱序窗 ≥ 通告窗`、`发送环 ≥ 受理闸` 都是硬约束，非法组合编译期 `#error` ✓；
   64/64 与 32/32 已跑过丢包 / 乱序 / FEC / 洪泛仿真与真 socket 双进程（`crc_err 0 / len_err 0 / seq_gap 0` ✓）。

#### 库外、但记在同一个进程账上的两笔

| 项 | 量级 | 说明 |
|---|---|---|
| 线程栈 | 1 条工作线程/端点（默认栈）| RSS 只算实际触碰的那几十 KB；栈上限由系统/`pthread_attr` 决定，不在 `tools/size.sh` 里 |
| 内核 socket 缓冲 | 唤醒 socket 请求 **4 KB/向**（内核翻倍 ⇒ ≈8 KB，对端共 ≈16 KB ✓）| 数据 socket 用系统默认（`dump` 里 `socket buffers` 那行是 `getsockopt` 的实测值 ✓）；它跟"在途量 × RTT"一起决定内核侧驻留，和上面两块环是**两笔不同的钱** ✗ |
