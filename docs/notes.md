## 1. 设计目标（项目方给的原话）

1. 局域网音视频传输；
2. internet 上的 P2P 音视频传输 + VPN 网络。

要求：**低延迟**，以及**弱网环境下的带宽稳定**。

### 1.1 优先级决策（项目方拍板，2026-10，作为此后一切取舍的依据）

**① 优先降低重传率 → ② 然后保证低延迟 → ③ 然后保吞吐量。**

具体化（验收与设计时按这个次序判断）：

| 优先级 | 可量化判据 | 对设计的要求 |
|---|---|---|
| ① 重传率 | 客户端 `counter_resend_ratio`：38.7% → **< 5%** | 允许为此**适度延长 RTO / 牺牲修复延迟** |
| ② 低延迟 | 有效载荷的**平均**延迟不恶化；RTO 取"能压住重传率的**最小值**"，并设硬上限 | 不接受"用秒级 RTO 换重传率"❌；需要恢复**快重传**路径（真丢包的修复才不必等 RTO） |
| ③ 吞吐量 | 有效载荷吞吐不下降（预期应**上升**，因为省下的重传字节还给有效载荷） | 不作为否决项，但不能明显掉 |

**由①②③推出的两条设计准则**（后面照此执行）：

1. ~~**RTO 用闭环抬到"刚好够"，而不是固定倍数**~~ ⇒ **该准则已被实测否掉，见 4.3 与 5.4**：
   想去覆盖往返分布的尾部，只有在"链路几乎没有真丢包"时才划算；只要链路有真丢包（internet P2P 一定有），
   抬高 RTO 就会延迟真修复 ⇒ 净亏（step13~step21 全部验证过）。
   **替代准则**：**不让瓶颈排队**（延迟梯度控速），让 RTT 自己回到基线 ⇒ RTO 就自然够用了。
2. **压住重传率的同时必须恢复 `cwnd`**：伪超时会把 `cwnd` 打到 1~3 ⇒ 在途只有 1~2 帧 ⇒
   接收端拿不到乱序证据 ⇒ `resend_fast` 恒为 0 ⇒ **真丢包的修复只能等 RTO** ⇒ 延迟反而更高 ❌。
   所以"减少伪超时"与"低延迟"是**同一件事的两面**：伪超时消失 → `cwnd` 不再塌 → 管道变深 →
   形成乱序证据 → 快重传生效 → 真丢包修复不再依赖 RTO ✓。

## 2. 测试环境与测量协议

| 角色 | 机器 |
|---|---|
| server | 有线网台式机 |
| client | WiFi 网络笔记本 |

用过两个 AP：`Apical001-5G`（噪声大、上行被硬限速）和 `m2msw-lj-5G`（链路好）。
测试程序 `test.c`，**每 10 秒自动 dump 一次**。

### 2.1 计数器的语义（很重要，容易误读）

- 所有 `counter_*` 都是**从 `ffrdp_init` 起累积**的（`ffrdp_dump(ffrdp, 0)` 的 clearhistory=0）；
- `averg_send` / `averg_recv` 是**最近一个区间**的速率，不是全程平均；
- 新加的 `elapsed : N s` 行用来核对两边是不是同一时刻的 dump。

### 2.2 贴 log 的三条要求

1. **同一轮、两边、同一个 dump**：同一时间窗内两边字节数必须相等（±丢包）。曾经出现过
   `m2msw server send 10.72MB` vs `client recv 143.25MB`（差 13 倍），那是两次不同时间的 dump，
   拿来对比会得出完全错误的结论。
2. **一轮 60 秒的 6 个 dump 全贴**：这样能直接量化**同一次运行内**的波动，不用反复上机。
3. 用 `elapsed` 行核对两边对齐。

### 2.3 噪声的现实（必须先接受）

同一个 AP、**同一份代码**，重传率实测出现过 `17.78%` 和 `31%–33%`（差近一倍）。
所以：

- **单次结果不能定论**，判断收益要看同一轮内多个 dump 的趋势/中位数；
- 这也是先把仿真做成**完全确定性**的原因（见第 5 节）。

## 3. 链路画像：Apical001-5G

### 3.1 形态

| 指标 | 实测 | 含义 |
|---|---|---|
| 上行（client→server） | 卡在 **≈393KB/s（3.14Mbps）**，怎么压都上不去 | 硬限速（整形/令牌桶） |
| 下行（server→client） | 可以到 **36Mbps** 以上 | 上下行 **≈10 倍不对称** |
| 超速率的行为 | **主要是延迟抬升**（缓冲排队），真实丢包只有 **~0.3%**（见 3.2 修正） | 抖动大（`rttd` 12~27ms，峰值 109ms），**不是丢包主导** |
| 乱序上报 | `counter_ack_mack = 0`、`counter_ack_hole = 0` | 这条链路上**没有人在报乱序** |

### 3.2 一次代表性实测（客户端 60s，**用逐 10 秒增量对齐，不依赖时钟**）

> **教训**：两边进程启动时刻不同，`elapsed` 也对不齐；**只有逐 10 秒的增量可以比较**。

| | 每 10 秒增量 | 速率 |
|---|---|---|
| 客户端 `txfull` | 2861 / 2889 / 2806 / 2887 / 2858 | **287 帧/s** |
| 服务端 `rxfull` | 2879 / 2807 / 2841 / 2852 / 2865 | **286 帧/s** |

→ **真实上行丢包 ≈ 0.3%** ✓ —— 早期我算出的"11%"是**错的**（用了错位的累计值），特此修正。

同一轮客户端的其它计数：

```
counter_send_1sttime  12588     counter_resend_rto   4874  → 重传率 38.7% ✗✗
counter_resend_fast       0     counter_ack_una_dup  4871  ≈ resend_rto
counter_rto_head       3562     counter_rto_chain    1312     counter_rto_stale 0
counter_recv_ooo         20     counter_ack_mack        0     counter_ack_hole  0
wait_snd             248~256    （长期钉在上限 256）          counter_send_failed 13356
```

**结论：0.3% 的真实丢包 ↔ 38.7% 的重传率 ≈ 90 倍放大，全是自己造成的。**

（顺带澄清两个容易误读的计数：`counter_recv_ooo/mack = 0` 是"链路干净、根本没有乱序"的必然结果，
不是上报 bug；`counter_send_failed` 是**应用层背压**——队列满时 `ffrdp_send` 拒绝写入，不是网络错误。）

### 3.3 机制：RTO 太紧（贴着延迟分布的上沿）

客户端实测 `rtts 35~71ms`、`rttd 12~27ms` → `rto = rtts + 4×rttd = 99~177ms`；
而最近一次往返（`rttm`）能到 `109ms`，在途窗口 `cwnd` 只有 1~12 帧。

- 每秒发生 **81 次超时**（4874 / 60s），而每秒只发 287 帧 → **每 3.5 次发送就有 1 次超时**；
- 按在途 8~12 帧估算 → **约 25% 的在途帧被误判超时** → 即 **RTO 大致落在实际往返分布的
  75 分位上** ✗（TCP 会把它留在 99 分位以上）；
- 更糟的是**退避会被下一条 ACK 的 RTT 重算立刻抹掉**：代码在每个非重传帧被确认时都用
  `rtts/rttd` 重算 rto → "超时 → 退避 ×1.5 → 收到快 ACK → rto 降回去 → 再超时"循环
  （实测 60s 内退避 229 次、超时 4874 次）。

**对照组**：好 AP（m2msw）`rtts 0~4ms / rttd 0~7ms`、重传率 **0.14%**、`send_failed = 0`
→ **协议本身没坏** ✓，问题只出在"延迟大 + 抖动大"的那条链路上。

## 4. 关键机制发现（比任何单个改动都值钱）

### 4.1 `cwnd` 的语义陷阱

**`cwnd` 限制的是"每次 update 允许处理多少帧"，不是"在途帧数"。**

- 客户端 update 周期约 3ms，`cwnd = 1~3` ⇒ `1 帧/3ms ≈ 429KB/s`，**正好是那条链路的硬顶**；
- 所以在被限速的链路上，`cwnd` 必须保持在 1~3，**任何"窗口下限"或激进 AIMD 都会把
  发出量直接顶到硬顶之上**，只会更糟；
- 结论：**在这类链路上要低于硬顶，唯一办法是跳过某些 tick（pacing）**，靠窗口做不到。

（这也是为什么"加大窗口/撑开在途"那条路在真机上没收益、在仿真里重传率反而爆炸。）

### 4.2 `mack = 0 / hole = 0` ⇒ 发送端只能靠超时重传

- 接收端在 ACK 里用 24 位 `mack` 报"洞后面已经收到的帧"；实测这条链路上**全程为 0**；
- 于是发送端**拿不到任何乱序信息**，只能等 RTO 超时来补洞；
- 这是 28% 重传率的直接原因之一；

**怎么一锤定音**：看**接收端**的 `counter_recv_ooo`（乱序到达 = 它下面有洞）。

- 若 `recv_ooo` 在涨，而发送端 `counter_ack_mack` 恒为 0 → **接收端的空洞上报逻辑有问题**；
- 若 `recv_ooo` 本身就很小 → 说明对端真的没收到洞后面的帧，超时重传是唯一办法，
  快重传在这条链路上**不可能**起作用，别再往那个方向优化。

**仿真对照（确定性，工作区无行为改动版）**：

| 场景 | 接收端 recv_ooo / recv_far | 发送端 mack / hole |
|---|---|---|
| 干净链路 | 0 / 0 | 0 / 0 |
| iid 5% 丢包 | **1381 / 214** | 197 / 58 |
| 6 连丢突发 2% | **195 / 106** | 79 / 65 |

也就是说**仿真里上报是正常的**。真机 `mack = 0` 的原因**不是上报 bug**，而是**这条上行根本不产生乱序**：

```
重传 3499 次          ← counter_resend_rto
对端确认的重复帧 3810  ← counter_ack_dup（接收端自己的计数）⇒ 99% 的重传是白费的
本地判定白费 3418     ← counter_rto_spurious（97.7%）
counter_rto_stale  0  ← 没有"清滞后"型重传
```

⇒ **上行几乎没有真丢包**，所以既没有洞、也没有乱序可报 ✓。
（**更正**：早先"上行丢了约 11%"的读法是把**重复帧**当成了丢包 ✗ —— `txfull − rxfull` 的差额是重传副本，
不是丢失的帧。）

另外注意 `recv_far` 占比（5% 丢包时 214/1381 ≈ 15%）：**24 位 mask 表达不了的乱序帧是真实存在的**，
这部分永远报不回去，属于 ACK 格式的硬限制。

### 4.3 28% 重传率的真正来源：**我们自己把瓶颈队列灌满了**（2026-10 实测 + 代码级确认）

**实测（Apical，客户端上行，step20 那一轮）**：

| 观测 | 数值 | 含义 |
|---|---|---|
| 重传次数 `counter_resend_rto` | 3499 | — |
| 对端确认的重复帧 `counter_ack_dup` | **3810** | **99% 的重传对端早就收到了** |
| 加载后 RTT（rttm/rtts） | 100~234ms | 而好 AP 上同一份代码 `rttm` = 16ms |
| 早期 dump 的 RTT（空载基线） | ~10~30ms | ⇒ 多出来的 100~200ms 是**队列** |
| `swnd`（对端窗口） | 148 帧 | 允许在途 148 帧 |
| 链路 BDP | 285KB/s × 20ms ≈ **5 帧** | 允许值是 BDP 的 **~30 倍** |
| `wait_snd` | 钉在 252~255 | 应用被背压堵死 |

**代码级原因（两行就能看清）**：

```c
for (i = 0, p = ffrdp->send_list_head; i < (int32_t)ffrdp->cwnd && p; i++, p = p->next)  // cwnd 只限制"每次 update 走几个表项"
    if (ffrdp->swnd > 0) { ... }                                                          // 真正的闸门是 swnd
...
ffrdp->swnd = node->data[7];   // ← 每次 ACK 都被"对端接收窗口"直接覆盖，cwnd 从不参与
```

⇒ **`cwnd`/`ssthresh` 一直在维护，但对发送量毫无作用** ✗；唯一的刹车是"对端缓冲区大小"（148~256 帧），
而这条链路真正的 BDP 只有 ~5 帧 ⇒ **我们自愿把 AP 的队列灌满** ⇒ 队列排水时间 = RTT 里多出来的
100~200ms ⇒ **往返分布整体右移、`rtts+4rttd` 落到中位数** ⇒ 约 28% 的帧被误判超时 ✗。

**一个原因，三个症状**：

| 症状 | 归因 |
|---|---|
| 重传率 28%（① ✗） | 队列延迟把往返分布推过了 RTO |
| 延迟 100~234ms（② ✗） | 队列本身 |
| 吞吐/应用侧（③ ✗） | 重传吃掉空口时间 + `wait_snd` 被背压钉满 |

**⇒ 正确的信号是"延迟"而不是"丢包"**：丢包分不清限速与抖动（见 5.2），
而**延迟直接就是队列深度**，没有歧义。所以下一步是**延迟梯度控速**（Vegas 式：RTT 贴近最小值就涨，
RTT 抬头就收），而不是继续在"RTO 估计 / 按丢包 pacing"上打转。

### 4.3 RTO 的行为

- 实测 `rto` **恒等于** `clamp(rtts + 4 × rttd, 16, 2000)`：

  | log | rtts | rttd | rtts+4×rttd | 实测 rto |
  |---|---|---|---|---|
  | Apical baseline | 64 | 11 | 108 | 108 ✓ |
  | Apical S1 | 85 | 31 | 209 | 209 ✓ |
  | m2msw | 1 | 1 | 5 → clamp 16 | 16 ✓ |

- 也就是说 **每个非重传帧被确认时都会用 rtts/rttd 重算 rto**，退避造成的膨胀是**短暂的**
  → 所以 `counter_reach_maxrto` 一直很小（baseline 只有 7），"顶到 2 秒"不是主要病症；
- 但退避仍然值得修（见 S1）。
- 注意：`rto` 下限 16ms 在**移动端毫无意义**（Android/iOS 会把定时器合并到 100ms+），
  在快链路上反而制造伪超时——这会误导任何"按超时退让"的控制律（踩过，见 step6）。

### 4.4 `swnd` / `wait_snd` 是"信用"，不是在途

- `swnd` 由对端 ACK 里的接收窗口重置，每次 ACK 恢复一大笔（实测 `swnd` 148）；
- `wait_snd` 实测恒定 255（接收侧窗口），不反映在途量；
- 所以**不能**用它们当拥塞控制的输入。

### 4.5 计数器速查

| 计数器 | 含义 |
|---|---|
| `counter_send_1sttime` | 首次发送的帧数 |
| `counter_resend_rto` / `_fast` | 超时重传 / 快重传次数 |
| `counter_resend_ratio` | 重传占比（rto+fast）/ 首次；**打印时带上绝对数** `30.00% (6 / 20)` ⇒ 分母小的时候一眼看得见（见 10.4）|
| `counter_txfull` / `rxfull` | 完整帧的发送/接收条数（做丢包率核算用） |
| `counter_reach_maxrto` | rto 顶到 2000ms 上限的次数 |
| `counter_ack_recv` **(新)** | 收到的 ACK 帧数 |
| `counter_ack_mack` **(新)** | ACK 里带 mack 位（对端报了乱序）的次数 |
| `counter_ack_hole` **(新)** | ACK 报了真正空洞（最高已收帧下方有缺口）的次数 |
| `counter_recv_ooo` **(新)** | **接收端**：乱序到达的帧数（说明它下面有洞） |
| `counter_recv_far` **(新)** | **接收端**：乱序到达且距洞 > 23 帧 —— **24 位 ack mask 表达不了**，永远报不回去 |
| `counter_rto_backoff` **(新)** | rto 实际被乘 1.5 的次数 |
| `counter_timeout_evt` **(新)** | 发生了超时重传的 update 次数 |
| `counter_rto_stale` **(新)** | 超时重传的帧**已被对端上报过**（发送端清除滞后 → 纯浪费） |
| `counter_rto_behind` **(新)** | 超时重传的帧**对端从未上报**（洞后面卡住） |
| `elapsed` **(新)** | 从 init 起的秒数，用来核对两边 dump 是否对齐 |

### 5.4 三个信号家族都撞在同一堵墙上（为什么 step22 也塌了）

**先澄清仿真模型**：`tools/sim/simnet.c:121` 的 `jit` 是**每包均匀随机延迟 0~jit ms，且保持 FIFO 顺序、且该场景不限速（`cap=0`）⇒ 这条链路根本没有队列** ⇒
**任何"队列探测器"都不该对它反应** —— 而它确实没反应 ✓，塌掉的是**丢包反应** ✗。

**塌陷链条（已从数据 + 代码确认）**：
1. 抖动场景下 RTO 覆盖不了随机延迟 ⇒ 大量超时 ⇒ 重传率 20~30%（HEAD 也是 ✓）；
2. 我把"丢包 ⇒ `cwnd` 减半"接进了**真正的发送上限**（HEAD 里 `cwnd` 不约束发送 ⇒ 所以 HEAD 能活）；
3. 加上我的增长只有"每 RTT 一步" ⇒ 减半远快于增长 ⇒ `cwnd` 稳定塌在 1 ✗。

**⇒ 结论（与真机数据完全一致，且是同一个坑）**：真机上 **98% 的超时是被证明白费的**，
**在这种链路上做"丢包反应式窗口"，窗口必然塌** ✗。所以**任何窗口方案上线前，必须先让"被证明白费的超时"不再惩罚窗口**
（Eifel 语义：超时时记住 `cwnd`/`ssthresh`，一旦证明该次重传白费就**恢复**）。

**三个家族都失败于"信号无法区分两种成因"**：

| 家族 | 用的信号 | 被什么骗了 |
|---|---|---|
| pacing v1~v8 | 丢包率 | 限速 vs 抖动（5.2） ✗ |
| RTO 尾部估计 step13~21 | 超时/尾部 | 真丢包时为它延迟修复 ⇒ 净亏 ✗ |
| 延迟梯度 step22 | 延迟 | 本身没被骗 ✓，但**并存的丢包反应把窗口打死** ✗ |

**所以下一步的顺序是（两个独立改动，先易后难）**：
1. **step23（先做）**：Eifel 撤销——超时减半时保存旧窗口，证明白费后恢复 ⇒ 直接消灭"28% 伪超时把窗口打死"这个后果 ✓；
2. **step22 重做（后做）**：在 step23 之上恢复延迟梯度窗口 ⇒ 队列排空 ⇒ RTT 回到基线 ⇒ `rtts+4rttd` 自然够用 ⇒ 伪超时从源头消失 ✓✓。

### 5.5 step23（Eifel 撤销）单独有效 ✓；但与延迟窗口**合并后会互相打架** ✗

**step23 单独**（只改 Eifel 撤销这一处）：

| 场景族 | 结果 |
|---|---|
| 干净 d4 / d10 | 逐字相同 / 22.01→22.22 ✓ |

| 5% / 10% 丢包 | ≈ 持平（4.41 / 1.97）✓ |
| 整形器（队列型）场景 | **退化** ✗（1200/200：4.74→3.38；1200/64 重传 12%→24%） |

⇒ 单独不可交付 ✗，但**目的达成已被证明**：伪超时把窗口钉在 1 的后果可以消除 ✓✓。

**step22+step23 合并：不达验收 ✗**，失效方式是新的、必须记住：

| 版本 | 现象 |
|---|---|
| v1（Eifel 无条件恢复 + 纪元 1s） | **正反馈失控**：Eifel 的恢复把延迟刹车刚做的收缩撤销 ⇒ 目标场景重传 **772%** ✗✗ |
| v2（"排队时不许恢复" + 纪元 250ms） | 失控消失，但**判据自锁**：抖动场景 `cwnd` 塌到 1 **再也回不来** ✗（窗口塌 ⇒ RTT 采样太少 ⇒ 纪元极小值偏高 ⇒ 判据一直说"在排队" ⇒ 不许恢复 + 继续收缩）⇒ jit40 5.91→0.99、jit100 2.46→0.12 ✗✗ |

**教训：两个反馈环必须由同一个决策仲裁** ✗——丢包反应环与延迟反应环会互相抵消。缺一不可的两条：

1. **仲裁规则**：只有"没有我们自己的队列"（延迟贴基线）时，**丢包反应才生效**；一旦在排队，窗口只由延迟收缩；
2. **窗口必须有"测量下限"（4~8 帧）**：`cwnd=1` 是 stop-and-wait ⇒ **RTT 采样太少、快重传无从触发** ⇒ 判据自锁 + 链路饿死 ✗。这不是"窗口下限"意义上的 hack，而是"要测链路就必须有几个在途帧"。

**顺带一个新发现（对 ③ 有用）**：合并版在**无整形器**的丢包场景出现大幅正收益（5% 丢包 4.47→**8.11MB**、10% 丢包 1.84→**3.93MB**），
而重传率只从 7%/15% 升到 9%/19% ⇒ **HEAD 在这些场景有近一半链路是闲置的**（`cwnd` 被伪超时打到 1~4 ✗）。
说明"别让窗口塌"本身就值一倍吞吐，与优先级 ① 并不矛盾 ✓。

### 5.6 下一个改动（step24）= 仲裁式窗口 + 测量下限

单一改动，三条规则（都由 5.5 的失败直接推出）：

1. 发送窗口下限 4~8 帧（**测量下限**，保证 RTT 采样与快重传有素材）✓；
2. `cwnd_queueing == 0`（延迟贴基线）⇒ 丢包反应生效（含 Eifel 恢复）；`== 1` ⇒ 窗口只由延迟收缩、Eifel 不恢复 ✓；
3. 增长与收缩都按"每 RTT 一步"（同时间尺度），避免任何一边把另一边吃掉 ✓。

### 5.8 定位完成 ✓ —— 放大来自"超时不再收窗口"，而且它**推翻了我们对重传率指标的读法**

在 HEAD 上**只改一处**逐个跑（其中"超时不收窗口"那一版是变体 B）：

| 变体 | jit40 交付 / `rto` 计数 | 判定 |
|---|---|---|
| A：`swnd = MIN(对端窗口, cwnd)` | 5.00MB / **60** | **不是放大器** ✓（但各场景 -15%~-22% ✗：塌窗饿死） |
| B：**超时不收窗口**（其余同 HEAD） | **6.04MB（+2%）** / **1483（20 倍）** ✗ | **就是它** |
| B 的其它抖动 | jit60 4.19（+7%）、jit100 2.61（+6%），`rto` 886 / 713 | 同向 ✓ |

**机制（清楚了）**：HEAD 每遇到一次超时就把 `cwnd` 塌到 1 ⇒ 发送循环每 tick 只看 1 个表项 ⇒
**绝大多数"已过期"的帧根本没被巡查到** ⇒ `counter_resend_rto` 被"人为压低" ✗。
一旦窗口不再塌（变体 B），巡查走完整个表 ⇒ 所有过期帧都被重传 ⇒ 计数/重传率暴涨 **正是该有的行为**，
而且**交付量还涨了**（+2%~+7%）✓✓。

**⇒ 两条必须记住的结论**：

1. **`counter_resend_ratio` 不能单独当判据** ✗ —— 它可以被"饿死链路"刷低（HEAD 的 1.47% 就是这么来的 ✓）。
   判据必须与**交付量**一起看（例如"每交付 1MB 需要多少次重传"）。
   **这条同样适用于优先级 ①**：否则会优化出"什么也不发"的假最优 ✗。
2. **抖动场景下的重传本身就是浪费** ✓：变体 B 用 **+30% 的发送量**（重传 30% ✗）只换来 **+5% 的交付** ✗。
   与真机完全一致（98% 的重传被对端确认是重复帧 ✓）⇒ **窗口层面的任何改动只能改变"暴露多少"，消除不了浪费** ✗。

**⇒ 所以窗口这一族（step22~24）的失败不是"控制律不对"，而是"它治的不是这个病"** ✗。

### 5.9 下一步（step25）：用"对端重复上报"驱动**持久生效**的 RTO 下限

RTO 家族唯一的问题只是"抬 RTO 会延迟真修复" ✗；而现在有一个**干净、与重传计数无关**的判据：
**对端的重复帧上报**（真机 `counter_ack_dup` 3810 vs 重传 3499 ✓）⇒ 它直接回答"当前重传里有多少是白费的" ✓✓。
这正是 step17 想用、但当时被污染的那个信号 ✓。

**具体做法（与 step17/19/20 的关键区别）**：
- `rto = MAX(rtts + 4*rttd, floor)`，`floor` 只在"白费占比高"时抬、在"真修复占比抬头"时撤 ✓；
- **保证 floor 不被 ACK 的 RTO 重算抹掉** ✓ —— step17/19/20 全部是被这一条废掉的 ✗✓（见 5.3/5.4 的代码级分析 ✓）；
- 验收三条不变，但 ① 的判读**改用"每交付 1MB 的重传次数"** ✓（见 5.8 第 1 条）。

### 5.10 step25 第一版：**机制首次命中目标现象** ✓✓

**做法**：
1. 接收端把"收到重复帧"的个数（`dist < 0` ✓，即"我们已经有它了"）放进 **ACK 第 9 字节** 回传 ✓（对端不发这一字节时该字段为 0 ⇒ 下限永不动作 ⇒ 旧对端安全 ✓）；
2. 发送端按**每 64 次重传**为一个证据窗 ✓，算 `白费占比 = win_dup / win_need`：

### 5.1c 第二次上机暴露的两个问题（step18/19）

**step18（下限绑 `3×rtts`）失败** ✗：这条链路的 `rtts` 在 **1.7ms ↔ 162ms** 之间摆动（100 倍 ✗），
任意一次 `rtts` 走到低位，`MIN(rto_floor, 3×rtts)` 就把下限砸到个位数 ⇒ RTO 回到"太紧"的值 ⇒
**重传率又回到 40%/98% 白费** ✗。同时闸门（128 帧窗、无滞回）反复开关、每次关闭都把下限清零 ✗。

**step19 修正（三处）**：

1. 下限的回落边界改成绑 **`rtt_max`**（缓慢衰减的尾部，2~3 秒落地），既不锁死也不被瞬时低点砸碎；
2. 证据抬升**直接抬到 `rtt_max`**（不再被 `3×rtts` 限制）；
3. 闸门加**滞回**（<1% 开、>3% 才关）并把窗口设为 **256 帧**（≈ 真机 1 秒；512 帧时小场景永远不评估）。

**还有一个根因级修正（step19 的核心）**：`rtt_max` 只从"没超时过的帧"的确认里采样（Karn 规则），
**而真正慢的帧恰恰都超时了** ⇒ 尾部估计**系统性偏低** ⇒ RTO 永远追不上真正的尾巴 ✗。
而在"已证明白费"的那条路径上，我们**知道**这个确认回应的是更早那次发送 ⇒
**可以合法地量出它的真实往返 = 现在 − 原始发送时刻**，直接喂进 `rtt_max` ✓。
（这条是解开"98% 重传白费却修不掉"的钥匙 ✓。）

**注意**：仿真对这一版**不敏感** ✗ —— 仿真场景太短（<330 帧，闸门窗口都填不满）、
抖动又是对称的（`rtts + 4×rttd` 本就覆盖了尾），碰不到机制生效的条件。
**本机制的验证只能靠真机 A/B** ✗（这也是它的判据第一次必须走出仿真）。

### 5.1d 第三次上机：机械部分全部正确，但 RTO 卡在"中位数"上（step20）

**step19 的机械部分全部验证通过** ✓：

```
rto_floor 全程跟住 rtt_max（124/124、159/159、205/205、232/232 …）✓
counter_rto_floor 从 5 涨到 55（真在抬）✓
tail ok 稳定为 1（不再抖动）✓
98% 的重传仍被证明白费（4739 / 4848）✓
```

**但重传率仍是 30%** ✗，原因从数值一眼可见：客户端 `rto` = **187~330ms**，而往返分布就在
**200~300ms** ⇒ **RTO 正好卡在往返分布的中位数上**，约 30% 的帧落在晚侧被误判超时 ✗。

**为什么"尾部估计"这条路走不通（结构性原因）**：

- Karn 规则把**超时过的帧**排除在 RTT 采样之外 ⇒ 而慢帧恰恰都超时了 ⇒ `rtts/rttd/rtt_max` **一致偏低**；
- step19 加的"计时判据"又要求**确认在半个往返内回来** ⇒ 只能看到**边缘**那些伪超时 ⇒
  仍然够不到真正的尾巴。

**step20 的改法**：不再估计尾巴，**按可观测量闭环** —— 只要还有"被证明白费的重传"，就把
`rto_floor` **每个往返抬一次 ×1.25**（上限 1000ms），并用极慢的衰减（每 ack ×0.9995，≈5 秒半衰期）
把它拉回来。**这个环的不动点就是真正的尾巴** ✓（我们测不到它，但可以让 RTO 自己爬到那里）。
成本仍由闸门兜住：真丢包为主的链路闸门关闭，`rto_floor` 归零，行为回到 HEAD ✓。

**代价的取舍**：不动点可能落在 400~800ms ⇒ **重传/修复延迟变长** ✗。但这条链路真实丢包只有
~0.2% ⇒ 对媒体流影响很小 ✓；而 30% 的上行被重传吃掉是实打实的损失 ⇒ 值得换 ✓。

### 5.20 ⑦ 乱序上报：先量化（2026-10-10）—— 一处更正 + 纯诊断落地

**先更正我自己的一个错误判断** ✗：我先前说过 `counter_recv_ooo / recv_far` 存在"口径虚高"
（用的是"每次 update 内的批次计数"、不是线序）✗ —— **这个说法是错的** ✓。
复查代码：`recv_una` 每次 update 都从 `ffrdp->recv_seq` 起算 ✓，之后**只在 `dist == 0` 时推进** ✓，
而接收循环是按 `recvfrom` 的**返回顺序**走的 ✓ —— UDP 套接字保序 ✓ ⇒ 这个顺序**就是线序** ✓
⇒ `dist > 0` 确实等价于"比洞先到" ✓，`dist` 就是真实距离 ✓。
所以那两个计数器的语义是**对的** ✓，不需要"修口径" ✗；缺的只是**分布**，以及"报告有没有送到" ✓。

**为什么 `dist > 24` 的帧永远拿不到位**（决定"加宽有没有用"的那一步）：
掩码建立在 `recv_list` 上、参照是 `ffrdp->recv_seq` ✓，而后者只在**排空**（洞被填上）时前进 ✓；
距离变小的唯一途径就是"洞被填" ✓ —— 而洞一填，这帧就落到 `una` 之下、改成被**累计确认** ✓
⇒ 它**一个 mack bit 也拿不到** ✓ ⇒ 只能等发送端超时/快重传来修（在这里就是白重传 ✗）。
所以"距离落在哪一档"直接决定 64 位掩码能买到多少 ✓。

**本轮新增（纯诊断，行为零变化 ✓）**：

| 计数器 | 含义 |
|---|---|
| `counter_ooo_d1_24 / d25_64 / dgt64` | 乱序到达时"距洞多远"的三档；**三档之和恒等于 `recv_ooo`** ✓ |
| `counter_mack_bits_sent` / `_recv` | 本端发出的 mack 位数 / 从对端收到的 mack 位数（两端的差值 = **报告丢在路上** ✓）|
| `counter_ooo_64reach` | `(d1_24 + d25_64) / recv_ooo` ⇒ 64 位掩码能表达的占比 ✓ |

**自检（仿真 17 场景）**：三档之和 17/17 都等于 `recv_ooo` ✓；`far − (d25_64 + dgt64)`
恰好等于"`dist == 24`"的样本数 ✓（0/2/3/5/16 ✓，都很小 ✓）—— 顺带确认旧 `counter_recv_far`
的边界是 `dist > 23`，比掩码本身**严一帧** ✓（`dist 24` 其实装得下 ✓）。

**仿真给出的两个有用结论**（`TESTS="t_ack e2e" bash tools/sim/run.sh` ✓）：

- 干净链路 / 纯抖动等 12 个场景 `recv_ooo = 0` ✓（没有乱序 ⇒ 在那里加宽掩码毫无意义 ✓）；
- 有丢包 / 整形 / 重尾的场景里 `d25_64` 是**真的**：5% 丢包 `198/1381`（14%）✓、
  6 连丢 `103/195`（53%）✓、限速 1200/64 `196/251`（78%）✓、policer `4/74` ✓；
- **`dgt64` 在所有场景都是 0** ✓ —— 但**不要**由此推断"距离结构上 ≤ 64" ✗：仿真的在途上限本来就是 64，
  它根本量不到更大的距离 ✓。真机上这一档是**非零**的（8.1%，见 5.22）✗ ⇒ 那个推断已按真机数据更正 ✓；
- `mack_bits_sent` 与 `recv` 差 **5~10%** ✓（如 `2120 vs 2024`、`4176 vs 4161` ✓）⇒
  携带位图的 ACK **确实会丢** ✓，这个指标不是空转 ✓。

**顺手记一个自己踩的坑** ✗：第一版把新的汇总行写在 `ffrdp_free(c0/c1)` **之后** ✗
⇒ 读了已释放的上下文 ⇒ **段错误**（`e2e` 直接崩 ✓；`t_ack` 因为不打印那行，照样过 ✗ ⇒ 单测抓不到）。

### 5.21 "Ctrl+C / kill 都杀不掉"的现场：根因是 `select` + `scanf`（2026-10-10）—— 决定：不特殊处理 Ctrl+C

**现象**：真机上按 Ctrl+C，`verify` 汇总**打出来了** ✓，但进程**不退** ✗；再按多少次都一样 ✗；
`kill`（SIGTERM）同样无效 ✗，最后只能 `kill -9` ✗。**复现概率低** ✓。

**根因（已确定性复现）**：主循环等 stdin 用的是 `select` + `scanf("%s")` ✗ ——
`select` 只保证"**有字节可读**" ✓，而 `scanf("%s")` 要凑够一个**完整的、空白分隔的 token** ✗：
一行里只剩换行时（比如开跑前多按了一次回车 ✓），`select` 报可读 ✓、`scanf` 却永远等不到 token ✗
⇒ 主线程卡在 `scanf` 里 ✓，再也不去看退出标志 ✓。（终端是"行完整才可读" ✓，而一个纯换行本身就是"完整的一行" ✓
⇒ 正好踩中 ✓。）而 `signal()` 在 glibc 是 **BSD 语义（带 `SA_RESTART`）** ✗ ⇒ 信号到了只会把 `scanf`
**重启** ✗ ⇒ 连"EINTR 回来再检查标志"这条路也没有 ✓。
同一进程里的两个对等端线程看到标志后正常收尾 ✓（所以汇总打了 ✓），main 却永远走不到 `join` ⇒ 进程活着 ✓。

**确定性复现**（这就是那条 bug 的判据 ✓）：

```bash
{ printf '\n'; sleep 30; } | ./test_ffrdp --server --client    # 再发 SIGINT / SIGTERM
```

当时的行为：两种信号**都无效** ✗（`^C` 按多少次都没用 ✓）；而 stdin 是**干净管道**时正常退出 ✓
—— 这正是"复现概率低"的来源 ✓。

**决定（不做信号路径）**：为一个测试程序维护信号处理不值得 ✓ ⇒ **删掉整套 Ctrl+C 处理**
（`sigaction`、处理函数、`select`+`read` 都删掉 ✓），退出只认 `quit` / `exit`（或 stdin 结束 ✓）。
**Ctrl+C 会直接结束进程、看不到 verify 汇总** ✓ —— 这是**接受的正常结果** ✓；
要看汇总就用 `quit`/`exit` ✓（文档已写明，见 [`../readme.md`](../readme.md) 的 `test_ffrdp` 一节 ✓）。

顺带两点：

- 那个卡死是 **`select` + `scanf` 这个组合**造成的 ✓ ⇒ 去掉 `select` 之后它**自然消失** ✓，不需要别的修法 ✓；
- 过程中发现：stdout 被重定向时是**块缓冲** ✓ ⇒ 进程被 `kill -9` 时缓冲区里的汇总会整个丢掉 ✗
  （终端里看不到这个问题 ✓，因为终端是行缓冲 ✓）—— 现在用 `quit` 正常退出，`exit()` 会 flush ✓，
  所以"重定向存日志 + `quit`"能拿到完整汇总 ✓。

### 5.2 本质矛盾（关键，别再重复踩）

**"丢包 / 超时"这一个信号同时承载了"限速"和"抖动"两种含义**：

| 链路类型 | 降速后发生什么 | 判别器看到的 |
|---|---|---|
| 被限速 | 超出硬顶的部分不再被丢 → 吞吐**保持** | "限速" ✓ 该开 pacing |
| 抖动 | 在途帧变少 → 迟到超时也变少 → **丢包也下降**，吞吐本来就低于在发速率 | 看起来**同样像"限速"** ✗ 误判 |

所以**抖动链路上降速会让"丢包"变好、"吞吐"也看起来没掉**——任何基于丢包/超时的判别器都会被骗。
而**真实链路两者同时存在**（你实测 `rttd=31ms` 说明抖动不小，同时上行被硬限速 393KB/s），
因此不存在"一刀切"就对的开关。

**结论**：pacing 想救回的那部分（被限速丢包浪费掉的 ~17% 上行）是真实的，但要安全拿到它，需要的是
"**只削掉确切的那部分浪费**"（例如只按"实得速率 + 小余量"发，且绝不低于 cwnd 隐含速率），
而不是"按丢包信号整体降速"——这属于重新设计，不是调参。

> **因此建议先放下 pacing 这条线**，改攻证据更硬、且没有这个矛盾的方向：
> **空洞上报 / 补洞路径**（见 4.2 与第 7 节）。

**验收标准（三条同时满足才交付上机）**：

1. 目标场景 ≥ +100%；
2. 干净链路 0 损耗；
3. 随机丢包/抖动场景不退化。

## 8. 真实 internet 上普遍存在、值得处理的情况

### 8.1 三种瓶颈形态（决定了传输该怎么设计）

| 形态 | 特征 | 传输该怎么做 |
|---|---|---|
| **浅缓冲限速**（Apical 就是） | 超速率 → 直接丢包，**RTT 不涨** | pacing + 速率估计；"丢包出现但 RTT 不涨"是判别特征 |
| **深缓冲排队**（bufferbloat） | 超速率 → **RTT 暴涨**到几百 ms~秒，丢包来得很晚 | 必须**延迟梯度控速**；对音视频这是头号杀手 |
| **MAC 层重传**（WiFi） | 丢包被 L2 隐藏，但抖动/突发延迟很大 | 抖动容忍；**别把它当拥塞信号** |

### 8.2 硬限速不对称是常态，不是异常

- 家庭宽带上行天生是下行的 1/10（100/10、500/50、1000/100）→ **上行是瓶颈是默认情况**；
- 企业/园区/酒店 WiFi 按客户端限速（2-10Mbps）是标配（`m2msw` 这种托管网络几乎一定有整形器）；
- 移动/固定无线（LTE/5G/WISP）：上行稀缺 + 调度 + 令牌桶；
- VPN：隧道端点自己的限速经常是最弱一环。

### 8.3 其他值得处理的

**A. 链路特征**

1. **随机丢包 ≠ 拥塞**（最重要）：随机丢包下调窗/降速都是净亏，收益为零，只能靠 FEC；
2. **突发丢包**：5G/WiFi 一次 airtime 事件丢一串，修复必须按"串"做（step7 就是被这个否掉的）；
3. **乱序被误判为丢包**：需要乱序容忍 + 乱序上报（见 4.2）；
4. **bufferbloat**：需要延迟梯度控速，而不是等丢包；
5. **RTT 尖峰/停顿**：移动端 RRC 空闲、上行调度（没流量就不给授权）、WiFi 省电（客户端睡 100-300ms）。

**B. 路径与协议（VPN / P2P 尤其关键）**

6. **MTU / 隧道封装**：PMTUD 常被防火墙黑洞化；VPN 下 1280 字节载荷可能超隧道 MTU → 每包静默丢。
   建议 MSS 钳制 + 保守初始 MTU；
7. **NAT/CGNAT**：对称 NAT、UDP 空闲超时（30s~几分钟）、打洞失败要能回退中继；
8. **5 元组变化**：NAT rebinding、WiFi 漫游、蜂窝切换 → 需要连接迁移（换 5 元组继续，而非重连）；
9. **运营商对 UDP 的限速/去优先级/屏蔽** → 要有 TCP/TLS 回退路径；
10. **计时器粒度**：Android/iOS 定时器合并到 100ms+，依赖毫秒精度的 RTO 会失效。

**C. 工程与测量**

11. **公平性**：不理会丢包的 UDP flood 会被运营商整形、并饿死同链路的 TCP
    → 这也是必须"对丢包保持响应"的原因；
12. **测量方法**：同一 AP 重传率能在 17.78%~33% 之间漂移，所以参数必须自适应，
    基准必须看分位数/同一轮多 dump，不能靠单次运行。

### 8.4 对照设计目标的优先级

| 目标 | 第一优先级 |
|---|---|
| 局域网音视频 | LAN 本身不难，风险是**自伤**（实测总量 10.6Mbps vs 链路 ~11.5Mbps，已在悬崖边）：WiFi AP 缓冲一样会溢出，pacing/airtime 意识在 LAN 也需要 |
| interent P2P 音视频（低延迟） | ① 不在瓶颈排队（pacing）② **视频帧按截止时间丢弃而不是排队等**（部分可靠传输）③ bufferbloat 用延迟梯度控速 |
| internet P2P（带宽稳定） | **FEC** + 有截止时间的重传，而不是继续折腾 `cwnd` |
| VPN | MTU/PMTUD、连接迁移、NAT 超时；**隧道端点的上行**通常才是真瓶颈 |

### 10.4 诊断字段修订：`counter_resend_waste` 的口径（2026-10-10）

**起因**：`--send_speed=1`（客户端限速 1KB/s）那一轮，dump 打出

```
total_send, total_recv: 0.04MB, 37.91MB
counter_resend_ratio: 7.50%
counter_resend_waste: 300.00%      ← 看着像"白费率 300%"，其实不是 ✗
rto_floor, waste%   : 0, 100.0%
```

**查出来的原因** ✗：`counter_resend_waste` 的实现是"重传次数 ÷ `counter_txfull`"，
而 `counter_txfull` **只统计长度恰好等于 MSS 的数据帧**
（`ffrdp.c`：`switch (frame->size - smss) { case 4: txfull; default: txshort; }`）。
`--send_speed=1` 时令牌只有 1024 字节/周期 ⇒ 每包都被裁到 < 1280 ⇒ **全是 short 帧**
（dump 里 `counter_txfull 0`、`counter_txshort 43` 正好印证）⇒ 分母为 0 被 `MAX(..., 1)` 兜成 1
⇒ `3 / 1 = 300%` ✗。⇒ 它和"白不白费"毫无关系 ✗（只是名字叫 waste ✗）。

**真正的白费率**在同一轮的 `rto_floor, waste%` 里 = `counter_ack_dup` ÷ 重传总数 = 3/3 = **100%** ✓：
40 秒只发了 40 帧（1 帧/秒），而 `rto = rtts + 4·rttd = 19ms` 正好贴着这条路的往返
（`rtt_min 7ms`、`rtts 11ms`），同时对端在以 ~970KB/s 跑 ⇒ 我们那**稀有的**一帧的 ACK 很容易晚过
19ms ⇒ 伪超时 ⇒ 重传被对端认出"我早有了" ⇒ 100% ✓。与"**帧是迟到，不是丢了**"这条老结论一致 ✓，
只是总量小到可忽略（3 次 / 40 秒 ✓）。

顺带记一个**已知小缺口** ✗（本次不处理）：发送很稀时（1 帧/秒），证据窗口永远攒不满
`FFRDP_WASTE_MIN = 16` 次重传 ⇒ `rto_floor` 不会被调节 ✓
（dump 里 `rto_floor 0` / `probes 0` 印证 ✓）；代价极小 ✓，要处理得走"仿真 → 真机"流程 ✓。

**同一个"分母太小"的毛病，`counter_resend_ratio` 上也有（而且方向相反：它是被刷高）**：

限速 1KB/s 时它按 60% → 30% → 20% → 15% "一路变好" ✗，其实**分子没动**：

| 时刻 | 分子（重传）| 分母（累计首发）| ratio | 说明 |
|---|---|---|---|
| 10s | **6** | 10 | 60.00% | 就是冷启动那 6 次 ✓ |

### 10.5 test.c 加消息校验（framing + seq + crc32）；并让 ffrdp_send 真正原子（2026-10-10）

**动机**：`test.c` 原来只收发 + dump，从不检查"数据到底有没有丢/坏" ✗
⇒ 加校验之后才知道协议交付是否真的可靠 ✓。

**先查清两个 API 语义**（这决定方案能不能成立）：

1. `ffrdp_recv()` 是**有序可靠字节流**、**没有消息边界** ✗
   （`ret = MIN(len, recv_size)` + `ringbuf_read` 按字节搬 ✓）⇒ 必须自带**定长头**才能解析 ✓；
   接收侧缓冲装不下时是"**等待**"而不是丢弃 ✓（`size <= 剩余空间` 的守卫 ✓），
   所以"多次 recv 拼起来 = 发送的字节流" ✓，但**不能**假设一次 recv 拿到整条消息 ✗
   （接收缓冲 128 帧 ≈186KB，而一次 `ffrdp_send` 上限约 256 帧 ⇒ 消息可以比缓冲大 ✓，
   真正保证不丢的是**流控** ✓）；
2. `ffrdp_send()` 原来**不总是原子** ✗：入口预检查（队列满 / 未连接）是"整包拒绝" ✓，
   但 `frame_node_new()` 分配失败时 `break` ⇒ 返回 `0 < ret < len` ✗ ⇒ 调用方**无法安全重发**
   （已吞掉的那部分会重复出现在流里 ✗）。**先把它修掉** ✓：
   改成"**先把这个调用要用的帧全部申请好，再开始写入**" ✓（任何一次申请失败 ⇒ 释放已申请的、
   返回 -1 ✓）⇒ 契约变成 **"要么整条接受（返回 len），要么什么都没接受（返回 -1）"** ✓
   （`ffrdp.h` 注释已写明 ✓）。

**test.c 的改动**：

```
消息格式：[4B 总长 len][4B seq][payload...][4B crc32]      crc32 覆盖 len + seq + payload
```

- 发送：只有 `ret == len` 才 `seq++` ✓；`ret == -1`（队列满，正常背压）⇒ **原样重试同一条**
  （绝不重新生成 ✗）；出现 `0 < ret < len` ⇒ 打 `partial send` 告警并计数 ✓（send 原子后不该出现 ✓）；
- 接收：256KB 累积缓冲 + 解析状态机 ✓；逐条校验 **len 合法性 / crc32 / seq 连续性** ✓；
  长度非法 ⇒ 报"流失步"并停止解析 ✓（一旦失步无法可靠恢复 ✓）；crc 错 ⇒ **跳过这一条继续** ✓
  （长度可信 ⇒ 边界仍对齐 ✓）；
- 日志限流：每类错误最多逐条打 3 次 ✓，其余只计数 ✓；退出打印 `verify:` 汇总 + `OK / 未通过` ✓；
- 限速与消息的配合：消息不能裁剪（原子 ✓），所以改成按剩余额度**选**这一条消息的大小 ✓；
  额度不够装最小一条 ⇒ 这一轮不发 ✓。

**踩到的坑（值得记）** ✗：第一版把"额度用完、这一轮不生成消息"写成了
`msg_len = msg_build(...)` 返回 **-1** ✗，而 -1 **既不为 0**（不会重新生成 ✗）**又不 > 0**（不会发送 ✗）
⇒ **发送永久停摆** ✗。是"限速档的速率检查"抓到的 ✓：`--send_speed=100` 只发出**恰好一个周期**的
102396 B ✓、然后就不动了 ✓。改成用 `room` 标志显式跳过 ✓，并把 `msg_len < 0` 兜成 0 ✓。
**教训**：速度类改动必须有"**速率是否还贴着目标**"的断言 ✓ —— 只看"没报错"是发现不了的 ✗。

**验证**（本机自测；每次运行都做 seq/crc 校验 ✓）：

| 场景 | 结果 |
|---|---|
| 不限速 16s | 收 **190538 条 / 1.57GB**，`seq_gap 0 / crc_err 0 / len_err 0 / partial_err 0` ✓；速率 ~96MB/s（这是测试程序自身 CPU 的上限 ✓，真实链路 ~1MB/s ⇒ 无关 ✓）|
| `--send_speed=100` | **100.37KB/s** ✓，285 条 / 1.63MB，零错误 ✓ |
| `--send_speed=1` | **1.00KB/s** ✓，82 条 / 16KB，零错误 ✓（`counter_send_failed 55` ⇒ 背压重试路径被真实走过 ✓）|
| 反向验证 a（故意改坏 crc）| 两侧都报 `VERIFY ... crc mismatch` ✓ |
| 反向验证 b（故意 `seq += 2`）| 两侧都报 `VERIFY ... seq gap` ✓ |

仿真：`ffrdp_send` 原子化后 **21/21 场景逐字相同** ✓、`leaked=0` ✓（只改了分配顺序 ✓）。

**真机上暴露的第一个缺陷（同一轮修掉）** ✗：`Ctrl+C` 退出时**看不到 verify 汇总** ——
因为汇总是在线程退出循环时打的 ✓，而 `SIGINT` 默认直接杀进程 ✗，线程没机会收尾 ✓。
修法：`g_exit` 改成 `volatile sig_atomic_t` ✓ + 捕获 `SIGINT/SIGTERM` 只置标志 ✓
（信号处理里唯一安全的动作 ✓）；`main` 原来死等在阻塞的 `scanf` 上 ✗（默认会被重启 ✗），
改成**带 100ms 超时地等 stdin**（POSIX `select` ✓）⇒ 收到信号后立刻去 `join` ✓，线程收尾并打印 ✓。
验证：`kill -INT` / `kill -TERM` 各跑一遍，都打出 4 行 `verify` ✓（两侧各 2 行 ✓），
`quit` 路径无回归 ✓；`stdin` 关闭（Ctrl+D / 管道结束）也会退出 ✓。

## 11. 选型、边界与延迟尾巴（2026-10-10 讨论归档）

### 11.1 与其他 UDP ARQ 的对照（设计层面判断，**非同机跑分** ✗）

| 维度 | **ffrdp** | **KCP** | **QUIC** | **UDX 类** |
|---|---|---|---|---|
| 拥塞控制 | 延迟探测型**在途闸门**（自研 ✓；"被限速 + 抖动"链路上实测有效 ✓）；**不因随机丢包退让**（设计选择 ✓）| 基本没有（靠外部限速）| CUBIC/BBR ✓ 成熟、对互联网友好 ✓ | 自带 BBR 类 |
| 重传策略 | **证据驱动**：对端重复上报抬 RTO 下限 + 快重传纪律 ⇒ 实测重传 28% → **0.1~0.3%** ✓、稳态 **0 次/秒** ✓ | **激进**（快重传 N=2）⇒ 低延迟但费带宽 | TCP 式 + 尾部丢失探测 | 类似 QUIC |
| 可靠性模型 | 全可靠有序流（**无部分可靠** ✗）| 可靠流（可调）| 流 + **不可靠 DATAGRAM** ✓ | 可靠流 |
| 头部开销 | **极小**：4B 帧头（+可选 1B）✓ | ~24B/包 | ~20~40B + 握手/TLS | 中等 |
| 加密/握手 | 可选 AES，**无握手**（应用自管）| 无 | **内置 TLS1.3** ✓ | 无 |
| 连接迁移 | ✗ | ✗ | ✓ | 部分 |
| 生态/验证规模 | 自研单文件 ✓、**实测证据扎实** ✓，**但无大规模验证** ✗ | 老牌、面广 | 标准 + 各大厂 + 内核 | 特定 P2P 生态 |

**读法**：不是"谁更强"，而是"**谁的失效模式你能接受**"。ffrdp 领先的是**别家一般不优化**的两个维度：
**极小开销** ✓ 与 **"自伤队列"治理** ✓（负载 ping 220ms → 18~38ms ✓）；落后的是**拥塞控制成熟度 / 迁移 /
加密握手 / 部分可靠 / 生态** ✓（这几项 QUIC 全面领先，KCP 在"激进低延迟"上更极端）。

### 11.2 裸 UDP vs ffrdp 做 VPN 底层

判据（VPN 底层需要什么）：

| VPN 的需要 | 裸 UDP | ffrdp 现形态（可靠有序流）|
|---|---|---|
| 不做队头阻塞 | ✓ | **✗**（一个帧丢了，内层所有流一起等）|
| 不做有序交付（IP 本就无序）| ✓ | **✗**（多一层没必要的有序性）|
| 外层不重传（内层 TCP/UDP 自己处理）| ✓ | **✗**（重复劳动 + 把丢包对内层藏起来）|
| 报文边界（一包 = 一个 IP 包）| ✓ | ✗（字节流，要自己加长度前缀）|
| **排队/拥塞控制** | **✗ 完全没有** | **✓✓（v1.1.0 的全部价值：实测 220ms → 18~38ms）** |
| MTU | 应用自己分片 | 库内按 `smss` 分帧 |
| 公平/不被限速 | 内层 TCP 会退让 ⇒ 大致公平；但**内层 UDP 流不退让** ✗ | 由闸门兜住 ⇒ 行为良好 |

**可靠有序流对 VPN 的两个结构性代价**（重要 ✓）：

1. **队头阻塞**：一个帧丢了 ⇒ 内层所有流一起等它修好；
2. **内层看不见丢包**：内层 TCP 把隧道当"不丢包的管子" ⇒ 拥塞控制失真（靠 `ffrdp_send` 满队列返回 −1 的
   阻塞式背压缓解 ✓，但没有消除 ✓）。

⇒ **结论**：不是"谁替代谁"，而是"**UDP 的数据报语义 + ffrdp 的排队控制**"这个交集 ✓ ——
即给 ffrdp 加一个**"不可靠报文模式"**（帧仍是数据报：不做有序交付、不重传；但保留在途闸门 + 探测 + QUERY keepalive），
**去掉 ARQ/有序那一层**。这一处改动同时服务 **VPN 底层 + 音视频**（与"截止时间/部分可靠"是同一处代码）✓。

### 11.3 延迟尾巴：在途扫描的实测结果（工具 `tools/inflight-sweep.sh` ✓）

方法：把 `FFRDP_INFLIGHT_MAX` 钉住、`FFRDP_PROBE_ENABLE` 置 0，各跑 300 s（在被限速的那一端 ✓），
读 `rtts − rtt_min`（排队 ✓）与 `confirmed rate`（速率，不能掉 ✓）：

| cap | rtt_min | rtts | **排队 = rtts − rtt_min** | 确认速率 | 每MB重传 |
|---|---|---|---|---|---|
| probe（现状：探测开、默认 64）| 5 | 18 | **13 ms** | 229 f/s | 5.4 |
| 2 | 3 | 14 | **11 ms** | 229 f/s | 0.6 |
| 3 | 4 | 14 | **10 ms** | 230 f/s | 2.2 |
| ~~4~~ | — | — | **无效 ✗** | — | — |
| 6 | 4 | 22 | 18 ms | 228 f/s | 2.0 |
| 8 | 3 | 31 | **28 ms** | 228 f/s | 0.6 |

**结论（本次实测 ✓）**：

1. **速率对窗口完全不敏感** ✓（2~8 帧全是 228~230 f/s ⇒ **2 帧就足够喂满这条链路** ✓）；
2. **排队延迟随窗口单调上升** ✓（cap 2~3 ⇒ 10~11ms；cap 8 ⇒ 28ms）；
   ⚠️ **更正（同日复查代码后 ✓）**：那两档**其实不是 2 帧和 3 帧** ✗ —— 刹车处写的是
   `MAX(inflight_max, 4u)` ⇒ `2`、`3` 都被**静默夹成 4** ✓ ⇒ 它们量到的 10~11ms 就是 **4 帧**的排队 ✓，
   **"低于 4 帧更好"从来没有被观测到** ✓（也说明这条曲线在 4 帧处就到头了 ✓）；
3. **真正的目标就是 4 帧** ✓：探测现在停在 ~5 帧（成因见 11.5 ✗）⇒ 比 4 帧**多排约 4ms**
   （这一步的胜负手正是 `rtts` **18 → 14ms** ✓）⇒ **把探测的"保留判据"从相对改成绝对** ✓，
   收益约 **4ms / 约 20% 的典型延迟** ✓，且**没有速率代价** ✓（2~8 帧速率全平 ✓）；
4. ⚠️ `cap=4` 那一档**作废** ✗：从 240 s 起对端/链路出问题（确认速率 229 → 7~12 f/s、`swnd` 塌到 0~3、
   `rtts` 涨到 500~650ms）⇒ 与 cap=4 无关 ✓；需要时重跑 ✓（结论不依赖它：2/3/6/8 已把曲线包住 ✓）；
5. 备注：每MB重传在几档之间波动大（0.6~5.4）⇒ **主要来自开头那段收敛期** ✓（见 5.22 的趋势 ✓），
   不宜用单档 5 分钟的数值互相比较 ✓。

## 12. 端口上的敌意输入：健壮性与两个远程崩溃（2026-10-11）

**问题（项目方原话）**：ffrdp server bind 了端口，任何人往这个端口发非法数据，至少要保证进程不崩。

**结论：修之前做不到** ✗ —— **一个 1 字节的包就能让服务器进程死掉**，而且不需要会话、不需要握手
（服务端收到第一个包就会把这个源当作对端，之后照样处理它）。

### 12.1 根因：帧长被当成算术输入

`ffrdp_recv_data_frame()` 用**收到的包长**算两样东西：**`rmss`**（对端载荷大小，`FULL ⇒ 帧长−4`、
FEC 类型 `⇒ 帧长−6`）和 **`frame_payload_size()`**（`帧长−4−(是否 FEC)`）。而 `rmss` 之后被当作
**除数**（`recv_wnd = … / rmss`）与**拷贝长度**（把载荷写进接收环形缓冲时）用。

| 一个包 | 算术 | 结果 |
|---|---|---|
| **1 字节 `00`**（FULL）| `rmss = 1−4` **下溢**；载荷 `1−4 = −3` | 拷贝长度成了 `0xFFFFFFFD` ⇒ `memcpy` 约 40 亿字节 ⇒ **SIGSEGV** |
| **4 字节 `00 00 00 00`**（FULL，序号 0 正好"按序"）| `rmss = 0` | `recv_wnd = X / 0` ⇒ **SIGFPE（除零）** |
| 4 字节 `02 00 00 00`（FEC2）| `rmss = 4−6` 下溢；载荷 `−2` | 同第一行 ⇒ **SIGSEGV** |

**实测（手工，每样只发一个包）** ✓：`exit=139 (signal 11)` / `exit=136 (signal 8)` / `exit=139`；
对照组（8 字节的正常 ACK）**活着** ⇒ 不是"发什么都会崩"，而是**长度算术**被喂了非法值。

### 12.2 第三处：乱序队列没有界（远程耗尽内存）

`dist >= 0` 的帧一律入队，而"洞"永远可以不被填 ⇒ **一个数据报换一个约 1.5KB 的节点**，
且插入是 O(n)（既耗内存又耗 CPU）。实测（修复前的仿真）：**2000 个包 ⇒ 2000 个节点**（线性）。

### 12.3 修复（三处，都很小）

1. **在门口校验长度**（`ffrdp_recv_data_frame`）：`FULL` 必须 `> 4`、FEC 类型必须 `> 6`
   （"至少要有一个载荷字节"）⇒ `rmss >= 1`、载荷 `> 0`，根因消除；
2. **两处兜底**：`recv_wnd` 的除法加 `rmss ?`；拷贝前加 `size > 0`（万一日后又有路径喂进非法长度）；
3. **入队加界**：`dist >= FFRDP_RECV_QUEUE_MAX (256)` 直接丢弃 —— 依据是**我们在每个 ACK 里**把窗口
   （1 字节 ⇒ ≤ 255 帧）交给对端，守规矩的对端不可能更远。实测：**4000 个包 ⇒ 255 个节点**（不再增长）。

顺带加两个可观测计数：`counter_rx_bad`（长度不可能）、`counter_recv_drop`（太靠前）——
正常运行两者都是 0，非 0 就说明有人在探端口。

### 12.4 工具：一内一外

| 工具 | 做什么 | 怎么跑 |
|---|---|---|

## 13. lowlevel 分层：接口定为 tx + rx + timer（2026-10-11）

v2.0.0 要把协议层和 socket 解耦，底层不一定是 UDP，于是先做 lowlevel 这一层（`lowlevel.h` +
`lowlevel-udp.c`），并把它定义成 **三个东西**：发（tx）、收（rx）、时间（timer）。

### 13.1 为什么是这三个

- 协议层需要知道的事只有三件：能发一帧吗 ✓、收到一帧了吗 ✓、时间到了吗 ✓ —— 这就是全部的
  "与传输无关"的部分 ✓；其余（RTO、重传、探测、pacing）都建立在这三件事上 ✓。
- **线程属于概念的一部分** ✓，不是实现细节：lowlevel 自带一个工作线程，把事件**推**给上层 ✓
  ⇒ 协议被低层驱动，而不是被应用主循环驱动 ✓（今天 `ffrdp_update()` 必须被应用周期性调用，
  而且它内部直接 `select` 在自己的 udp_fd 上 —— 见 `ffrdp.c` 的 `ffrdp_sleep()` ✓）。
  上层 API 因此才能做成 socket 那样（send/recv ✓），这也是选 B 的原因 ✓。
- **timer 不叫 wake** ✗：对 uart 说"wake uart"没有意义 ✓。换成 timer 的语言，"立刻"就是
  "**期限已过**" ✓ ⇒ 一个函数同时表达三件事：设期限 ✓、立刻催一次 ✓、关掉（`0` = 不用叫我 ✓）。
- **recv 用回调而不是 recv 接口** ✓：数据到达就在协议线程上 ⇒ 天然背压（读一帧 → 回调 →
  再读下一帧 ✓）；哪天要 pull 语义，在中间层加个队列即可 ✓，不锁死 ✓。

### 13.2 语义（写在 `lowlevel.h` 里）

| 项 | 语义 |
|---|---|
| `timer(fl, deadline_ms)` | **绝对**毫秒 ✓，与 `ffrdp_get_timestamp32_ms()` 同一时间基 ✓ |
| `deadline_ms == 0` | 没有期限 ⇒ 睡到有数据为止 ✓（空闲时不影响 CPU 唤醒 ✓）|
| `addr_parse(fl, "1.2.3.4:5678", &addr)` | **configured peer 与 learnt peer 同构** ✓：把对端的文本形式变成 `send` 能用的 addr ✓ —— 因为从 RECV 拿到的 addr 只能"回发" ✓，而**还没开过口的对端必须有人先给它起个名字** ✓（客户端发第一帧就是这种情况 ✓）；实现复用收包路径同一个编码函数 ✓ ⇒ 两种来源逐位相同 ✓ |

| 期限已过 | **立刻**回调一次 ✓（这就是"催发"的唯一写法 ✓）|
| 重复调用 | **覆盖式** ✓（替换上一次，不是累加 ✓）|
| 调用线程 | **任意线程可调** ✓（上层从应用线程催发就是靠它 ✓）|
| 回调 | 一帧一回调 ✓、不嵌套 ✓、不阻塞 ✓（它就是收包路径 ✓）、回调内可调 `send`/`timer` ✓ |
| `exit` | **不得在回调里调用** ✗（它会 join 当前线程 ⇒ 自死锁 ✓）|
| `send` 返回 −1 | 就是"这一帧没收下" ✓ ⇒ 丢掉、由上层重传 ✓ |
| init 返回后第一帧可能丢 / 首个 `send` 可能 −1 | **允许** ✓（丢包本来就允许 ✓）—— 不为这两条做设计 ✓ |

### 13.3 实现（`lowlevel-udp.c`）

## 14. 收发加等待时间（timeout_ms）；一次被实测否掉的顺序（2026-10-11）

v2.0.0 要让应用不再需要"主循环里调 ffrdp_update"，第一步是给收发加上等待语义，并让**等待的那一方**
承担"跑协议"的责任。接口变成：

```c
int ffrdp_send(void *ctxt, char *buf, int len, int timeout_ms);
int ffrdp_recv(void *ctxt, char *buf, int len, int timeout_ms);
```

`timeout_ms` = 0 时**逐字保留旧行为**（不等待、`recv` 有数据就返回、`send` 原子），所以既有调用方
加一个 `, 0` 就是完全等价；>0 = 最多等这么多毫秒（期间协议照常跑）；<0 = 等到有 / 能接受为止。

### 14.1 被否掉的一步：先删 ffrdp_update，再换驱动者

原计划分两步：先删掉公共的 `ffrdp_update`、让收发顺带驱动协议，再把 tick 交给 lowlevel 的工作线程。
**实测第一步就不成立** ✓✗：

| 本机回环 `test_ffrdp --server --client`（15 秒）| 服务端发出 | 吞吐 | confirmed rate |
|---|---|---|---|
| HEAD（旧接口，主循环每轮 update）| 873 MB | **55.5 MB/s** | 50636 帧/s |
| 删掉 update、由 recv 顺带驱动 | 183 MB | **11.6 MB/s** ✗ | 9299 帧/s ✗ |

根因是结构性的 ✓：`recv` 只在"应用自己的接收环空着"时才让协议转一圈 ⇒ **应用一积压，协议就被
饿住** ✗ ⇒ ack/重传变慢 ⇒ 吞吐掉 5 倍。`counter_send_failed` 全程为 0 ✓（应用从没被拒 ✓），
说明这不是背压，而是**驱动者缺位** ✓。

⇒ 结论 ✓：**"应用不再 tick" 与 "由 lowlevel 线程 tick" 是同一件事** ✓ —— 删掉 `ffrdp_update`
的前提是先把驱动者交给别人 ✓。所以 `ffrdp_update` 这一步**保留** ✓（`ffrdp.h` 里写明它是过渡态 ✓），
等下一步把 tick 移交给 lowlevel 的 `RECV` / `TIMER` 回调时一起删 ✓（那一步还要同时把 `tools/sim`
的接缝从"假 socket"改成"假 lowlevel" ✓）。

### 14.2 等待语义本身也要看阶段

同一次实验里还量到：在"协议仍挂在应用线程上"这一步，`ffrdp_recv` 传 >0 会把应用自己的循环节拍
压到 10ms 一档 ✓ —— 回环吞吐 35.5 → 13.0 MB/s ✓（两次运行内部自比 ✓，都是同一个优化级别 ✓）。
所以 `test.c` 这一步两个调用都传 0 ✓；应用侧的等待留到协议有自己的线程之后再用 ✓。

## 15. 发送改成"应用排队、协议成帧"（2026-10-11，迈向上层边界的第一步）

要把协议搬到 lowlevel 的工作线程上，先得把**应用与协议之间的界面**做出来，否则两条线程会同时碰
`cur_new_node` / `send_seq` / 加密密钥这些协议状态。这一步（记为 C1）只做界面，**不动驱动者**：
`ffrdp_update` 还在，协议仍由应用线程按时驱动 ⇒ 因此仍能用最强的判据（差分仿真逐字相同）来验 ✓。

### 15.1 改动

* `ffrdp_send` 不再就地成帧，只把消息（**4 字节长度 + 数据**）放进一个按 `smss` 分配的队列
  （容量 `FFRDP_MAX_WAITSND * (smss + 4)`，与旧版"最多 256 帧在途"同一量级）；
* 成帧由协议在 `ffrdp_update` 开头调用 `ffrdp_drain_tx()` 完成；原 send 的主体**一字未改**，
  只是改名 `ffrdp_frame_message()`；
* **受理判据（帧数上限）留在发送入口**，逐字照旧 —— 这一条是踩过才明白的，见 15.2。

为什么这样切：成帧要碰的全是协议状态，让应用线程直接写它，等于把半个协议搬到应用线程上；
放进队列之后，协议侧只被一个执行者碰，下一步切换驱动者时，这个队列就是两条线程之间**唯一**的界面
（那时给它加一把锁、并把 `wait_snd` 的读放进锁里）。

### 15.2 中途踩到一次，也正好说明判据在起作用 ✓

第一版把"帧数上限"的判据从入口挪到了出队处（因为"应用只看队列、不碰协议"更自然）✗ —— 差分仿真
立刻报出 **16 个块有差异** ✗，差异全是 `wait=` / `fail=` 这类**受理口径**的数字 ✓。判据挪回入口后
**逐字相同** ✓。

⇒ 这一步的纪律 ✓：**可以改变"数据放在哪里"，不能改变"谁会被拒"** ✓。受理口径一变，线上时序就变，
差分仿真就会（也应该）立刻抓住 ✓。

### 15.3 验证

* 差分仿真 **20 个块**（17 个 e2e 场景 + t_rto + t_ack + t_fuzz）两侧**逐字相同** ✓，0 差异 ✓；

## 16. C2 第一步：接收段抽成函数（2026-10-11，纯搬迁）

把协议搬到 lowlevel 的工作线程上（C2）有一个前提：**接收路径必须能被"一帧一次"地调用** ✗ ——
而它现在只能从 `ffrdp_update` 内部的 `recvfrom` 循环里**整批**处理 ✓。这一步只做搬迁 ✓：

* `ffrdp_on_frame(ffrdp, node, len, b)` ✓ —— 一帧的解析与记账（原循环体逐字搬移 ✓）；
  节点仍由调用方分配（保持"复用同一个节点"的旧写法 ✓），返回值表示它是否已被乱序队列接管 ✓；
* `ffrdp_apply_acks(ffrdp, b, dstaddr)` ✓ —— 应答 + 把收到的 ack 应用到发送表（原来"整批一次"那段 ✓）；
* 跨帧累积量（`recv_una` / `send_una` / `send_mack` / `got_data` / `got_query` ✓）搬进
  `FFRDP_RX_BATCH` ✓，由调用方持有 ⇒ 旧调用方一批一份 ✓、将来的 RECV 回调一帧一份 ✓。

搬家是**脚本按锚点原样做的**（不手抄 ✓ —— 避免转录差异 ✓），唯一的编码改动是 `ret` → `len`
（帧长现在是传输层交过来的长度 ✓，不再是 `recvfrom` 的返回值 ✓）。

⚠️ 这一步查清了一件对 C2 很重要的事 ✓：**[B] 段是"批量处理器"** ✗ —— 逐帧解析 ✓，但**应答（ack）与
发送表清理是整批做一次** ✓（`send_una` / `send_mack` 跨帧累积 ✓）。⇒ 换成"一帧一回调"之后，
**ack 的批量会变成一帧一个** ✗ ⇒ 线上时序会有真实（且可解释）的变化 ✓ —— 下次切换驱动者时，
差分仿真在这点上**应当**出现差异 ✓，而不是"必须逐字相同" ✓。

**验证**：差分仿真 **20 个块两侧逐字相同、0 差异** ✓（纯搬迁的判据 ✓）；本机回环两端 `verify: OK` ✓、
`seq_gap / crc_err / len_err / partial_err` 全 0 ✓、吞吐与 HEAD 同级别（46.0 vs 50.0 MB/s ✓）；
`-Wall -Wextra -Werror` 零告警 ✓。

### 17.5 差分仿真：接缝换了，差异只应来自 ack 粒度

仿真接缝从"假 socket"换成"假 lowlevel"：`tools/sim/simll.c` 提供一个 `FFRDP_LOWLEVEL` 的假实现，
`run.sh` 用 `-D'ffrdp_udp_lowlevel_init(p,cb,ctx)=sim_ll_init(p,cb,ctx)'` 把 `ffrdp_init` 的那一次调用
引过去；两侧的驱动方式由 `-DFFRDP_LL_DRIVEN` 分开 —— base（HEAD，协议挂在应用线程上）继续 `ffrdp_update`，
工作区这一侧每步调用 `sim_ll_run(idx, ctxt)`：先把该端点此刻待收的包逐包以 `RECV` 回调交给协议，
再给一次 `TIMER`。假 lowlevel 的 `timer()` **只记录、绝不触发回调** ✓（否则应用线程在 `ffrdp_send` 之后
的唤醒会改变测试的步进模型）。

结果（`bash tools/sim/run.sh`，rc=0）：

| 测试 | 结果 |
|---|---|
| `t_fuzz` | **两侧逐字相同** ✓（398 个敌意片段全部存活，上界行为一致）|
| `t_ack` | **两侧相同且 PASS** ✓（3/2/1 与 5 都对）|
| `t_rto` | 有可见数值差：`rto 24 → 90`、`retransmits 12 → 11`、`rto_backoff 1 → 0` |
| `e2e` | 17 个配置都有差异：11 个只有数字不同，6 个多/少一行诊断（flag 行）|

主因只有一个，而且正是 17 节开头说的那一条：**应答粒度从"一批一 ack"变成"一帧一 ack"** ✓。
最干净的证据是无丢包配置那一行：

```
HEAD  c0 recv= 47.26MB ... ack_recv=5782
work  c0 recv= 47.29MB ... ack_recv=38708      <- 6.7 倍的 ack
```

**数据速率基本没动** ✓（47.26 → 47.29 MB ✓），变的几乎全是 ack 与由 ack 派生的计数
（`mack` / `dup` / `rto_floor` / rtt 采样 ✓）。t_rto 的数值差也是这一类：ack 什么时候到决定了 rtt 采样，
rtt 决定了 rto。

⇒ 下一步最值得试的一件事：**把 ack 推到这一段结束再发**（每帧只标记 `got_data`，由 tick 统一回一个 ack）。
那既恢复旧版 ack 的经济性，也很可能把 17.2 里那 30% 的回环代价收回去 —— 因为多出来的正是包数与唤醒。

**t_rto 那两行数值差的机理**（不是"差不多"就算过，值得写清楚）：新模型里 RECV 先于 TIMER，所以在这一步
里 ack 是在重传**之前**被应用的 —— 头帧先被 ack 释放，于是 Karn 规则不再抑制这次 rtt 采样，`rtts/rttd`
被播种成 30/15 ⇒ `rto = 90`；旧模型先重传再收 ack，那次采样被 Karn 跳过，`rto` 停在 24。
`retransmits 12 → 11`、`rto_backoff 1 → 0` 都是同一条因果链的下游。无崩溃、无校验失败。

### 17.6 这个仿真**看不见**什么（很重要）

假 lowlevel 的 `timer()` **只记录、不触发**，而 `sim_ll_run` 每步固定交一次 `TIMER` —— 这是为了让步进模型
确定。后果是：**deadline 怎么算，仿真完全测不到** ✓。我把 17.1 里那两条调度修正（"有队可发就立刻"、
"有帧可首发就立刻"）加进去之后重跑，仿真结果**逐字不变** —— 因为在那套步进模型里 deadline 本就不参与。
那两条只在本机回环上现了形（50 → 10 MB/s、tick 腰斩）。

⇒ 结论：**差分仿真管协议语义（帧的解析、记账、ack、fuzz 上界），本机回环管调度与吞吐**，两者不能互相
代替。将来再动 `ffrdp_arm_timer`，必须跑回环，不能只看仿真绿。
