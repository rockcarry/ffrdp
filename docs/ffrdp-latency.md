# ffrdp 音视频延迟预算（H.265 / VBR 场景）

> **语言** ✓：本文档**只有中文版** ✗（英文版只有仓库根目录的 [`readme.md`](../readme.md) ✓）。
> 需要其它语言请**用 AI 自行翻译** ✓ —— 记得让它保留宏名、命令、代码块与 `✓ / ✗` 符号原文 ✓。

本文回答一个问题：**在音视频（一帧必须完整送到才能解码）的场景里，ffrdp 自己加了多少延迟、这些延迟
从哪来、按什么顺序去压。** 前 8 节只算 **ffrdp 自己那一段** ✓；第 9 节把它放回**整条流水线**（编码器 /
jitter buffer / 显示才是大头 ✓），第 10 节与 **TCP / KCP / QUIC** 做**延迟**层面的横向对比 ✓。

结论是**从代码机制 + 实测参数推出来的**，不是经验值 —— 每一项都标了依据（`ffrdp.c` 的行号或常量 ✓），
方便以后核对与更新 ✓。**不含**编解码器自身的延迟、播放端 jitter buffer、容器封装（那些在 ffrdp 之外 ✗）。

---

## 1. 一句话结论

以 1080p H.265 VBR **1.5 Mbps**（≈ **187.5 KB/s**）、视频帧率 25–30 fps、GOP 25–50 为例：

| 场景 | ffrdp 加的延迟（不含编解码）| 主导项 |
|---|---|---|
| 慢 AP（C ≈ 300 KB/s，RTT ≈ 10 ms）稳态 P 帧 | **25–35 ms** | 帧自身的串行化（/C）|
| 慢 AP 的 **I 帧**（40–60 KB）| **150–220 ms** | 同上，突发 |
| 快 AP（C ≈ 3–5 MB/s）稳态 P 帧 | **6–10 ms** | RTT/2 |
| 快 AP 的 **I 帧** | **15–25 ms** | RTT/2 + 串行化 |
| 每次丢包（那一帧）| **+10～30 ms** | 快重传 0.5–1.5 RTT；RTO 地板 16 ms |
| 音频（**独立连接**）| **≈ 10 ms** | 自身只 1～2 ms，主要吃 RTT/2 |
| 音频（**与视频同连接**）| 峰值 = 视频队列延迟（100–200 ms）| 队头阻塞 ✗ |

**关键结论：10 ms 的 RTT 本身只贡献约 5 ms** ✓。真正决定音视频延迟的是**链路带宽 C、I 帧大小、
以及"一帧必须到齐"这个约束**；RTT 只在**丢包恢复**和**窗口该开多大**上起作用 ✓。

> ⚠️ 上面的数是 **ffrdp 自己那一段** ✓（第 6 段）。用户感知的端到端延迟还要加上编码器缓冲、
> jitter buffer 与显示流水线 —— 那几段总和通常是它的 **5～20 倍** ✗（见 §9）。协议层面的横向对比见 §10。

## 2. 延迟怎么算

ffrdp 是**有序可靠字节流**（接收侧 `recv_seq` 逐帧按序推进，**洞会挡住它后面所有字节** ✓ ——
`ffrdp.c` 的接收交付循环），而"一帧视频可解码"要求**该帧最后一个字节已到达**，所以：

```
T_整帧到齐 ≈ 入队推迟 + Σ(排在前面的字节)/C + 本帧字节/C + RTT/2 + 丢包恢复
```

| 项 | 量级（1.5 Mbps / 10 ms RTT）| 依据 |
|---|---|---|
| `RTT/2`（单向传播 + 空口调度）| **≈ 5 ms** | 实测 `rtts ≈ 10 ms` |
| `本帧字节/C`（串行化）| **主导项**，见表 | 瓶颈按 FIFO 排空 |
| 入队推迟 | **0～2 ms** ✓ | 半帧（没攒满 smss 的尾巴）由协议自己发走：判据是"应用停手超过 `FFRDP_FLUSH_IDLE = 2 ms`" ✓（旧行为是等 500 ms 超时或被下一帧填满 ✗，见 §4.1）|
| 丢包恢复 | **+10～30 ms / 每丢一次** | 快重传 `hole_wait` = 0 / 1·rtt / min(3·rtt, 300) ✓；RTO = `max(rtts + 4·rttd, rto_floor)`，硬地板 `FFRDP_MIN_RTO = 16 ms` ✓ |

两个容易忽略但很重要的性质：

- **数据帧即时 ACK**（`FFRDP_ACK_COALESCE = 0` ✓）⇒ 接收侧**不用等 ACK 就能交出字节** ⇒ 解码延迟
  与 ACK 无关 ✓；ACK 只影响发送侧的窗口释放 ✓。
- **ffrdp_flush() 会立刻唤醒传输线程** ✓（`ffrdp_flush` 里调 `lowlevel->timer()` 打断 `select`）
  ⇒ 协议自己的循环**不引入**额外延迟 ✓；10 ms RTT 的链路上一圈 lap 只有 2～3 ms ✓。

## 3. 代入数字

前提：MSS 取 `test.c` 常用的 `mss:1280`（线上 1280+4 头 = 1284 B）；若用默认则是 1464（线上 1468 B ✓）。
**需要按你的链路替换的量是 C（AP 有效吞吐）、I 帧字节数、帧率、丢包率。**

### 3.1 慢 AP：C ≈ 300 KB/s

| 帧 | 大小 | 串行化 | 加 RTT/2 |
|---|---|---|---|
| P 帧（典型）| 4–8 KB | 13–27 ms | **18–32 ms** |
| 平均帧 | 6.25–7.5 KB | 21–25 ms | **26–30 ms** |
| 中等帧 | 10 KB | 33 ms | **38 ms** |
| **I 帧** | 40–60 KB | 133–200 ms | **138–205 ms** |

此时视频只占链路 **62%** ⇒ **不形成常驻队列** ✓ ⇒ 延迟基本就是"帧自身串行化"，抖动也小 ✓。
**但 C 若掉到 ~200 KB/s（视频 187.5 + 音频 + 重传开销就顶满了）⇒ 开始逐帧堆积，延迟非线性爬到几百 ms ✗** ——
这是慢 AP 上最危险的工作点 ✓。

### 3.2 快 AP：C ≈ 3–5 MB/s

| 帧 | C = 3 MB/s | C = 5 MB/s |
|---|---|---|
| P 帧 6.25 KB | **7 ms** | **6 ms** |
| 平均帧 7.5 KB | **7 ms** | **6 ms** |
| I 帧 50 KB | **22 ms** | **15 ms** |

视频只占链路 **4–6%** ⇒ 延迟从"带宽受限"变成 **"传播受限"** ✓，地板就是 `RTT/2` + 一包空口时间 ✓。
**注意**：快 AP 上会冒出三个新约束（见 §4.3 与 §5）。

### 3.3 丢包的那一帧

| 路径 | 代价 | 依据 |
|---|---|---|
| 快重传（对端下一帧到达即报洞）| **0.5–1.5 RTT**（10 ms RTT ⇒ 5–15 ms）| `hole_wait` 由"白费率"证据自调：白费 < 40% ⇒ 0（立刻重传）、中间 ⇒ 1 RTT、≥ 80% ⇒ min(3 RTT, 300 ms) ✓ |
| RTO 兜底（洞之后没流量）| **≥ 16 ms**，典型 20–40 ms | `rto = max(rtts + 4·rttd, rto_floor)`，`FFRDP_MIN_RTO = 16` ✓ |
| 连带影响 | 有序交付 ⇒ **洞会把后面所有字节一起挡住** ✗ | 所以一次丢包不只推迟它自己那一帧 ✓ |

**在快 AP（低 RTT）上，`FFRDP_MIN_RTO = 16 ms` 会变成丢包恢复的主导项** ✓ —— 若快 AP 的 RTT 只有
3 ms，一次尾丢就是 5 个 RTT 的代价 ✗。

### 3.4 音频

AAC 单包约 400 B（20 ms 采样）⇒ 自身串行化只 **1.3 ms** ✓。所以：

- **独立连接** ⇒ 音频延迟 ≈ `RTT/2` + 1～2 ms ≈ **10 ms** ✓；
- **与视频同连接** ⇒ 单连接是 FIFO 有序流，音频包排在 I 帧那 50 KB 后面 ⇒ **峰值 = 视频队列延迟
  （150–200 ms）** ✗。这是音视频一起跑时最容易被忽略、也最伤体验的一条 ✓。

## 4. 三个真正咬人的机制（都跟 RTT 无关；第 1 条已由协议自动兜住 ✓）

### 4.1 半帧必须发走（已自动 ✓，不必每帧 `ffrdp_flush()`）

半帧（没攒满 MSS 的尾巴）如果自己不发送，就只能被**下一条消息**填满或等超时 ✗ —— 视频帧最后那
几 KB 正好是半帧 ⇒ 那样就等于**凭空加一个帧间隔**（25 fps ⇒ 40 ms），流一停还会挂到 500 ms ✗。
所以"帧尾必须发走"这件事本身跑不掉 ✓。

现在由协议自己兜住 ✓：出口 ② 的判据是"**距最后一次追加字节**超过 `FFRDP_FLUSH_IDLE = 2 ms`"
（`ffrdp.c`，`next_due` 里的期限是同一个值 ✓ —— 只改判据不改期限，timer 根本不会在 2 ms 后醒来 ✗）
⇒ 尾巴按 SHORT 帧发走。默认档实测 **max 延迟 486 ms → 4 ms** ✓（`docs/notes.md` §26.95、
`ffrdp-v2.md` §9.2）。

- **对吞吐没有影响** ✓：判据是"**应用停手了**"，不是"每 2 ms 冲一次" —— `cur_new_tick` 每次追加字节都
  刷新 ⇒ 持续供数据时这个条件**永远不成立**，帧照旧攒满走出口 ① ✓（饱和档 74~80 → 81~84 MB/s ✓）。
- **`ffrdp_flush(ctxt, conn)` 仍然有用** ✓：它是"**别等这 2 ms**"的显式捷径（立刻叫醒传输线程）；
  但**不再是每帧必须做的事** ✓。
- **代价** ✗：每次"应用停手"会多出一个短包（尾巴单独成包）；纯吞吐、低码率（< smss/IDLE ≈ 730 KB/s）
  的场景可把 `FFRDP_FLUSH_IDLE` 调大 ✓。

### 4.2 音视频同连接 = 队头阻塞

见 §3.4。**建议音频走独立 ffrdp 连接**（同一 UDP 路径、不同实例）✓ —— ffrdp 本身**不做优先级** ✗。

### 4.3 在途闸门按"帧数"计，要对着 BDP 看

`FFRDP_INFLIGHT_MAX = 64` 帧（≈ 82 KB）、地板 `FFRDP_INFLIGHT_MIN = 4` ✓，探测（`FFRDP_PROBE_ENABLE = 1` ✓）
可以把它压到"已证明能赢"的值 ✓。

| 链路 | BDP = C × RTT | 与 64 帧的关系 |
|---|---|---|
| 慢 AP 300 KB/s | ≈ 3 KB ≈ **2.4 帧** | 窗口是 BDP 的 ~20 倍 |
| 快 AP 5 MB/s | ≈ 50 KB ≈ **39 帧** | 只剩 1.6× 余量 ✗ |

- **对"填满管道"的吞吐流**：窗口远大于 BDP ⇒ 多出来的帧堆在缓冲里形成**常驻队列**（代码注释里记的
  实测是"对端允许 148 帧、路径只 carry 5 帧 ⇒ 约 200 ms 常驻队列"✓）⇒ 凭空几百 ms ✗。
- **对限速的音视频流**：源速率（187.5 KB/s）远低于 C，ACK 释放帧快于编码器产帧 ⇒ 在途量自然贴着
  BDP（≈2 帧）⇒ **这个坑对音视频反而不怎么咬** ✓；只有 I 帧那种瞬时突发会被窗口一次性放出去 ✓。
- **快 AP 上反过来**：窗口 64 帧的速率上限 = `64 × 1286 B / RTT` ≈ **8.2 MB/s** ✓ —— 5 MB/s 时是天花板的
  61% ✓，**再往上推就会撞窗口而不是撞链路** ✗（那时该调 `FFRDP_INFLIGHT_MAX`，其次才是 MSS）✓。

## 5. MTU / IP 分片

### 5.1 "把 MTU 调大能降延迟吗" —— 基本不能 ✗

延迟 = 一帧总字节数 / C，MTU 只改变"这些字节装在几个包里"，**总字节数不变 ⇒ 串行化不变** ✓。
省下的只有每包的固定开销（4 B 帧头 + 2 B FEC 尾 + 28 B UDP/IP）：

- 6.25 KB 的帧：MSS 1280 → 5 包；MSS 1464 → 5 包（**包数没变** ✓）
- 50 KB 的 I 帧：40 包 → 35 包，省 ~170 B ≈ 0.05 ms

⇒ 延迟改善 **< 1 ms**，可忽略 ✓。MTU 真正的收益是**吞吐效率与 CPU**（每包固定的空口前导 / IFS 摊薄、
syscall 变少）✓。

### 5.2 反而要注意：默认 MSS 曾经让**每个满帧都走 IP 分片** ✗（已修 ✓）

线上字节 = 本层帧 + UDP 8 + IPv4 20：

```
（修前）MSS 1492 ⇒ 普通满帧 4+1492   = 1496，+28 = 1524  > 1500  ⇒ 分片 ✗
                  FEC 帧  4+1492+2 = 1498，+28 = 1526  > 1500  ⇒ 分片 ✗
（修后）MSS 1464 ⇒ 普通满帧 4+1464   = 1468，+28 = 1496  ≤ 1500  ✓
                  FEC 帧  4+1464+2 = 1470，+28 = 1498  ≤ 1500  ✓
```

根因：`lowlevel.h` 的注释只减了 UDP 头，**漏算 IP 头那 20 字节** ✗。现在代码把**收 / 发两个 MSS
拆开** ✓：`FFRDP_MAX_RX_MSS` 仍是 1492（收包节点按它建，缩了会**静默截断**老对端的满帧 ✗ ⇒ 收侧
不能动 ✓），只有 `FFRDP_MAX_MSS = 1464` 变小 ✓，并加了编译期守卫防回归 ✓。

**分片为什么伤延迟** ✗：丢任一分片 = 整个数据报报废（重传整帧）✗；空口上第二片只有 16 B 载荷却要再付
一次每包开销 ✗；部分 NAT / AP 对非首分片处理很差 ✗；路径 MTU 不是 1500 时（PPPoE 常见 1492）更糟 ✗。

**动手前先量路径 MTU** ✓：

```bash
ip link show | grep mtu          # 两端都看
ping -M do -s 1472 <peer>        # 1472+28 = 1500 ⇒ 通 = MTU 1500
ping -M do -s 1496 <peer>        # 1496+28 = 1524 ⇒ 报 "Message too long" = 本地 MTU 就是 1500
```

（若整条路径 MTU 本来就 ≥1528，比如内部 jumbo，那本来就没分片 ⇒ 把 MSS 调小只会白丢 ~2% 窗口字节 ✓。）

## 6. 把延迟压下来的顺序（按性价比）

1. **音频拆到独立连接** ✓ —— 避开队头阻塞。慢 AP 上值 150 ms，快 AP 上也值一个 I 帧的串行化。
2. **别让半帧等** ✓ —— 已默认做掉（`FFRDP_FLUSH_IDLE = 2 ms` 空闲即发，§4.1）；要更硬的帧间节拍再显式
   `ffrdp_flush()` ✓。
3. **开 FEC**（`fec:N`）—— 快 AP 带宽富余（视频只占 4–6%），拿 `N/(N+1)` 带宽把"丢包恢复 = 1 个 RTT
   + 16 ms 地板"换成 **0 RTT** ✓。⚠️ 出货构建默认 `FFRDP_FEC_ENABLE = 0`，FEC 是**编译掉的** ✗ ⇒ 要开宏重编 ✓。
4. **砍 I 帧体积 / 缩 GOP 依赖（编码器侧）** ✓ —— 唯一能直接砍掉最大串行化项的手段，比动传输层有效得多。
5. **在途闸门对着 BDP 调**（`FFRDP_INFLIGHT_MAX`）—— 只在"窗口成为速率瓶颈"时才动 ✓（见 §4.3）。
6. **低 RTT 链路上重新审视 `FFRDP_MIN_RTO = 16`** —— 确认不会造成伪重传的前提下 ✓。
7. **确认不出 IP 分片**（§5.2）—— 这是正确性问题，不是调优项 ✓。

## 7. 怎么量（别猜）

ffrdp **本身不测量"应用层整帧延迟"** ✗ —— 它只有传输层量 ✓。所以：

**（a）先看 `ffrdp_dump()` 这几行**（`tools/check.sh` 跑完也能在日志里看到）：

| 行 | 看什么 |
|---|---|
| `rtt_min` | 路径的**真实地板** ✓（"最低能做到多少"看它，不是看 `rtts`）|
| `rttm / rtts` | 当前往返；与 `rtt_min` 的比值就是**排队**（探测的判据是 `rtts > 3 × rtt_min` ✓）|
| `inflight, cap` | 窗口有没有变成速率上限（对比 BDP = C × RTT）✓ |
| `counter_resend_ratio` / `counter_resend_waste` | 重传与白费比例（丢包恢复的代价）✓ |
| `udp lowlevel lap cost` | 协议自己循环的开销（pre / mid / tick µs）⇒ 确认地板不是 ffrdp 造成的 ✓ |

**（b）要拿到真实的"整帧到解码"延迟，只能在 payload 里打点** ✓ —— 学 `test.c` 的做法塞一个
帧号 + 首字节时间戳，在**编码输出**与**解码入口**各打一次 ✓。这是唯一能把"编码 / 排队 / 传输 / 解码"
四段拆开看的办法 ✓。

## 9. 把 ffrdp 放回整条链路：全流水线预算

前面算的都是 **ffrdp 自己那段** ✓ —— 用户感知的是"从摄像头曝光到屏幕出画面"的**整条流水线** ✓。
实时音视频的端到端延迟是**各段相加** ✓，且各段**互不掩盖** ✗：传输层做得再好，也压不掉编码器的
帧缓冲和播放端的 jitter buffer ✓。

一条 1080p H.265、摄像头 → 播放器的典型链路：

| # | 段 | 低延迟配置 | 普通/默认配置 | 谁负责 | 怎么砍 |
|---|---|---|---|---|---|
| 1 | 传感器曝光 + 读出 | 5–15 ms | 5–15 ms | 摄像头 ISP | 少开多帧降噪 / 3DNR |
| 2 | 编码器内部流水 | 1 帧（33–40 ms）| 1–2 帧 | 编码器 | 硬件编码；开"低延迟 / 零延迟"模式（禁 lookahead ✓）|
| 3 | B 帧重排 | **0**（IPPP）✓ | 1–2 帧 ✗ | 编码器 | `max_b_frames=0` ✓ |
| 4 | 码率控制缓冲（VBR）| +0～1 帧 | +1～3 帧 ✗ | 编码器 | 实时用 CBR / 低延迟 VBR；盯 `vbv-bufsize` |
| 5 | 应用队列 → ffrdp | **0～2 ms** ✓ | 最多 500 ms ✗ | 协议 | §4.1：空闲 2 ms 自动冲刷（旧行为）；应用侧别再攒帧 |
| 6 | **ffrdp 传输** | **6–35 ms**（§1 表）| 同 | ffrdp | §6 的顺序 |
| 7 | AP / 空口排队 | 0～10 ms ✓ | +10～200 ms ✗ | 链路 | 别让它饱和（见下）✓ |
| 8 | 接收端 jitter buffer | 1 帧 ≈ 33 ms ✓ | 2–5 帧 = 66–166 ms ✗ | 播放器 | **常是最大的一段**：按真实抖动定，别按最坏定 |
| 9 | 解码 | 5–15 ms | 5–20 ms | 解码器 | 硬件解码；别开"多帧参考"的延迟模式 |
| 10 | 渲染 / 合成 / 垂直同步 | 1 帧 + 16–33 ms | 1–2 帧 | 显示 | 关多帧滤镜 / 去隔行；零拷贝直通 |
| | **端到端合计** | **≈ 100–180 ms** | **≈ 250–450 ms** | | |

读法（三点 ✓）：

1. **ffrdp 那段只占 5～20%** ✓ —— 它是**唯一**被本文档优化的部分 ✓，但天花板由**编码器缓冲 +
   jitter buffer + 显示**决定 ✗。要进 100 ms 内，光调 ffrdp 不够，必须同时压 #2/#3/#4 与 #8 ✓。
2. **每个"帧级缓冲"就是一次帧间隔**（25 fps ⇒ 40 ms）✓ —— 上面 10 段只要有三处各留 1 帧，
   就已经 120 ms ✓，传输层那 10 ms 的差别被淹掉 ✗。
3. **相加的是"路径 + 缓冲"，不是"最好的那一次"** ✓ —— jitter buffer 通常按**最坏抖动**定，而链路排队
   (#7) 正是抖动的主要来源 ⇒ §4.3 的"别自伤成常驻队列"是**唯一**能同时压低 #7 与 #8 的手段 ✓。

**稳定性判据**（比"平均延迟"更重要 ✓）—— 一帧必须完整送到才可解码 ⇒

```
平均帧字节 × 帧率  ≤  C × 安全余量（建议 ≤ 0.6）
I 帧字节 / C       ≤  帧间隔（否则 I 帧形成暂态队列，表现为周期性卡顿 ✗）
```

以 1.5 Mbps / 25 fps 为例：平均帧 7.5 KB ⇒ 要 C ≥ ~125 KB/s（视频只占 62% 才不形成常驻队列 ✓，
同 §3.1）；而 I 帧 50 KB / 300 KB/s = 167 ms ≈ **4 个帧间隔** ✗ ⇒ **I 帧是唯一"能自己超过一帧"的东西** ✓。
要么砍 I 帧（编码器侧 ✓）、要么垫 C、要么让接收侧在 I 帧那一刻多留一点缓冲 ✓。

**量它，别猜**（见 §7(b)）✓：只有"编码输出"与"解码入口"各打一次时间戳，才能把上面 10 段拆开 ✓；
只看 `ffrdp_dump()` 只能看到第 6 段 ✗。

## 10. 与其他协议比延迟（设计层面判断，**非同机跑分** ✗）

与 `notes.md` §11.1 的对照表互补 ✓：那里比的是**能力** ✓，这里只回答**延迟** ✓。

### 10.1 先给结论

| 对比 | 无丢包稳态 | 丢包那一帧 / 尾延迟 | 结论 |
|---|---|---|---|
| **ffrdp vs TCP** | ffrdp 略优（ACK 即时、无 Nagle/delayed-ACK ✓）| ffrdp **明显优**（RTO 地板 16 ms vs ~200 ms ✗）| 目标场景（限速 + 短 RTT + 随机丢）ffrdp 赢 ✓ |
| **ffrdp vs QUIC（可靠流）** | 基本相同（都是 `RTT/2` + 串行化 ✓）| ffrdp 略优（快重传可 0 等待 ✓；QUIC 靠 PTO/TLP 仍要 1+ RTT）| 延迟 ffrdp 略优、开销更小 ✓；QUIC 赢在建连 / 迁移 / 加密 / 生态 ✓ |
| **ffrdp vs QUIC（DATAGRAM）** | 相同 ✓ | **QUIC 赢**（不发就是不发，没有 ARQ 修复延迟 ✓）| 音视频的**正确形态**是不可靠 + FEC ⇒ 这是 ffrdp 的缺口 ✗ |
| **KCP vs QUIC** | KCP 略优（无 ACK delay、无 pacing ✓）| **KCP 优**（激进快重传 N=2 ✓ vs QUIC 的 3-dup + PTO）| 低延迟 KCP 更极端 ✓；但 QUIC 不会因盲重传自伤 ✓ |
| **KCP vs ffrdp** | 相近 ✓ | ffrdp 优（把"早重传"做成**证据驱动**，只在真丢时早 ✓，见 §10.2）| ffrdp ≈ "KCP 的低延迟 + 不自伤" ✓ |

### 10.2 "KCP 用高重传换低延迟"成立吗 —— **一半成立，一半是误读** ✓

**成立的那一半**："更早的重传"确实换"更短的延迟尾部" ✓。一帧因丢包多等的延迟 ≈

```
P(丢) × 恢复时间 × 是否挡住后续字节
恢复时间：快重传 ≈ 0.5–1.5 RTT；RTO ≈ max(rtts + 4·rttd, RTO 地板)
```

KCP 的做法是把**两个因子都往小里调** ✓：快重传阈值降到 N=2（甚至 1）、内部 tick 默认 10 ms、
RTO 下限低（"快速模式"可低到几十 ms，标准模式 ~200 ms）⇒ 真丢包时恢复得快 ✓。

**误读的那一半**："高重传率"本身**不是**低延迟的来源 ✗，它恰恰是**代价** ✓。一次重传要么是
① 真丢了（有用的修复 ✓），要么是 ② 对端其实有、只是被超车/乱序（**白费** ✗）。②的份额一高：

- 白传的字节照样占 C ⇒ 抬高**所有**帧的串行化与排队延迟 ✗；
- 洞判错又撤回 ⇒ 接收侧白等 ⇒ 抖动变大 ✗。

正确说法：**"只在对端真没有时更早重传"换低延迟 ✓；"盲目更早重传"既费带宽又抬延迟 ✗。"重传率"
是诊断量，不是目标量 ✗。**

判据（ffrdp 就是这么做的 ✓，`ffrdp.c` 的 `waste` 比率 = 对端重复上报 / 重传次数）：

| 白费率 `waste` | 含义 | ffrdp 的动作 |
|---|---|---|
| ≥ `FFRDP_WASTE_HI` = 80% | 我们重传的包对端早就有 ⇒ RTO 太短 | 抬 RTO 地板；快重传改为等 `min(3·rtt, 300 ms)` ✓ |
| 40% ≤ waste < 80% | 说不清 | 快重传等 `1·rtt`；地板缓慢下探 ✓ |
| < `FFRDP_WASTE_LO` = 40% | 修复是真的 | **快重传 0 等待**、`rto_floor = 0` ✓ |

这正好回答 ffrdp 自己的历史 ✓：**v1.0.x 的 ~28% 重传率是"废"（②占大头）** ✗ ⇒ 那 28% 不但没换到
低延迟，还在自伤（`notes.md` 记的负载 ping 220 ms 就是它的账 ✓）。改成证据驱动后重传降到
0.1～0.3%、稳态 0 次/秒 ✓，延迟反而从 220 ms 掉到 18～38 ms ✓ ——
**低延迟不是重传率换来的，是"把无效重传删掉"换来的** ✓。

### 10.3 ffrdp vs TCP

TCP 的延迟劣势**不在传输设计本身**（"中规中矩"评得准 ✓），而在**为通用场景付的代价** ✓：

| TCP 的机制 | 对实时音视频的代价 |
|---|---|
| **RTO 下限**（Linux `TCP_RTO_MIN` ≈ 200 ms）| 尾丢 / 无后续流量时恢复 **+200 ms 起** ✗；ffrdp 是 `FFRDP_MIN_RTO` = **16 ms** ✓（差一个数量级）|
| 快速重传要 **3 个 dup ACK**（现代有 RACK/TLP 缓解 ✓）| 小窗口（音视频在途常只几帧 ✓）里凑不出 3 个 dup ⇒ 退回 RTO ✗；ffrdp 靠"对端报告了更高序号"即触发，`hole_wait` 可为 0 ✓ |
| **delayed ACK（典型 40 ms）+ Nagle** | 交互 / 小包场景最坏各加一次 40 ms ✗；ffrdp `FFRDP_ACK_COALESCE` = 0（收到即回）✓ |
| **拥塞控制把随机丢当拥塞** | 无线 / AP 上随机丢 ⇒ 退窗 ⇒ 吞吐波动 + 缓冲里排队抖 ✗；ffrdp 明确**不因随机丢退让** ✓ |
| **发送缓冲膨胀（bufferbloat）** | 应用队列堆在内核、延迟不可见 ✗；ffrdp 的在途闸门 + 探测直接对着"排队"（`rtts / rtt_min`）调 ✓ |
| 无消息边界 / 无 flush 语义 | 半帧要等凑满 ✗；ffrdp 有帧边界 + 空闲 `FFRDP_FLUSH_IDLE = 2 ms` 自动冲刷（`ffrdp_flush()` 可选）✓ |

反过来 TCP 更好的地方（要诚实 ✓）：成熟拥塞控制对互联网**友好** ✓（不被饿死、也不饿死别人）、
SACK / RACK / TLP 恢复机制丰富 ✓、有 TSO/GSO 硬件卸载（吞吐与 CPU ✓）、广域网随机丢包下
**现代 TCP（BBR）未必输** ✓。

⇒ **结论**：ffrdp 的延迟优势集中在**它自己的目标场景** —— **局域网 / 限速流 / 短 RTT / 有随机丢包** ✓；
出了这个场景（长肥管道、多路共享、需要公平性），不构成普遍优势 ✗。

### 10.4 ffrdp vs QUIC

QUIC 的传输层大量借鉴 TCP ⇒ §10.3 的多数条目对它同样成立 ✓；这里只讲**差异** ✓。

| 维度 | ffrdp | QUIC（可靠流）| 对延迟的意义 |
|---|---|---|---|
| 包头 | **4 B**（+1 可选）✓ | 20–40 B + TLS 记录 | 小包（音频 ✓）上 ffrdp 省 ✓ |
| 建连 | **无握手** ✓（应用自管）| 1-RTT / 0-RTT + TLS1.3 | 首帧 / 重连 ffrdp 快 ✓（代价：无加密、无迁移 ✗）|
| ACK | 收到帧**当场**回 ✓ | ACK delay 可配（默认量级 25 ms ✗）+ ACK frequency | 稳态有 ms 级差别（取决于对端配置 ✓）|
| 丢包恢复 | 快重传 `hole_wait` 可 0 ✓；RTO 地板 16 ms ✓ | TCP 式 + PTO / TLP ✓ | 尾丢 ffrdp 更早 ✓；QUIC 的恢复机制更完整 ✓ |
| 拥塞控制 | **自研在途闸门 + 探测** ✓（不因随机丢退让 ✓）| CUBIC / BBR 成熟 ✓ | 在"被限速 + 抖动"链路上 ffrdp 的**排队治理**更强 ✓（这是它明显领先 QUIC 的一项 ✓）|
| **可靠性模型** | 只有**可靠有序流** ✗ | 可靠流 **+ DATAGRAM** ✓ | **音视频的关键差距** ✗（见下）|
| 多流 / HOL | 无多流（建议音频另开一条连接 ✓）| 原生多流、无跨流 HOL ✓ | 音视频合流时 QUIC 天然不互相挡 ✓ |
| 迁移 / 加密 / 生态 | ✗ / 可选 AES / 自研单文件 | ✓ / 内建 TLS1.3 / 标准 | QUIC 全面领先 ✓（但都不直接降延迟 ✓）|

**对延迟最狠的一条** ✓：实时音视频**不该走可靠流** ✗。用可靠流（无论 ffrdp 还是 QUIC）跑视频，
就等于把"一帧必须到齐"变成"**每一帧都必须到齐**" ⇒ 丢一帧要么重传（+0.5–1.5 RTT ✓）要么堵住
后面所有帧（HOL ✗）。QUIC 的答案是 **DATAGRAM 帧**（不可靠、无重传、无 HOL ✓）配 FEC 或直接丢给上层 ✓
—— **这一档的延迟 ffrdp 现在拿不到** ✗。

`notes.md` §11.1 / §11.2 已记了这个结论 ✓：ffrdp 要补的是**"不可靠报文模式"**（帧仍是数据报：
不做有序交付、不重传；但**保留在途闸门 + 探测 + QUERY keepalive** ✓）。补上之后：

> **稳态**：两者都是 `RTT/2 + 串行化`，差距在噪声内 ✓。
> **有丢包**：不可靠模式 + FEC ⇒ 两者都能做到"**0 重传，丢就丢**" ✓，延迟等于路径本身 ✓。
> **剩下的差距**：包头开销（4 B vs QUIC 的几十 B ✓）、无握手 ✓、排队治理（ffrdp 领先 ✓）
> 与建连 / 迁移 / 加密 / 生态（QUIC 领先 ✓）。

### 10.5 一句话总结

- **TCP**：设计均衡 ✓，但为通用性付了"**200 ms RTO 地板 + 40 ms delayed ACK + 把随机丢当拥塞**"的
  代价 ✗ —— 实时音视频恰好**每一项都踩** ✗ ⇒ 在 ffrdp 的目标场景下，ffrdp 的延迟明确更优 ✓。
- **KCP**：把"早重传"做到极致 ✓，换到了尾延迟 ✓；但"高重传率"是**它的代价、不是它的原理** ✗ ——
  无脑更早重传会自伤 ✓（ffrdp v1.0.x 就是反面教材 ✓）。
- **QUIC**：**能力**上全面领先 ✓（建连 / 迁移 / 加密 / 多流 / DATAGRAM / 生态），**延迟**上稳态与 ffrdp
  持平 ✓，在"抖动的限速链路排队治理"上落后 ✓。真正的分水岭是**可靠性模型**：QUIC 有不可靠
  DATAGRAM ✓、ffrdp 没有 ✗ ⇒ 补齐它之前，**实时音视频上 QUIC 是更正确的选择** ✓。
