# tools/sim —— 差分仿真（A/B 对比同一份改动的效果）

## 它解决什么问题

真机测量**跨轮次不可比** ✗：同一条链路在不同时刻的丢包/乱序/负载都不同，
所以"这次 2.3%、上次 2.9%"分不清是代码变了还是链路变了 ✗。

这个仿真把网络**确定化**：虚拟时钟 + 由包头序号 hash 决定的丢包/抖动 ⇒
**两次运行面对的网络逐字节相同** ✓ ⇒ 把"老代码"和"新代码"放在同一条假链路上跑，
**差异就一定是代码造成的** ✓（噪声为 0，不是 ±50% ✓）。

## 怎么跑

```bash
bash tools/sim/run.sh                    # 跑全部（t_rto + t_ack + e2e）
TESTS="e2e"  bash tools/sim/run.sh       # 只跑端到端
TESTS="t_rto" bash tools/sim/run.sh      # 只跑 RTO 放大测试
REF=/path/to/old_ffrdp.c bash tools/sim/run.sh   # 基线不用 git HEAD，而用指定文件
```

| 环境变量 | 含义 | 默认 |
|---|---|---|
| `TESTS` | 要跑哪些测试（可多选，空格分隔）| `t_rto t_ack e2e` |
| `REF` | **基线**源码路径 | `git show HEAD:ffrdp.c` |

**被测版本恒为工作区当前 `ffrdp.c`** ✓ —— 所以典型用法是：改完代码直接 `bash tools/sim/run.sh`，
看"对比 HEAD 有没有变化" ✓。

依赖只有 `gcc` 和 `bash` ✓，**不需要网络** ✓（`sendto`/`recvfrom`/`select`/`calloc`/`free`
都用 `-D` 换成了仿真实现 ✓）。

## 它是怎么做到的（读代码前的 30 秒）

1. **时钟虚拟化**：`run.sh` 把 `ffrdp.c` 里 `get_tick_count()` 的真实时钟实现
   （匹配 `ts.tv_nsec` 的那行）替换成 `return sim_tick();` ✓ ⇒ 时间由
   `sim_setstep()` 驱动，**1 步 = 1 ms** ✓（不依赖真实时间 ⇒ 跑多快都一样 ✓）。
2. **两台实例**：`e2e.c` 起两个 `ffrdp` 上下文（side 0 / side 1），形状与 `test.c` 相同 ——
   每步各自投喂一个 1..`maxchunk` 字节的随机块并 `update()` ✓。
3. **假网络**（`simnet.c`）：两个内存队列，提供丢包、连丢、延迟、抖动、
   **共享限速器（shaper）**、**令牌桶（policer）**、**重尾尖峰（spike）** ✓。
4. **内存记账**：`calloc/free` 被计数 ⇒ 输出里的 `leaked=` 是**真正的泄漏** ✓（应当恒为 0 ✓）。
5. **计数器自动适配**：`run.sh` 会探测源码里有没有 `counter_ack_recv` / `counter_recv_ooo` /
   `counter_recv_dup` / `inflight` 等，自动加 `-DNEW_COUNTERS` 之类的开关 ✓
   ⇒ **同一份测试能同时编译老源码和新源码** ✓（这是能做 A/B 的关键 ✓）。

> 生成的中间文件（`ffrdp_base.c`、`ffrdp_new.c`、`*_base`、`*_new`、`simnet.o`）
> 都在 `.gitignore` 里 ✓ —— 它们不是源码，每次 `run.sh` 都会重写 ✓。

## 三个测试

| 测试 | 内容 | 判据 |
|---|---|---|
| `t_rto` | 12 个同时过期的帧被逐个重传，观察 RTO 被放大多少次 | 期望"**每往返退让一次**"⇒ `rto_backoff` 只有 1 次，而不是 12 次 ✗ |
| `t_ack` | 手工注入 3 个 ACK 帧（无洞 / 连续 / 有洞），验证诊断计数 | 期望 `ack_recv=3 mack=2 hole=1` ⇒ 打印 `PASS` ✓ |
| `e2e` | 端到端跑 `steps` 步，输出一行摘要 + 若干诊断行 | A/B 对比 `recv`（交付量）与 `resend%`（重传率）✓ |

### e2e 的参数（13 个，位置固定）

```
./e2e_new loss burst delay jitter steps maxchunk [cap qmax [pcap pburst [spike% spike_ms]]]

loss      丢包率（0.05 = 5%）
burst     连丢个数（0 = 随机丢；6 = 一次丢 6 个）
delay     单向延迟 ms
jitter    抖动 ms（0 = 无抖动）
steps     仿真步数（1 步 = 1 ms；6000 = 6 秒）
maxchunk  每步最多投喂的字节数
cap       共享限速器速率 KB/s（0 = 不限速）
qmax      限速器队列 KB（超出即丢）
pcap      令牌桶速率 KB/s（只作用于 side 0 的上行；超速即丢，不排队）
pburst    令牌桶深度 KB
spike%    被"重尾"命中的包比例（%）
spike_ms  重尾额外延迟 ms
```

`shaper` 与 `policer` 的区别值得记住：**shaper = 排队（延迟上升）**，
**policer = 丢弃（超量直接丢）** ✓ —— 真机链路上限速往往两者混合 ✓。

### 内置的 17 个场景（`run.sh` 里写死）

| # | 参数 | 含义 |
|---|---|---|
| 1 | `0.0 0 4 0 6000 16384` | 干净链路（4ms）|
| 2 | `0.0 0 10 0 …` | 干净链路（10ms）|
| 3 | `0.05 0 4 …` | 5% 丢包 |
| 4 | `0.02 6 4 …` | 2% 丢包 + 6 连丢 |
| 5 | `0.10 0 4 …` | 10% 丢包 |
| 6 | `… 1200 200` | 限速 1200KB/s，队列 200KB |
| 7 | `… 1200 64` | 限速 1200KB/s，队列 64KB |
| 8 | `… 600 200` | 限速 600KB/s，队列 200KB |
| 9 | `… 2048 1200 200` | 限速 + 小分块（2048B）|
| 10 | `… 40` | 抖动 40ms |
| 11 | `… 60` | 抖动 60ms |
| 12 | `… 100` | 抖动 100ms |
| 13 | `… 1200 200 400 4` | 限速 + 令牌桶 400KB/s（超量丢）|
| 14 | `… 15 300` | 15% 的包 +300ms 重尾 |
| 15 | `… 1200 200 … 15 300` | 限速 + 重尾 |
| 16 | `0.0 0 40 … 5 200` | 40ms 延迟 + 5%/200ms 重尾 |
| 17 | `0.0 0 30 … 3 150` | 30ms 延迟 + 3%/150ms 重尾 |

场景 6~9、13、15 是**"有队列/有整形"族**（对应真机的缓冲膨胀 ✓）；14、16、17 是**重尾族**
（对应真机"帧迟到"而不是"帧丢了" ✓）—— 这两族是仿真里最有价值的部分 ✓。

## 输出怎么读

```
       rto_floor=142 ms (the peer called 24 of our retransmits pointless)   ← 附加行，最先打印
loss=0.000 burst=0 delay=4 jit=1 cap=1200KB/s q=200KB pol=0KB/s/0KB spike=0%/0ms |   ← 场景参数回显
c0 recv=  4.75MB resend= 0.61% (rto   24 fast    0) cwnd=64 ssth=32 wait=255 fail=5222 rttd=6 |
c1 recv=  1.88MB resend= 3.44% maxrto=0 leaked=0
       c0 ack_recv=… mack=… hole=… timeout_evt=… rto_backoff=… | peer recv_ooo=… recv_far=… | dup=… ack_dup=…
       c0 spur=… rto_floor_raises=…
       air loss c0->c1=0.00% (…/…)  c1->c0=0.00% (…/…)
       c0 inflight=…
```

| 字段 | 含义 |
|---|---|
| `rto_floor=` | 本端当前 RTO 下限 ms，以及**对端报告"我们有多少次重传是白费的"** ✓（源码带 dup 上报的版本才有这一行 ✓）|
| 第一组（`recv`/`resend`/`cwnd`/`wait`/`fail`）| **c0 → c1 方向**：`recv` 是 c1 实收字节 ✓，`resend` 是 **c0** 的重传率 ✓ |
| 第二组 | **c1 → c0 方向**（对称）|
| `leaked` | 未归还的分配数，**必须为 0** ✓ |
| `air loss` | 真实空口丢包率（发送帧数 − 收到帧数），用来核对"场景的丢包率"是否如实生效 ✓ |
| 其余附加行 | 仅在源码带对应计数器时打印（旧源码会少几行，这是正常的 ✓）|

> 每跑一步都是"先 HEAD 后 work"两行成对 ✓ —— **A/B 就看这两行之间有没有差异** ✓。

## 使用纪律（这几条是踩出来的）

1. **干净链路必须"逐字不变"** ✓ —— 任何改动只要动了场景 1/2 的输出，就先当成回归查 ✗。
2. **不要用单个小场景判"退化"** ✗ —— 同一族代码只改 RTO 逻辑就能让某个场景的结果跳 8 倍
   （1ms 量化 tick + 队列耦合 ⇒ 混沌 ✓，详见 `NOTES.md` 末尾"判据的坑"）。
   **要看"场景族的趋势"**（例如"丢包族一致退步"才是真信号 ✓）。
3. **仿真验证不了的两类改动** ✗：
   - **乱序相关**（本仿真没有乱序模型 ⇒ 快重传纪律只能在真机验证 ✓）；
   - **收窄在途量**（仿真的 ACK 粒度比真机粗 ⇒ 小窗口在仿真里会直接断流 ✗ ⇒ 只能看真机 ✓）。
4. **判据的顺序**：仿真判"**没有回归**" ⇒ 真机判"**确实有收益**" ✓ ——
   两者缺一不可，任何一步不过就不要上机 ✗（`OPTIMIZATION.md` 里的 step27 就是仿真不过而放弃的例子 ✓）。

## 局限（诚实列出）

- **无乱序模型**：帧要么丢要么按 FIFO 顺序到 ✓ ⇒ 与乱序有关的收益/风险测不出来 ✗。
- **ACK 粒度较粗**：窗口小到一定程度仿真会断流 ✗（真机不会 ✓）。
- **1ms 时间量化**：短 RTT 场景的时序与真机不完全可对应 ✗ ⇒ 别用它推断绝对时延 ✓。
- **无 AES / 无真实 socket 语义**：只验证协议状态机与拥塞控制逻辑 ✓。
